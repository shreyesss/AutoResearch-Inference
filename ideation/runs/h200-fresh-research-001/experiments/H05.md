## Source observation

Installed DP synchronization calls dist.all_reduce. #61767 offers CPU recursive doubling; its large multi-node measurements do not predict local DP4 benefit and its source port conflicts.

## Upstream fix

Use a guarded CPU collective for eligible small groups/tensors with normal collective fallback.

## Root transfer prediction (untested)

Shorter exposed CPU control synchronization may improve steps where GPU work waits; observed allreduce duration might instead be arrival skew.

## Baseline eligibility and cheapest first step

Attest process-group backend, group-local ranks, tensor shape and invocation ordering; inspect fixed tags and fallback before adaptation.

## Strongest comparator

Current Gloo call with identical ranks/arrival skew; single-process and balanced timing controls where meaningful.

## Activation denominator

New collective calls / eligible CPU reductions; all-rank entry/exit times and skew.

## Mechanism and competing explanation

Separate arrival wait, communication and exposed CPU critical path; trace only as a diagnostic.

## Reject, stop or defer

Mostly rank skew or hidden time, no eligible calls, inconsistent ordering/tags, or unchanged service despite microbenchmark gain.

## Correctness scope

Group-local rank mapping, sequential/concurrent collectives, fallback, cancellation and idle/wake liveness.

## Workload and held-out conditions

D1/E1 and burst E2, with deliberately balanced versus skewed batches.

## Model statement and experiment

Replace eligible small CPU DP reductions with the recursive-doubling implementation from PR #61767, conditional on exposed synchronization cost. The supplied installed excerpt contains a distributed all-reduce call, while the patch shows the replacement algorithm and engine-state caller. For each four-rank replica, the power-of-two branch requires two exchange rounds; this arithmetic says nothing about serving speed. First confirm the actual process groups, call sites and whether an equivalent implementation is already active. Compare against stock Gloo under matched CPU placement, separating rank-arrival skew from collective service time. The prediction is shorter dispatch gaps when transport overhead is exposed, with negligible benefit when GPU work or late ranks dominate.

**Control:** Attested baseline using current Gloo reductions with matched CPU affinity, thread configuration and telemetry. Compare against supported static CPU-placement tuning before crediting algorithmic gains.

**Correctness:** Check exact int32 SUM equivalence, group-local rank mapping, stateless groups, idle/dummy participation, pause transitions and termination. Audit reserved tags and overlapping invocations; prove call ordering or serialize safely and include its cost. Exercise fallback and failure paths. Map to relevant G01-G05 definitions when supplied; unchanged GPU math does not remove distributed correctness requirements.

**Cost:** Moderate distributed validation effort without a GPU-kernel rebuild. Microbenchmark gains do not estimate serving savings. Use C8*T/(3600*Nqualified); eight-GPU node price is unknown.

**Held out condition:** Primary agent-f75 and fixed Mooncake schedules at seq64. Hold out mixed prefill/decode bursts, highly uneven rank arrivals, pause/resume waves and simultaneous host contention from both replicas.

**Inconclusive if:** Rank timestamps cannot separate arrival skew, process-group compatibility is unresolved, activation coverage is missing, or measured differences remain within full-run uncertainty.

**Metrics:** All-rank call counts and eligible opportunities at each site, including skipped coordination. Activation numerator: replacement calls; denominator: eligible contiguous CPU SUM calls on the intended Gloo group. Record arrival skew, collective completion latency, exposed CPU-to-GPU gaps, host utilization, TTFT tails, request TPOT, exact tokens, throughput, qualified goodput, draft/verify/accepted counters, KV/preemption and replay lag.

**Rejects if:** Equivalent behavior is already active; supported eligible calls show no useful exposed-time reduction; the strongest static comparator matches or beats it; or ordering, correctness or serving regressions occur.

**Supports if:** The replacement reduces collective service time and exposed dispatch gaps, then improves unprofiled serving metrics without distributed failures or tail regressions. Require at least five alternating paired full-run confirmation blocks for small effects, with drift checks, intervals and held-out confirmation.

**Treatment:** Inspect call-site membership and process groups first. Then qualify and test the replacement at worker metadata synchronization, followed by a separately attributed engine-state arm. Use the required staged evaluation sequence.
