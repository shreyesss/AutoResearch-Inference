# Independent PJ01 capture-handoff review

**Accept the source-control clarification; preserve PJ01's deferred status and original baseline.** The native callback is a suitable existing integration point for a fixed, admitted smaller projection. This does not make a native helper executable, capture-safe or numerically verified. No readiness/status upgrade follows.

I followed the exact DFlash capture call, context helper, graph-manager closure and base warmup/record/replay sequence. Pinned DSparkSpeculator inherits DFlashSpeculator and does not override the inspected capture/preparation helpers. Context mappings are filled with PAD before capture; `_prepare_graph_forward` calls `_precompute_context_kv` without dummy override. That helper passes a tensor/list view, while explicit dummy_run selects None. DSpark's context method performs the fused projection, KV slice and norm before checking for None. PAD and None must not be treated as equivalent phase selectors or permission to skip projection.

The callback factory's warmup flag does not branch its context-preparation path. The base manager invokes the warmup closure, constructs a fresh capture closure, then invokes it inside the capture context. Both call preparation before query forward. A candidate installed and kept stable before capture will therefore be reached through that callback for those descriptors. The existing warmup is not proof of successful allocation, external scratch sufficiency, supported reduced-N tactics or complete coverage of eager-tail shapes. The graph mode can also remain NONE when FULL support is unavailable; source existence does not attest enabled capture.

Replay uses the recorded graph, so new eager Python views or toggling an option later cannot update captured pointer arguments. Owner/layout replacement, feature changes and invalidation must use a correct stack lifecycle; the report does not claim to supply one. Admission fallback before native execution is distinct from attempting to recover after an unsafe device/backend failure.

The minimal handoff correctly isolates columns-only PJ01: retain per-layer input quantization, all three norms/inserts, full query modules and original graph/eager partition. Optional round48 input quantization reuse and TR01 row trimming remain separate. The prior processed-weight/scale view arithmetic and module-hook guards are prerequisites, not retested native facts. Smaller N can change numerical reduction/tactics even when algebra matches. External mm_mxfp8 with out=None still leaves real allocation/workspace/current-stream behavior unresolved.

The eight observations are AST inspections. They are not eight target executions, and lexical source predicates alone would not establish arbitrary control-flow properties; reading the actual closure bodies confirms the narrower claims made here. I did not rerun the same AST script as new evidence. No tensor, CUDA, model/backend import, compilation, network or timing occurred.

Next evidence should be a compatible loaded-backend/prepared-tensor receipt followed by separately authorized native differential/capture tests. More symbolic view equations or a new warmup framework are not justified now. The source clarification improves the implementation handoff, with no measured exposure or service benefit and no new identity.
