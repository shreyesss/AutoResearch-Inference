Motivation
SGLang currently supports FlashInfer's SM90 MXFP4 W4A16 CUTLASS MoE path, which was introduced in SGLang
#24816
on top of FlashInfer
#3084
. FlashInfer
#3738
adds a different Hopper path that dynamically quantizes activations to FP8 and runs MXFP4-weight x FP8-activation MoE GEMMs using Humming-style pre-MMA E8M0 scale fusion.
This PR wires that path into SGLang as an explicit opt-in:
--moe-runner-backend flashinfer_mxfp4 \
--flashinfer-mxfp4-moe-precision fp8
The existing
default
and
bf16
behavior is unchanged.
Related work:
SGLang
Add FlashInfer SM90 cutlass MXFP4 MoE backend (W4A16) for GPT-OSS + DeepSeek-V4
#24816
FlashInfer
perf: optimize MXFP4xBF16 & INT4xFP8 and add MXFP4xFP8 CUTLASS MoE backend for SM90
flashinfer-ai/flashinfer#3738
FlashInfer version requirement
This integration intentionally targets the corrected API from FlashInfer
#4431
, where the FC1 and FC2 residual scales are FP32 tensors in local-expert order with shape
[num_local_experts]
. FlashInfer reuses its internal expert permutation to map those scales to routed rows, including global-to-local expert mapping under EP.
The original
#3738
ABI briefly shipped before being reverted from FlashInfer 0.6.17 by
#4411
. It required downstream runtimes to construct routed-row residual tensors during every forward. SGLang does not support that older ABI.
The new option therefore requires both:
flashinfer-python >= 0.6.18
preprocess_moe_weights_for_sm90_mixed_gemm_humming
SGLang currently pins FlashInfer 0.6.17. This PR does not change that global pin. With 0.6.17, selecting
fp8
fails immediately with an actionable error, while all existing FlashInfer paths remain compatible. The dependency, cubin, and JIT-cache pins should be upgraded together in a follow-up change.
GPU validation for this PR used FlashInfer 0.6.18 built from commit
8044d94bf9acc5369857baf88d28906bb32bf264
, which contains the corrected API from FlashInfer
#4431
.
Modifications
Runtime selection and compatibility
Add
fp8
to
--flashinfer-mxfp4-moe-precision
.
Select the new path only for
flashinfer_mxfp4
on SM90.
Keep W4A16 as the default SM90 behavior.
Reject the SM90-specific
fp8
option on SM100 and SM120 to avoid confusing it with their existing MXFP8 activation paths.
Require the corrected FlashInfer 0.6.18+ API instead of accepting the older routed-row residual ABI.
Pass
use_wfp4afp8_humming=True
only when the new path is selected. The keyword is omitted completely for FlashInfer 0.6.17 compatibility.
Weight preprocessing
Use
preprocess_moe_weights_for_sm90_mixed_gemm_humming
for both FC1 and FC2 during post-load processing.
Store the folded interleaved weight scales produced by FlashInfer.
Store
residual * 64
as one FP32 value per local expert for FC1 and FC2.
Preserve GPT-OSS gate/up layout conversion and its existing padding rules.
Fill synthetic E8M0 scale padding from an existing scale in the same expert, preventing padding from changing that expert's min/max exponent range.
Support both the GPT-OSS MXFP4 quantization path and the DeepSeek-V4 MXFP4 expert path.
Kernel invocation
Construct the five Humming quant-scale slots expected by the corrected FlashInfer API:
FC1 folded weight block scales
FC1 per-local-expert residual scale, including the fixed
2^6
compensation
Reserved scalar FC2 activation scale
FC2 folded weight block scales
FC2 per-local-expert residual scale, including the fixed
2^6
compensation
The existing TP/EP topology is forwarded to FlashInfer so it can map global expert IDs to the corresponding local residual scale.

A coordinated FlashInfer 0.6.18 dependency update is required before production enablement.

fix(mxfp4): exclude pre-rounded hidden tail from Humming scale range
…
d312c83
FusedMoE rounds hidden_size up (GPT-OSS 2880 -> 3072) BEFORE
create_weights whenever the flashinfer_mxfp4 backend is selected -- the
same gate that later selects _fi_kernel = "cutlass_sm90". The SM90
post-load processor therefore sees K_un = 3072 = K_pad, so the
preserve_expert_range fill guarded an empty region, while scale columns
[2880, 3072) INSIDE K_un keep the _UE8M0_ONE (127 = 2^0) buffer fill
that the naive-copy loader never overwrites.

Humming derives each expert's residual from its min/max E8M0 exponents.
The stale 127s sit far above any real per-expert max, so they inflate
the range, shift the residual, and perturb the REAL weights on repack.
Same story on w2's K rows.

Fix: FusedMoE records hidden_size_unpadded before the round-up,
create_weights stores it as _unpadded_hidden, and the w13/w2 scale
copies stop at the checkpoint's K (ceil'd to the 32-wide group boundary)
so the never-written tail is covered by the existing per-expert fill.
The tail's weight bytes are zeros (never written), so whatever scale
sits there multiplies zero -- numerically inert in the GEMM. The trim is
gated on preserve_expert_range, so the W4A16 path stays byte-identical.
The SM120 helper needs no change: it has no per-expert range statistic,
and its stale scales multiply zero weights.

Add test_humming_range_ignores_prerounded_hidden_tail, which builds the
production shape (buffers at 3072, checkpoint data to 2880, real scales
well below 127) and asserts the per-expert residual is invariant to the
tail content. The existing tests missed this twice over: they construct
the method at 2880 directly (never seeing FusedMoE's pre-round), and
their random scales span 125..130, which straddles 127.
fix(mxfp4): compare full FlashInfer Version for the Humming gate
…
2ec959a
The 0.6.18 gate compared Version(...).release[:3] >= (0, 6, 18). The
release tuple drops prerelease markers -- Version("0.6.18rc1").release
is (0, 6, 18) -- so 0.6.18rc*/0.6.18.dev* builds, cut before the

through the gate. Compare full Versions instead:

    Version(flashinfer_version) >= Version("0.6.18")

which rejects rc/dev prereleases of 0.6.18 while still accepting
0.6.18.post*/+local and anything newer (including dev builds of later
versions). Applied to all three copies of the gate: the module-level

refactor(mxfp4): gate Humming on check_pkg_version_at_least
…
409f07e
Replace both hand-rolled FlashInfer version gates (try/except around
__version__ parse + hasattr probe) with the existing
check_pkg_version_at_least("flashinfer_python", "0.6.18") helper. It
already does the prerelease-aware full-Version compare the previous
commit introduced, and returns False when the package is absent, so the
try/except scaffolding and the InvalidVersion handling collapse into one
call at each site.

Dropping the hasattr probe is safe: both weight processors import
preprocess_moe_weights_for_sm90_mixed_gemm_humming directly at use time,
so a build that misreports its version still fails loudly with a clear
ImportError there. As a kernel package, flashinfer_python also honors
SGLANG_SKIP_SGL_KERNEL_VERSION_CHECK=1 through the helper -- the
standard escape hatch for source builds with stale metadata.

The unit test's HAS_CORRECTED_HUMMING_API guard keeps its explicit
Version + hasattr form on purpose: under the skip env the helper returns
True unconditionally, which would un-skip the Humming tests on an old
FlashInfer and fail them spuriously; the test guard must reflect the
actually-installed API.
