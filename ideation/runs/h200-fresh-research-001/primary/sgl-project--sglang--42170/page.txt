Single-node H20-3e report: vision CP + DSpark, long-prefill improvements, and three upstream PRs
Thanks for maintaining this roadmap and for the kernel/CP work behind it. We have been integrating and testing DeepSeek-V4.1-Flash on
one 8× NVIDIA H20-3e server
, with text, image+text, tool calling, streaming, and cache reporting as requirements.
Our October 5–7 experiments started from
unmodified SGLang v0.5.21
and ended with a production deployment of a pinned integration build. The strongest paired comparisons were:
524,032-token cold TTFT: 323.261 → 25.531 s
, a
92.1% reduction / 12.66× speedup
.
C64 aggregate output: 877.01 → 2,534.61 token/s (+189.0%)
; per-request streaming decode:
15.69 → 49.10 token/s (+213.0%)
.
These are
whole-deployment improvements
, not the isolated effect of any one PR. We have contributed
#39306
,
#42922
, and
#42924
; their narrower validation and attribution are described below.
1. Setup and measurement scope
Hardware: 8× H20-3e, SM90, approximately 140 GiB visible memory per GPU, NVLink/NVSwitch (NV18 topology), 2 TiB host RAM, two NUMA nodes.
Baseline: v0.5.21 at
e00930c5489053f26d86b179cee0d087f846acbb
,
TP8/EP8, DSpark block size 5 already enabled
, no CP, no decoder bounded replay, GPU-resident Engram, no HiCache.
Final:
TP8/EP4, CP8 interleave, CP decode-attention TP, DSpark5, decoder SWA bounded replay
, FlashInfer MXFP4 MoE with FP8 precision; Engram host table in
per_rank
layout, NUMA binding, HiCache ratio 1.5 /
write_through
.
Both use a 524,288-token context limit, static memory fraction 0.8, chunk size 8192 and max-running-requests 64. Prefill CUDA graphs remain disabled; decode CUDA graphs are enabled.
Final local integration revision:
79b468a7435e1bd29ad0d377587ff10b3c214ba3
(
not an upstream release/commit
). Runtime: PyTorch 2.13.0+cu130, Triton 3.7.1, FlashInfer 0.6.18; the final DeepGEMM integration uses
sgl-deep-gemm 0.2.2
. This is a backported integration, not a claim that stock v0.5.21 supports this configuration.
The baseline and final integration use the same V4.1 model weights on the same hardware. No P/D disaggregation is used. All performance below is from a single eight-GPU server. These results describe the pinned October 5–7 snapshots, not the latest heads of every roadmap PR.
Comparison boundary:
the near-512K and C64 baseline measurements were supplemented using exactly the final workload construction, warmup and three measured rounds. Input hashes, token counts, output lengths and zero-cache-hit conditions match. Other baseline cells are historical references: cold-prefill nonces differ, and the early natural-generation prompts/warmup procedure differ from the final protocol. The tables explicitly mark the paired supplements with †. Runs were sequential, on different dates, not randomized interleaved A/B trials.
2. Optimization path and what we retained
Use vision-compatible CP as the foundation.
We chose
model: DeepSeek V4.1 vision CP and single-owner image encoding
#40219
for its merge-before-shard multimodal preparation and single-owner image encoding. We adapted the owner callback API and fixed physical request-pool row mapping in the Torch prefill indexer. We borrowed the replay-tail idea from
[DSV4.1] DeepSeek-V4.1 support prefill CP
#40161
later, rather than importing its entire P/D integration.
Integrate the Hopper paths and H20 configurations.
This included
[Perf] Optimize DeepSeek V4.1 Flash Hopper paths and Blackwell prefill selection
#41251
,
[DSV4.1] Add H20 block-FP8 tuned configs
#41098
and the relevant
[DSV4.1] Enable Hopper decode optimizations for TP8
#39114
path, plus scorer/Top-K, compression, RoPE, dispatch and preparation changes listed below. We checked actual dispatch and added tables for six further missing matrix shapes encountered in this integration; small tuning differences below 3% retained the default. These additional local tables are distinct from the original six tables in
[DSV4.1] Add tuned H20-3e block-FP8 GEMM configs
#39306
.
Enable Engram host storage and HiCache together, then tune EP.
The
per_rank
layout shards the host Engram table across ranks rather than replicating the entire table eight times. The combined memory configuration increased the engine-reported KV token-pool capacity by about 31.25% relative to our preceding GPU-Engram/HiCache-ratio-2/memory-fraction-0.88 configuration, with essentially unchanged near-512K TTFT. This is a combined memory-layout result, not a standalone offload speedup.
Add decoder bounded replay while preserving image requests and DSpark.
After the last KV-source layer, replay shortens the late-layer token rows. We added tail-aware CP gather, global token indices for logits/DSpark, original CP-owner mapping, and preservation of canonical image IDs. This became
[DSV4.1] Support decoder SWA bounded replay with vision CP and DSpark
#42924
, with
[DSV4.1] Fix Torch prefill indexer request-pool rows under CP
#42922
as a separate row-mapping fix.
Add fused prefill scoring and native SM90 block32 FP8 GEMM.
[DSV4.1] Fuse Hopper prefill indexer scoring into one Triton kernel
#42365
fuses indexer score/ReLU/weighting/head reduction;
[SM90] Use native block32 DeepGEMM for DeepSeek-V4.1
#42604
enables the supported native DeepGEMM linear paths. We retained the existing compact-candidate path and fallbacks. Routed MXFP4 experts still use FlashInfer.

Experiments not retained:
TP8/EP1 with Marlin W4A16:
C64 aggregate output 1,797.47 token/s, versus 2,362.80 for the then-current EP4 build. Both backend and parallelism changed, so this is not an isolated EP comparison.
TP8/EP1 with an adapted FlashInfer W4A8 path:
preserve logical shard boundaries, then pad the 288-wide expert intermediate dimension to 384 for the required 128 alignment, including gate/up halves, down columns and scale handling. It passed our operator/model checks, but C64 reached 2,139.99 token/s, still below EP4.
TP8/EP2:
slightly better TTFT, generally worse natural-generation aggregate throughput.
Chunk 8192 → 16384:
about 1.5% better long TTFT, about 4.6% worse C64 aggregate output; retained 8192.
CP local-projection deduplication:
approximately 21–33% faster in the projection+gather microbenchmark, only 0.4–1.1% TTFT improvement end to end with mixed throughput results; removed.
[DeepSeek V4.1] an FP8 Tensor Core path for the FP4 grouped indexer
#40160
H32 adaptation:
correctness checks passed, but none of the six tested shapes beat the existing scorer; not dispatched in production.
The medium-mHC path remained disabled pending further validation.
