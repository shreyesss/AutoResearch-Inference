# E01 walkthrough: length-aware candidate-block selection

**Scope:** explanation and source audit only. No GPU run, source modification, image build or new experimental outcome. Supplement to [E01](../experiments/E01.md), not a replacement for its immutable memory record.

## 1. Define the operation

The candidate-source indexer groups historical-position scores into blocks and publishes selected block IDs. Later consumer indexers use that candidate pool. Candidate selection and consumer score computation are separate operations. #61830 requests consumer sparse scoring on H20/SM90; the configured B200 sparse backend already provides that capability. E01 concerns the source selection cost.

Sources: [#61830](https://github.com/vllm-project/vllm/issues/61830), [#61039](https://github.com/vllm-project/vllm/pull/61039), [pinned sparse backend](https://raw.githubusercontent.com/vllm-project/vllm/ac9126e58aa7bbab1856ba6593ba4d5003fea516/vllm/v1/attention/backends/mla/sparse_indexer.py).

## 2. Establish baseline applicability

The configured profile has maximum context1,048,576 and two TP1/DP4/EP4 replicas. The launcher enables MXFP4 indexer cache and sparse logits. Native agent-f75 uses8,192 input and1,024 output tokens. Actual deployed digest, source modifications, checkpoint candidate parameters and captured runtime tensor dimensions remain unverified.

The pinned `ac9126e…` candidate implementation derives block count from tensor width, writes scores across that width, and applies `torch.topk`. Its logits loads mask invalid positions. Thus the diagnosis is oversized block-score/selection work, not proof of dense dot products against a million live keys. [Pinned candidate implementation](https://raw.githubusercontent.com/vllm-project/vllm/ac9126e58aa7bbab1856ba6593ba4d5003fea516/vllm/model_executor/kernels/attention/dsa/candidate_blocks.py).

For a ratio-1 source row with block size8, a1M-wide buffer represents131,072 block positions while an8K request has1,024 valid blocks. After1K generated tokens it has approximately1,152. These calculations assume the described checkpoint geometry; record actual configuration before using them as runtime facts.

## 3. Proposed mechanism

The merged implementation computes per-row valid block counts, bounds the block-score loop and passes those counts to DeepSelect. It retains a full-width fallback for unsupported layouts/backends. It also retains a maximum-width score workspace: reduced processing does not establish proportional memory-capacity savings. [Merged implementation](https://raw.githubusercontent.com/vllm-project/vllm/7c3f7e5500c85aacb72aab50bd1ce05485b1d73a/vllm/model_executor/kernels/attention/dsa/candidate_blocks.py).

Keep the numerical mode fixed for the primary comparison. The PR's BF16-retention change is a separate effect. Where BF16 is already inherent in the dependency API, record that fact and do not invent a second conversion arm.

## 4. What can be argued without a benchmark

For ordinary finite valid scores, with identical dtype and block scoring, removing padding scored as negative infinity cannot remove a better valid candidate. If fewer than K valid blocks exist, retain them and pad the result. Preserve the newest-block rule. This is a limited equivalence argument, not proof of the entire GPU implementation.

Exceptions requiring direct checks: cutoff ties, NaNs, masked/negative-infinity values, empty and partial blocks, speculative row-to-request bounds, output padding, layouts, and repeated CUDA graph replay with changing lengths. Different tied candidates may be score-equivalent but need not produce identical model outputs. BF16 rounding is outside the same-score equivalence argument.

## 6. Minimal discriminating evaluation

### Eligibility and correctness first

Save image/source/checkpoint identities. Observe calls on a bounded diagnostic pass: logits shape/dtype, valid ends, candidate K/block size, row repeat, layout, DeepSelect/fallback choice. Confirm the actual source producer executes. If equivalent optimization already exists, stop the port experiment and record that disposition.

Reuse upstream candidate tests; extend only missing deployment shapes. Include contexts just below/at/above block and candidate-capacity boundaries, differing request lengths in one batch, empty/padded rows and changed-length graph replay. Compare candidate sets for untied finite scores; define tie handling explicitly. Verify padding/bounds and model outputs where changed selections or precision require it. Do not treat arithmetic smoke as comprehensive indexer correctness.

### Isolate the intervention

- A: actual baseline implementation and dtype,1M limit.
- B: length-aware candidate selection at the same dtype,1M limit and dependency set.
- C: separately test BF16 retention only if a distinct meaningful arm exists.

If separating the patch requires an adaptation, label it as such and test it; do not pretend that B is automatically the entire upstream cherry-pick. A dependency upgrade requires its own control to avoid attribution errors.

### Existing performance evaluations

Native E1: retain agent-f75, output length, prefix construction, warmup and measurement protocol; compare c256/384/512 with the same seq128 override. Profile only a separate diagnostic pass. Record indexer stage and whole-step GPU time plus observed output lengths, acceptance, TTFT/TPOT, failures and SLO-qualified goodput.

Mooncake E2: unchanged windows and scorer; group diagnostic results by actual context and decode occupancy. Preserve overall trace scores. At1× compare matched-load latency; use the existing trace-speedup sweep for capacity. Never infer throughput improvement solely from a faster kernel or an arrival-limited replay.

An optional2×2 diagnostic—old/new selection crossed with large/smaller supported maximum context, on the same requests—tests whether excess configured width causes the cost. Keep batch/workspace/graph conditions controlled when attributing kernel effects. A smaller maximum context changes the service contract and KV budgeting; it is not an interchangeable production baseline, and long Mooncake requests must never be truncated to fit it.

## 7. Decision and bounded expectations

Use the common [protocol](../PROTOCOL.md) for repeated paired runs, practical thresholds and uncertainty. Choose the primary endpoint before confirmation: qualified capacity, or matched-load latency with explicit capacity guardrails. Successful tests on long contexts cannot silently substitute for the current8K workload.

A useful upper-bound check is Amdahl's law: if the targeted stage occupies fraction f of the relevant serial critical path and becomes r times faster, the idealized whole-path speedup is1/((1-f)+f/r). For hypothetical f=0.04 and r=10, the ceiling is about1.037×. These are illustrative numbers, not measured B200 fractions. GPU overlap, DP synchronization, queueing and CPU limits make real serving behavior more complicated.

Promote only if correctness, mechanism and end-to-end evidence agree. A kernel-only win remains a kernel result. Inactive path is not applicable; noisy data is inconclusive; a reproducible semantic regression rejects the change for this scope.

**Current conclusion:** a technically credible first inspection, not a proven largest improvement. Configured-source waste is confirmed. Deployed-path identity, runtime cost fraction and B200 serving benefit remain open.
