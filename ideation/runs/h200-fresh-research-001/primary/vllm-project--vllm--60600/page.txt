🐛 Describe the bug
HummingExpertsBase._supports_quant_scheme()
lists MXFP4 weights with block-FP8 activations (group 128, float32 scales) as a supported MoE pair. The comment says it works on Hopper (
fused_humming_moe.py#L325-L328
):
# MXFP4 weight (group-32 e8m0) with block-FP8 activation
# (group-128 float32). Runs via WGMMA software dequant, so it
# works on Hopper (SM90/H200) as well as Blackwell.
(
kMxfp4Static
,
kFp8Dynamic128Sym
),
tests/quantization/test_humming_mxfp4_block_fp8.py
(from
#51332
) asserts that this pair is allowed.
humming-kernels 0.1.16 refuses the pair.
is_humming_schema_compatible()
in
humming/schema/humming.py
(lines 499 and 501) requires group-wise input scales to be e8m0 or e4m3 when the weights are FP4 with group scales:

The rule does not depend on the GPU. So vLLM's backend selection accepts
kFp8Dynamic128Sym
with MXFP4 weights, and the run then fails at weight load in
check_and_fallback_input_schema()

allow_fallback=True
the input silently becomes per-token FP8 instead.

The kernel itself can run this layout. When the compatibility check is bypassed, a dense MXFP4 GEMM with group-128 float32 input scales runs on H200 and its output matches the reference (kernel error 0.0017-0.0032, the same level as per-token FP8). So the mismatch is between vLLM's supported-pairs table and humming's schema rule, not a missing kernel.
A related limit on SM90: MXFP8 inputs (group 32, e8m0 scales) pass
is_humming_schema_compatible()
but have no SM90 kernel.
humming/tune/candidate.py:287
rejects every WGMMA candidate with "WGMMA input scales must use float32 storage, got float8e8m0", and
humming/tune/sm90_policies.py:256
then raises "no legal grouped-scale SM90 schedule".
For context, the dense-GEMM probe on H200 (N=2048, K=4096, MXFP4 weights) also showed that group-wise input scales are much slower than per-token on WGMMA at M=4096: 535.7 us for group 128 and 1720 us for group 32 (fp32 scales), against 72.2 us for per-token FP8 and 110.9 us for BF16.
Questions
Should humming accept float32 group scales with MXFP4 weights on SM90 (the kernel runs), or should vLLM drop
(kMxfp4Static, kFp8Dynamic128Sym)
on SM90 and fix the comment and the test?
Is e8m0 input-scale support on WGMMA planned? Without it, MXFP8 activations cannot run on Hopper.
PR
#59488
makes
--quantization-config.moe.activation
select the Humming MoE activation format for MXFP4 checkpoints. Until this is settled, it refuses
fp8_per_block_dynamic
and
mxfp8
on SM90 Humming at startup.
