Part of
#41589
(DeepSeek-V4.1 prefill optimizations, split into smaller PRs).
Motivation
The low-ratio (ratio 1/2) prefill indexer ran many small kernels per layer, sorted and remapped its selection before attention, had a schedule that is quadratic in a request's rows, and synchronized with the host several times per step.
Modifications
Fused index-Q kernel in the prefill indexer
: prefill query and head-weight prep goes through
index_q_rope_pack_weights
(
_index_q_and_weights
), shared with decode.
Prefill top-k written straight into the raw selection
: the DeepGEMM prefill top-k emits request-local compressed positions directly into the buffer sparse prefill reads. Pool slots (
page_indices
) are only derived when this forward's attention reads them (trtllm, non-sparse extend, sm120, late-layer tail, request window, or
SGLANG_OPT_FLASHMLA_SPARSE_PREFILL
off).
Selection
is removed; the output buffers are fields of
PrefillInputs
/
DecodeInputs
/
CapturedPrefillInputs
.
write_selection
keeps only the CP dense-blocks path and no longer sorts.
Row-pair request ids for the paged sparse indexer schedule
: DeepGEMM's paged sparse-logits metadata walks back over equal request ids once per row. Ids unique per consecutive row pair of a request (never spanning two requests) bound the walk to one step; logits are unchanged.
No host syncs in the prefill forward
:
get_deep_gemm_prefill_data
builds the flattened-K layout for the whole batch from host lengths instead of a per-request loop indexing with device scalars.
New
async_h2d
in
srt/utils/common.py
(pinned, non-blocking; the counterpart of
async_d2h
), used for the request starts, row-pair ids, CP rows, tail rows, and the engram history.
Engram's
repeat_interleave
takes
output_size
from
extend_seq_lens_cpu
.
No
record_stream
on the mHC stats input
: the stats kernels read the residual on the side stream, and every consumer joins that stream on the main stream while the residual is still referenced, so
record_stream
only delayed the reuse of each freed residual. Without the host syncs the host runs further ahead, and those delayed frees piled up to several full residuals and exhausted the allocator.
Tests
:
test_dense_prefill_indexer.py
and
test_dsv4_nonpaged_indexer.py
follow the new interfaces.
Checklist / TODO
Add coverage for the row-pair ids and the batched flattened-K layout.

[DSv4.1] Row-pair request ids for the paged sparse indexer schedule
…
60dc919
DeepGEMM's paged sparse-logits metadata walks back over equal request ids to a row's request start once per row, which is quadratic in a request's rows (~11 ms per call at 16384 rows on GB300). Ids that are unique per consecutive row pair of a request, never spanning two requests, bound the walk to one step while keeping the BLOCK_Q=2 pairing; the logits are unchanged. [DSv4.1] Remove host syncs from the prefill path
…
79f7467
Prefill synchronized with the device ~20 times per step at bs=1: the flattened-K layout of the DeepGEMM prefill indexer indexed req_to_token per request with a device scalar and copied the request starts from pageable memory (twice per index layer), the row-pair ids and the CP rows copied pageable lists, engram's repeat_interleave sized its output from a device sum, and the engram history went up as a pageable copy before the forward. The layout is now built for the whole batch from host lengths, host lists go up through the new async_h2d (pinned, non-blocking, next to async_d2h), and repeat_interleave gets its output_size from extend_seq_lens_cpu. On 4x GB300 with 40K-token prompts the other sites took a prefill step from 20 syncs to 1; the remaining one was the engram history copy, fixed here but not re-measured.

…
3814a5c
The pairing is only correct because DeepGEMM's paged scheduler has
BLOCK_Q == 2: the ids delimit what it already groups, and its page table is

Cover it too. The existing cases are single-request, so nothing saw a pair
