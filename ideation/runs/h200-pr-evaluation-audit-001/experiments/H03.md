# H03 — Reduce CPU DP metadata collective cost

Lane: **main**. Live-layout priority: **3**. Status: conditional plan; no GPU test or measured gain.

## Problem and causal hypothesis

Per-step CPU metadata synchronization may delay GPU dispatch even when the GPU collective itself is fast.

## Applicability to our H200 deployment

DP4 is live. Identify actual transport and separate rank arrival skew from transport time; require CPU synchronization on the critical path.

## Isolated control and treatment

A: existing CPU transport. B: isolated #61767 implementation, same participant groups, affinity and workload.

## Evaluation and predicted mechanism

E1: native agent-f75; E2: frozen Mooncake median/burst/cache-heavy. H200 capacity discovery and held-out confirmation in PROTOCOL.md.

Measure: Collective wall time after last rank arrives; rank skew; CPU utilization; GPU idle gaps; p99 ITL/TTFT and goodput.

## Why an additional evaluation is or is not needed

E1/E2 suffice. Add CPU spans and upstream distributed stateful/stateless group tests, including orderly shutdown.

## Decision and falsification

Apply [the preregistered protocol](../PROTOCOL.md). Confirm path and missing behavior before spending GPU time. Support requires correctness, predicted mechanism movement and a useful held-out SLO outcome. Reject an active, well-measured change with no useful endpoint gain or a correctness/tail regression. Mark absent-path, underpowered or failed-replay cases inapplicable/inconclusive; do not label them disproven. Correctness lanes establish only scoped correctness.

## Evidence limits

Inherited primary review, not freshly downloaded here. Multi-node microbench gains cannot be transferred to two local four-rank groups.
