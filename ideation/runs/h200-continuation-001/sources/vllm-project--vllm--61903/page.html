Overview

On H100/H200, GateLinear runs fp32 router weights above 32 tokens as F.linear(x.float(), w), an fp32 SGEMM on CUDA cores. SM100 has the CuteDSL BF16x3 kernel for this (#47973, #55899) and gfx950 has a hipBLASLt one (#52668). SM90 had nothing. This PR adds a CuteDSL BF16x3 kernel for SM90 behind the existing BF16x3 tier.

Models on main that hit this path on SM90 (fp32 router weight, bf16 activations): MiniMax-M2/M2.5/M3, GLM-4.5/4.6/4.7 and GLM-4.5-Air, Hunyuan-V3/V4, Step-3.5-Flash, ERNIE-4.5, Ling 2.0 (router_dtype: fp32), and others. The new models are on it too. Beam-1.0 (#62074) keeps fp32 router weights (5120, 256), and Muse Spark Open (#61879) keeps (8192, 256). Both shapes are in the fp32 GEMV table since #62042 and #62126, so on H200 every batch above its limit runs the fp32 SGEMM.

The first revision of this PR used Triton. It is now CuteDSL, like the other router GEMMs in the tree, and uses the VllmJitKernel warmup contract.

Claims

  • Router GEMM on 1xH200, inside CUDA graphs with cold L2, over 10 router shapes: 1.6-3.8x faster at 33-512 tokens and 3.3-7.7x faster at 1024-16384 tokens.
  • MAE against an fp64 reference is 0.16-0.73x that of the fp32 SGEMM it replaces, at every shape and token count measured.
  • MiniMax-M2.5 FP8, TP2 on 2xH200, with main and PR alternating in one container: TTFT 3-5% lower for 8K and 32K prompts, prefill throughput 4-6% higher, and on a mixed 1K-in/128-out workload 4.6% more output tokens/s and 4% lower TPOT. GSM8K accuracy is unchanged and its wall time is 2.5% lower.
  • In eager mode one router call costs 17-18 µs of host time, against 21-36 µs on main.
  • Beam-1.0 FP8 on one H200, as one TP8 rank (all 52 layers, dummy weights, main and PR alternating): an 8K prefill chunk takes 14.0% less time (155.3 to 133.5 ms), and a decode step at 64 and 128 requests takes 7.4% and 10.9% less.
  • On SM90 the fp32 GEMV now runs up to 24 tokens instead of 32, where the new kernel is faster. The GB200 rule for (5120, 256) from [Kernel] Add router GEMM kernels for (5120, 256) and BF16 output to ll_bf16_gemm #62042 and the B300 rule for (4096, 352) from Add Step-5 Preview support #61727 stay Blackwell-only.
  • No change for 24 or fewer tokens on the fp32 GEMV shapes, under VLLM_BATCH_INVARIANT, or on other architectures.

Benchmark script 
"""PR component benchmark: SM90 router GEMM for fp32 gate weights, main vs this PR (1xH200).

main: F.linear(x.float(), W) for M > 32 (fp32 SGEMM). PR: torch.ops.vllm.sm90_bf16x3_router_gemm.
Each number is the per-call time inside one CUDA graph that replays the op on N rotating copies of
(x, W) whose footprint is >= 4x L2, so every call starts with cold weights. MAE is against fp64.
"""

import json
import os
import statistics

import torch

import vllm.model_executor.layers.fused_moe.router.bf16x3_router_gemm_sm90  # noqa: F401

torch.set_float32_matmul_precision("highest")
dev = torch.device("cuda")
L2_BYTES = torch.cuda.get_device_properties(dev).L2_cache_size
print("device", torch.cuda.get_device_name(), "torch", torch.__version__, flush=True)

SHAPES = {
    "MiniMax-M2/M2.5": (3072, 256),
    "MiniMax-M3": (6144, 128),
    "GLM-4.5/4.6/4.7": (5120, 160),
    "GLM-4.5-Air": (4096, 128),
    "Hunyuan-V3": (4096, 192),
    "Hunyuan-V4": (2816, 256),
    "Step-3.5-Flash": (4096, 288),
    "Ling-flash-2.0": (4096, 256),
    "ERNIE-4.5-300B": (8192, 64),
    "Step-5": (4096, 352),
}
MS = [int(m) for m in os.environ.get("MS", "33,64,128,256,512,1024,2048,4096,8192,16384").split(",")]
SCALE = 0.053


def graph_time_us(fns, reps=7):
    for f in fns:
        f()
    torch.cuda.synchronize()
    g = torch.cuda.CUDAGraph()
    with torch.cuda.graph(g):
        for f in fns:
            f()
    g.replay()
    torch.cuda.synchronize()
    times = []
    for _ in range(reps):
        s = torch.cuda.Event(enable_timing=True)
        t = torch.cuda.Event(enable_timing=True)
        s.record()
        g.replay()
        t.record()
        t.synchronize()
        times.append(s.elapsed_time(t) * 1000 / len(fns))
    return statistics.median(times)


def mae(out, ref):
    return (out.double() - ref).abs().mean().item()


def main_path(x, w):
    return torch.nn.functional.linear(x.float(), w)


def pr_path(x, w):
    return torch.ops.vllm.sm90_bf16x3_router_gemm(x, w)


rows = []
for name, (k, e) in SHAPES.items():
    gen = torch.Generator(device=dev).manual_seed(0)
    for m in MS:
        nc = int(min(64, max(4, -(-4 * L2_BYTES // (m * k * 2 + e * k * 4)))))
        xs = [torch.randn(m, k, generator=gen, device=dev).to(torch.bfloat16) for _ in range(nc)]
        ws = [torch.randn(e, k, generator=gen, device=dev) * SCALE for _ in range(nc)]
        ref = xs[0].double() @ ws[0].double().T
        row = {"model": name, "K": k, "E": e, "M": m}
        for label, fn in (("main", main_path), ("pr", pr_path)):
            row[f"{label}_us"] = round(graph_time_us([lambda i=i: fn(xs[i], ws[i]) for i in range(nc)]), 2)
            row[f"{label}_mae"] = mae(fn(xs[0], ws[0]), ref)
        row["speedup"] = round(row["main_us"] / row["pr_us"], 2)
        rows.append(row)
        print(json.dumps(row), flush=True)
        del xs, ws
        torch.cuda.empty_cache()

os.makedirs("control/artifacts", exist_ok=True)
with open("control/artifacts/pr_component.json", "w") as f:
    json.dump({"device": torch.cuda.get_device_name(), "torch": torch.__version__, "rows": rows}, f, indent=1)

Details

Kernel. The MMA runs swapped: 64 experts form the wgmma M dimension and tokens the N dimension (32 to 128 per CTA), so small batches still fill the instruction. One TMA warp brings fp32 weight tiles and bf16 token tiles into shared memory. The MMA warpgroup reads each k16 slice of its weight fragment as fp32 and splits it in registers into three bf16 terms. Each term keeps the top 16 bits of what is left, so the three terms sum back to the weight bit for bit. It then issues register-A wgmma against the token tile, and splits the next slice while the current one runs. Products with bf16 activations are exact in fp32, so all error comes from accumulation:

  • The first-term products go to a tensor-core partial that starts from zero every K-tile (64 or 128 wide). It is then added into an fp32 register accumulator.
  • The second and third terms are about 2^-8 of the output. They keep their own partial across K, as the SM100 kernel does. This is the one numerical change from the Triton revision, which promoted all three terms every K-tile. It makes the largest tiles up to 9% faster. The worst MAE in my checks is 0.87x of the fp32 SGEMM's (GLM-4.7 shape, 7 tokens).

Split-K uses a thread-block cluster of up to 8 CTAs. Each CTA writes its partial tile to its own shared memory, reusing the weight stages, and after a cluster barrier sums one slice of the tile over all peers through DSMEM, in rank order. Results are deterministic, and there is no workspace and no second kernel. There is no host sync and no data-dependent shape, so the op is safe to capture in CUDA graphs.

Configs. There is no autotuning. _pick_config scores 4 tiles x 4 splits with a fixed cost model: waves times per-CTA time. A wave is one CTA per SM, and clusters of 4 or 8 only fill 15/16 of the SMs (120 of 132; at one CTA per SM, cuOccupancyMaxActiveClusters gives 30 clusters of 4 and 15 of 8 on H200). The per-tile costs were fitted to H200 timings. Over 10 shapes and 14 token counts, the rule is within 0.1% (geomean) of the fastest of the 16 configs per cell, and at most 4% slower. Each of the 10 shapes reaches 9-13 configs between 1 and 16384 tokens, at about 1 s of compile each.

Warmup. The kernel is a VllmCuTeDSLJitKernel. GateLinear registers it with its (K, E) and max_num_batched_tokens, as it does for ll_fp32w and as #50177 does for SM100. Warmup traces dispatch over 1..max tokens and compiles each key from fake tensors, with no launch. In the end-to-end runs above, the PR arm warmed 13 keys in about 10.5 s at startup. The JIT monitor logged no compile of this kernel while serving; it logged two fused_moe_kernel Triton compiles on both arms.

Host overhead. Outside CUDA graphs (mixed prefill/decode batches above the capture sizes), the host cost per call matters as much as the kernel. _pick_config is cached, and the launch is one TVM-FFI call. Eager host time per call on an idle H200 host:

M=64 M=930 M=4096
main, fp32-GEMV dispatch op (MiniMax-M2.5 shape) 26.3 µs 29.2 µs 28.9 µs
PR, same op 18.1 µs 18.4 µs 18.3 µs

Integration.

  • allow_bf16x3_router_gemm is now also true on SM90, with the same K % 8 == 0 condition as SM100. bf16x3_router_gemm_module() returns the SM90 module on SM90 and the SM100 module otherwise. The fp32-GEMV dispatch op and tier 4 use it.
  • In the fp32-GEMV dispatch op, SM90 bf16 inputs use the fp32 GEMV up to 24 tokens. The (5120, 256) GB200 rule from [Kernel] Add router GEMM kernels for (5120, 256) and BF16 output to ll_bf16_gemm #62042 and the (4096, 352) B300 rule from Add Step-5 Preview support #61727 are in the non-SM90 branch unchanged.
  • bf16x3_router_gemm_cutedsl.py is renamed to bf16x3_router_gemm_sm100.py, next to bf16x3_router_gemm_sm90.py.
  • The kernel is the custom op torch.ops.vllm.sm90_bf16x3_router_gemm, as [Perf] Improve BF16x3 router GEMM accuracy and make it default on sm100 #55899 does for SM100. The fp32-GEMV shapes keep dispatching on the runtime token count inside fp32_router_gemm_dispatch.
  • PDL is always on. SM90 supports it.

Alternatives measured on H200.

  • The Triton revision of this PR. This kernel is 1.25x faster (geomean over 10 shapes and 15 token counts). It is slower only for ERNIE-4.5 (E=64) at 128 or fewer tokens, where 9.6 µs vs 7.2 µs: one 64-expert tile and at most 8 splits leave most SMs idle. It is still 1.55x faster than main there.
  • One cuBLAS GEMM over the stacked (3E, K) bf16 weight, which is what gfx950 does: MAE 1.4e-6 to 4.3e-6 for the Step-5 shape, worse than the fp32 SGEMM's 3-5e-7.
  • A round-to-nearest split, like the SM100 kernel's but without sub.rn.f32x2 (sm_100 only): 0.5-4% slower than the truncating split at 64-8192 tokens on the Step-5, Beam-1.0, MiniMax-M2.5 and Muse shapes. Both MAEs are well below the fp32 SGEMM's. The other way round, the truncating split in the SM100 kernel on B200 is 0.1-2.3% slower than its own split on the same shapes, so each kernel keeps its own.
  • Two bf16 terms (BF16x2): 16 of fp32's 24 significand bits. Even with exact accumulation, that alone gives an MAE of 5.7e-6 to 7.4e-6 at 1024 tokens on the Step-5, Beam-1.0 and MiniMax-M2.5 shapes, against 0.8e-6 to 1.4e-6 for the fp32 SGEMM.
  • A pre-split weight kept in memory: needs 1.5x the fp32 router weight per layer (about 760 MB per rank for 88 layers of Step-5). The in-register split needs no extra memory.
  • One promoted partial for all three terms per k16 slice, instead of keeping the small terms apart: MAE rose above the fp32 SGEMM's at 33 tokens.
  • Two MMA warpgroups per CTA, along the experts or along the tokens (up to 4): not faster than the selected configs in my sweeps.

Limitations.

  • With one token, cuBLAS's fp32 GEMV is more accurate than this kernel for 3 of the 10 shapes (for example MiniMax-M3: MAE 3.1e-7 vs 4.7e-7). From 2 tokens up, all 10 shapes beat it. In eager mode those batches stay on the fp32 GEMV or ll_fp32w. The test starts at 8 tokens.
  • As on SM100, generic shapes reach tier 4 through tier 3's Python check on x.shape[0]. Under vLLM's guard-free torch.compile, that branch can be fixed at the first traced size, the issue [Perf][MoE] Wrap GateLinear ll_bf16_gemm in custom op to prevent torch.compile branch freezing #60681 fixes for tier 1. Small batches of those shapes may then run this kernel, which is still faster than the F.linear path main would freeze.
  • The cost model was fitted on H200 (132 SMs). Other SM90 parts get correct results and an SM-count-aware choice, but the choice may not be the fastest.
  • Add Step-5 Preview support #61727 lowers the fp32 GEMV cutoff for Step-5 to 11 tokens when allow_bf16x3_router_gemm is set, based on B300. On H200 the fp32 GEMV is still faster at 16 tokens for that shape, so that rule belongs in the non-SM90 branch next to the GB200 one.
  • The Beam-1.0 numbers come from a one-rank proxy with dummy weights. A full TP8 run needs [Model] Add Reflection Beam #62074 merged and 8xH200.

Not a duplicate. I listed every open PR that touches gate_linear.py, fused_moe/router/, fp32_router_gemm* or ll_fp32w*, or that has router/gate/bf16x3 in its title. Most are for other hardware or other tiers: #60376 (SM100 large batch), #60681 (tier 1 custom op), #61727 (Step-5), #50177 and #49627 (warmup), #50535, #61687, #61895, #59023 and #57626 (ROCm), #59486 (quantization), #59925 (deterministic MoE), #37306 (Llama4), #57848 (SM103) and #61463 (ll_bf16 split-K fix).

This PR is on by default, adds no dependency, keeps no extra weight copy, and its error stays below the fp32 SGEMM's.
