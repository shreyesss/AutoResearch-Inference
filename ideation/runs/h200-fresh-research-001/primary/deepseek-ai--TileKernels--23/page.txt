v6
The inference path now applies the RMSNorm weight fusion consistently with the grad-enabled path, and the added tests cover both weighted and unweighted cases.
v4
The MR fixes bug
#22
: the no-grad (inference)
mhc_pre
path sent the RAW
fn
weight into the fused
mhc_pre_big_fuse
kernel (which has no
norm_weight
argument) and therefore SILENTLY DROPPED the optional RMSNorm
norm_weight
applied by the grad-enabled path. The fix folds
norm_weight
into
fn
BEFORE the fused GEMM: since the weight is constant during inference,
(residual * norm_weight) @ fn == residual @ (fn * norm_weight)
, and the fused kernel divides by the SAME (unweighted) rms-denominator as the grad path and the torch reference; dtype/round-to-tf32 handling also match, so the math is CORRECT. A regression test is added that compares grad vs no-grad outputs (with/without
norm_weight
) over
torch.is_grad_enabled()
. Main concerns: (1) the test uses an extremely tight
atol/rtol = 1e-6
between two op-fusion/rounding/reduction-order-DIFFERENT kernels plus very large shapes, risking flaky/over-strict failures and slow CI; (2) the fusion logic is DUPLICATED/inlined at a low level across the two paths, which is itself the kind of divergence that caused
#22
(the grad path wraps the same
fn * norm_weight
merge in an autograd Function). Cleaning this into one helper selecting the autograd/raw-forward merge on
torch.is_grad_enabled()
would both remove the duplication and prevent future divergence. Overall: correct in substance, but I would request minor changes to test tolerance/duplication.
v3
This PR fixes a correctness bug in the no-grad (inference) path of
mhc_pre
in
tile_kernels/modeling/mhc/functional.py
. Previously, when
torch.is_grad_enabled()
was False, the code called
mhc_pre_big_fuse(...)
without ever applying
norm_weight
, since the fused kernel does not accept a
norm_weight
argument. As a result the RMSNorm weight was silently dropped in inference mode, diverging from the grad path (which fuses it via
_MHCFnNormwMerge
inside
mhc_pre_norm_fn
). The fix merges
norm_weight
into
fn
before calling the fused kernel using the same
_mhc_fn_normw_merge_fwd
kernel used by the grad path, so both paths are now numerically consistent.
The fix is correct and minimal: it mirrors the existing grad-path implementation exactly (
torch.empty_like(fn)
+
_mhc_fn_normw_merge_fwd(*fn.shape)(fn, norm_weight, merged_fn)
), so inference and training now produce identical results. The new regression test
tests/mhc/test_functional_mhc_pre.py
parametrizes over
generate_norm_weight
in {False, True} and asserts the grad-enabled and no-grad results match for
layer_input
,
post_mix
, and
comb_mix
. This directly exercises the bug and is an appropriate regression guard (a self-consistency check between the two code paths, where the grad path was the known-correct reference). Overall the change is sound and I recommend merging; only minor, non-blocking test/readability improvements are suggested below.
