## Minimal observation and flush

Use a separately named, identical A/B observer initialized once after final serving graph capture. Exclude `profile_only=True` memory-estimation capture, as native002 already does. Preserve the qualified candidate and original graph dispatch. Preallocate a fixed pool of event pairs and initialize their device resources before traffic; retain initialization wall time and memory costs. Suggested engineering capacity is65,536 real-call pairs per rank, with a separate integer count of dummy calls. It covers109 real calls per second over a600-second traffic cap. This is conservative provisioning, not a proven hardware lower bound or a mathematical workload maximum: duration-only warmup can repeat inputs, and recomputation/preemption can add calls. Capacity overflow must increment explicit counters, stop admission to the observer, preserve the entire preceding evidence and classify the timing cohort incomplete. Never overwrite a circular buffer, silently sample calls, or report a successful favorable prefix. The final designer may choose a smaller explicitly bounded capacity; that choice must precede results.

Only two event records per real proposal belong in the initial implementation. Optionally adding a target-forward control requires another pair with precisely reviewed forward boundaries and doubles that event overhead; it is not necessary to reuse the incomplete old collector. No `.item()`, tensor copy, synchronization, disk write or formatting belongs between the proposal events. Capture CPU metadata before the start event and append the small pending record after the end event. Retain actual stream/device identity. Any proposal spanning an unjoined side stream requires source proof of its join before interpreting the outer events; an event on the main stream is not automatically a universal device-work fence.

The simplest control path is always-on bounded observation during the fixed warmup and profiling workload, followed by one root-controlled flush after strict all-eight-engine and router drain. Resolve the final end event once per rank, then read earlier event durations, write atomic raw receipts and disable the observer. No per-step event query or synchronization is needed. A worker utility method can delegate to this flush via the existing collective RPC path. In the pinned `core_client.py`, `collective_rpc_async` uses `call_utility_async`; the DPLB override broadcasts with `call_utility_all_async` and returns only the first engine result. Therefore root must require eight final rank artifacts, not infer eight-rank success from a single HTTP response. Root invokes both outer backends directly and binds the nonce, PID/start ticks and expected GPU UUIDs.

A narrowly guarded HTTP flush route plus the worker utility is preferable to a background polling thread or a replacement request client. Root subsequently extracted the pinned source read-only. `engine/protocol.py261` and `v1/engine/async_llm.py1149` confirm `async collective_rpc(method, timeout=None, args=(), kwargs=None)`, forwarded to the engine-core async RPC. The proposed exact root interface is POST to each backend `/c25_live/flush` with `{run_id, arm, nonce}`, whose narrow route calls `collective_rpc("c25_live_timing_flush", timeout=30, kwargs=payload)`. The final API-router attachment point still requires the small launcher-source check before implementation. Existing `/start_profile` is not suitable unchanged: it requires profiler configuration and activates the existing profiler. No CUPTI configuration or timing reader from C24 is inherited. ## Existing CPU metadata and output accounting

At normal request preparation, `gather_batch_req_state`/`prepare_inputs` already expose `req_ids`, `idx_mapping_np`, `num_scheduled_tokens`, `num_draft_tokens_np`, `is_prefilling_np`, `has_prefill`, prefill lengths and the CPU upper bound on computed-token context. Copy those CPU arrays when they are produced; never read GPU positions or mappings just to classify timing. Record target requested/selected descriptors at dispatch and actual draft descriptor after its dispatch. Mark the exact real `sample_tokens` call as real; `execute_dummy_batch -> _dummy_run` must remain a separate count, even when its graph shape matches. A request-ID prefix alone is insufficient to prove real work.

Each raw row should retain run/arm/replica/rank/device/stream, monotonic local call ID, request IDs and slot-generation metadata, real/dummy classification, both graph descriptors, actual real and padded request/token counts, per-row prefill flags, scheduled draft counts and context upper bounds. Preserve all real prefill and mixed calls as separately labeled exposure. The primary decode cohort can require no prefill rows and actual FULL target/draft replay. Predeclare context bins using the recorded CPU upper bound, for example `<8192`, `8192–32767`, and `>=32768`; label these upper-bound strata rather than exact attention lengths. Keep dominant draft capacities1/2/4/7 visible and retain all other capacities. Do not choose cells based on favorable timings.

`AsyncOutput.__init__` already copies sampled IDs and `num_sampled` asynchronously to CPU at async_utils.py140–149. `get_output` already waits on its original copy event at176 and trims each returned token list at180–185. A callback/tag after the original method returns can copy those CPU counts/IDs and bind them to the pending real-call metadata without any extra GPU readback or synchronization. The pinned `multiproc_executor.py991–1030` confirms `get_output` executes inside `WorkerProc` before `worker_response_mq.enqueue`, optionally on the worker’s async-output thread with its CUDA device already set. `UniProcExecutor` also resolves it in its owning executor. Thus an in-process observer tag is feasible. Protect shared pending/output metadata with a short CPU lock, hold no lock across synchronization, require all pending tags resolved at flush, and copy CPU lists before downstream mutation. An optional actual `num_rejected` D2H copy is not free; avoid it initially. For ordinary pure decode with the unchanged single-bonus rule, the installed `input_batch.py507–552` computes `num_rejected = num_logits - num_sampled`, with chunked-prefill counts zeroed. Existing CPU scheduled-draft counts plus returned `num_sampled` can therefore supply an explicitly labeled reconstructed rejected count in that qualified cohort. Do not extend that formula across prefill placeholders, other sampler modes or an unverified bonus width.

The same-call accepted count is **not the yield of the newly timed proposal**. `sample_tokens` first verifies previous drafts, postprocesses those outputs, then proposes drafts for the next verification. Any yield attribution must join by actual request ID, a monotonic per-request proposal sequence and preemption/resumption generation. Never join by reused state row alone. Preserve proposals made on a terminal step that are never verified; they are real spent work. Keep these denominators distinct:

- Actual proposal calls and active proposed request rows, including terminal orphan proposals.
- Worker-returned sampled tokens, accepted drafts and bonus/correction tokens, with qualification and reconstruction flags.
- Client-committed output/usage tokens after scheduler/API EOS or length truncation, plus every cancellation/error.

Aggregate summed per-GPU **real-caller** proposal milliseconds divided by client-committed tokens is an observed stage-exposure ratio. It is not latency, a cycle wall time, total allocated-GPU compute cost or a hard end-to-end speedup bound. Idle DP dummy calls can still participate in expert-parallel work supporting another rank’s real requests, so excluding them from the real-call endpoint does not prove their GPU cost is absent. Report their count and the limitation explicitly. Report each rank and both replicas; do not sum overlapping spans and call the sum service wall time.
