Describe the bug

Serving deepseek-ai/DeepSeek-V4.1-Flash with --speculative-algorithm DSPARK on 2 nodes × 4 H200 (TP8 + EP8, LeaderWorkerSet, one 4-GPU pod per node over RoCE) deterministically deadlocks during startup, right after the DSpark draft weights finish loading. Three consecutive attempts across two different images all hang at the same point with the same split stack; removing the DSPARK flags (identical everything else) starts cleanly in ~10 minutes.

The split we capture on every occurrence (py-spy dump, all 8 scheduler processes):

Node 0 schedulers (leader, TP0-3) — parked after Load weight end ... type=DeepseekV4ForCausalLMDSpark:

monitored_barrier (torch/distributed/distributed_c10d.py:5435)
dist_barrier_after_load (model_runner_components/load_model_utils.py:380)   # also seen :344 on dev-cu13
load_model (model_runner.py:1307)
initialize (model_runner.py:653)

Node 1 schedulers (worker, TP4-7) — parked earlier, inside the KV-pool memory probe:

all_reduce (torch/distributed/distributed_c10d.py:3252)
wrapper (torch/distributed/c10d_logger.py:83)
get_available_gpu_memory (utils/common.py:550)
_profile_available_bytes (kv_cache_configurator.py:2214)

The worker-side ranks have posted the memory-probe all-reduce and wait for the leader-side ranks, while the leader-side ranks wait at a different synchronization point (post-load barrier). The two node halves sit at mismatched collective sites permanently — GPU utilization 0%, GPU memory and logs frozen from that point on. No watchdog fires (the stall happens before the scheduler loop starts).

This looks like the same unsynchronized-decision family as #39886 (DSpark CUDA-graph memory check not synchronized across ranks → ranks disagree on collective participation) and the runtime variant in #33289 (multi-node TP + DSpark → per-rank divergence → unmatched collectives). Our case adds a multi-node TP8/EP8 startup reproduction with full per-node py-spy stacks.

Reproduction rate: 3/3 with DSPARK on 2 nodes (2× dev-cu13, 1× dev-cu13-dsv41); 0 failures without DSPARK — the identical non-DSPARK cell starts cleanly in ~10 min and served a full benchmark suite.

Reproduction

Reproduction

Model: deepseek-ai/DeepSeek-V4.1-Flash

python -m sglang.launch_server \
  --model-path /.cache/deepseek-v41-flash \
  --served-model-name deepseek-ai/DeepSeek-V4.1-Flash \
  --tensor-parallel-size 8 \
  --mem-fraction-static 0.8 \
  --host 0.0.0.0 --port 30000 --enable-metrics \
  --nnodes 2 --node-rank 0 \
  --dist-init-addr <leader-host>:29500 \
  --chunked-prefill-size 16384 \
  --max-running-requests 256 \
  --ep-size 8 \
  --attention-backend dsv4 \
  --moe-runner-backend flashinfer_mxfp4 \
  --cuda-graph-max-bs-decode 64 \
  --max-prefill-tokens 32768 \
  --enable-decoder-swa-bounded-replay \
  --reasoning-parser auto --tool-call-parser auto \
  --trust-remote-code \
  --speculative-algorithm DSPARK \
  --speculative-dspark-block-size 5

(--node-rank 1 + same --dist-init-addr on the second node)

Failure timeline:

Attempt Image Result
1 lmsysorg/sglang:dev-cu13 (digest sha256:0e1b14e302619…, built 2026-09-22, commit 582389ce) Hangs; last log Load weight end … DeepseekV4ForCausalLMDSpark; stacks above; pod restart reproduces it
2 lmsysorg/sglang:v0.5.20-cu130 Not applicable — V4.1-Flash not supported in the release yet (unrecognized arguments: --enable-decoder-swa-bounded-replay)
3 lmsysorg/sglang:dev-cu13-dsv41 (build commit da64c5cbb8cf6bfd39be19da43573fdfd484c43a, action run 34631178591) Same hang, same split stacks

Control: same image + same flags without --speculative-algorithm DSPARK --speculative-dspark-block-size 5 starts cleanly (health 200, ~10 min).

Notes / additional data

  • py-spy dumps of all 8 scheduler processes from hung runs are available on request; they are uniform per node (node 0 = dist_barrier_after_load, node 1 = _profile_available_bytes all_reduce) across both dev-cu13 and dev-cu13-dsv41.
  • The stall line in load_model_utils.py differs slightly between images (380 on dev-cu13-dsv41, 344 on dev-cu13) — consistent with code movement between builds, same function.
