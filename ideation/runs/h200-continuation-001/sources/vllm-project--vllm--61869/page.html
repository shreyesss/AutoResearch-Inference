Overview

This is the DSpark half of the DeepSeek-V4.1-Flash specialized decode on GB300 (#61868). With decode_backend set to latency_specialized, it:

  • gives the DSpark draft model a decode executor of its own, on the target executor's kernels and streams;
  • fuses the Markov sampling loop, and shards it by vocabulary over the TP ranks at small batches;
  • captures the work between the target forward and the draft forward (sampling, the request-state update and the draft input preparation) in a CUDA graph.

With the switch off, the only shared change is that DFlash-family drafters prepare all their KV-cache groups in one launch, with the same outputs.

Depends on #61868 and is stacked on it. Until that lands, this branch also contains its commits; only the last commit, the DSpark changes, is under review here.

Claims

DeepSeek-V4.1-Flash on one GB300 tray with DSpark, the switch on in both arms, this PR against #61868:

  • Decode step: another 6.4% faster at batch 1 (4,354 → 4,075 µs), 4.3% at batch 8 and 1.9% at batch 32. Together with [Perf][DSv4.1] DeepSeek-V4.1-Flash specialized decode on GB300 #61868, the batch-1 step is about 24% faster than with the switch off.
  • InferenceX AgentX traces: P90 interactivity up another 5–10% at concurrency 1 to 32. At concurrency 64, turns finish sooner, so the closed loop admits more requests: throughput per GPU rises 15% and TTFT p50 falls from 5.55 to 1.46 s, while P90 interactivity drops 12% at the larger batch.
  • Accuracy and the DSpark acceptance length are unchanged.

Restructure. Following #61867, the draft layers moved from the stock layers into a draft executor, with no kernel change. The decode step before and after, in the same-tray ABBA as #61868's (switch on in both, each value the mean of two blocks):

Part of the batch-8 difference came from the post-forward graphs. Their key held input addresses, and the host-backed temperature, seed and prefill-length buffers rotate through a pool, so a batch shape could take up to four of the 32 graphs; which shapes were left to run eagerly depended on the order in which they first appeared. This revision copies those buffers in the region's existing copy launch, so each batch shape takes one graph (see Design notes). The rest of the batch-8 difference is in a GEMM this PR does not change. It stays on fresh servers serving only batch 8 (two servers per arm, 3,000-token decodes): 8,887 → 9,108 µs. Profiles late in those decodes differ in one kernel, the stock wo_b projection at 48 rows. It runs FlashInfer's cute-dsl MXFP8 GEMM with the tactic the autotuner picks when the server starts. Details

Where the time goes

DSpark proposes 5 tokens a step with three draft layers and a Markov head that samples the tokens one position at a time. In stock vLLM at batch 1, the draft side takes about 770 µs of the 5.4 ms step, and #61868 leaves it on the stock paths:

  • Draft layers (about 310 µs). They run the stock all-reduce, attention and MoE kernels, which [Perf][DSv4.1] DeepSeek-V4.1-Flash specialized decode on GB300 #61868 already replaced in the target.
  • Draft head and Markov loop (about 280 µs). The loop is sequential over the 5 positions, with several small kernels per position, and the logits are all-gathered before sampling.
  • Drafter preparation (about 180 µs). It does a separate launch per draft KV-cache group.
  • Host. Sampling, the request-state update and the draft input preparation run eagerly between the target and draft graphs. DSpark propose was about 1.5 ms of the host loop.

So this PR moves the draft layers onto the target's paths, fuses the Markov loop, and graphs the region between the target forward and the draft forward.

What changed

Each row is one optimization and the saving we measured when it was added, as a batch-1 decode-step ABBA on one tray. They were measured one at a time, so they do not add up exactly to the end-to-end figure.

Optimization Why Saving when added
A draft executor (specialized_decode/runtime/draft.py) runs the draft layers on the target's fused all-reduce + mHC kernel and mailbox. They ran the stock all-reduce and mHC at every sublayer boundary. −61 µs
The draft layers use the executor's attention, the routed-expert GEMMs and the MXFP8 GEMMs. The draft finalizes its own MoE with a new CuTe DSL kernel (moe/routed_expert_finalize_cute.py). The target's fused finalize is built for the target's top-k. −56 µs (routed-expert GEMMs)

Sharded Markov chain: the whole chain runs in one cooperative kernel per rank, with the Markov head sharded by vocabulary over the TP ranks. Ranks agree on each position's winner through a symmetric-memory mailbox (sharded_markov.py, with the kernel in CuTe DSL in sharded_markov_cute.py). With a plain vocabulary shard, it reads the draft LM head's local shard and skips the logits all-gather. That removes the remaining per-position launches and the all-gather. −8 to −20 µs for the chain, −19 µs for the local shard

The draft context work that reads only the target hidden states (the hidden-state combine and each draft layer's context-KV projection) runs on a side stream beside sampling. It does not depend on the sampled tokens. −28 µs

Every change except the last takes effect only with the switch on. The multi-group launch applies to every DFlash, DFlash2, LiLiCorr and DSpark user and writes the same outputs.

Design notes

Structure. The DSpark draft model registers itself when it is built with the switch on. The target's model state from #61868 then builds the draft's executor right after the target's, on the same fused kernel, mailbox and mHC side stream, and the draft model's forward asks it for a step the same way (plan(), then run()). The model state also offers Model Runner V2 the post-forward CUDA graphs, through a post_forward_cudagraphs attribute that vllm/v1/worker/gpu/post_forward_cudagraph.py reads. The speculator takes the fused and sharded samplers only when the draft model hands it the Markov weights, which it does only with the switch on.

With the switch off. The only shared change is the multi-group prepare:

  • Group 0 writes the shared outputs, and each group writes its own query and context slot mappings.
  • prepare_context_anchor now runs after the input preparation. LiLiCorr's anchor reads only target hidden states and query_start_loc, which that kernel does not write.
  • The padding loops use a fixed 1,024-wide block.

With the switch off, no model state offers post-forward graphs, so PostForwardCudaGraphs.create returns None, and the DSpark model shares no Markov weights, so the eager loop is unchanged.

Post-forward graphs: correctness and limits.

  • Eligibility. Uniform decode steps without logprobs, prompt logprobs, grammar or logits processing. It is decided per step on the host, from state every TP rank holds identically.
  • Sampling draws. They come from per-request seeds and positions, so a replay draws what the eager kernels draw.
  • Step tensors. The per-step tensors that prepare_inputs allocates are copied into buffers the graphs own, in one launch. So are the host-backed temperature, seed and prefill-length buffers, which rotate through a small pool of pinned host buffers; the region reads the copies.
  • Graph key. It holds the addresses of the other inputs, so a moved buffer captures a new graph instead of replaying a stale one. A batch shape therefore has one key.
  • Replay. A replay waits for the previous step's output copy stream.
  • Capture and memory. The first step of a shape runs eagerly, and the second captures. Graphs are captured while serving, into one memory pool of their own that the start-up memory profile does not see. That pool holds about one region's temporaries at the largest batch, mostly its logits.
  • Limit. Past 32 graphs, further shapes run eagerly, which costs performance only.
  • Trade-off. On graph steps, the async copy of the sampled tokens starts after the draft input preparation instead of before postprocess_sampled.

Sharded chain: rank lockstep.

  • The exchange is a cross-rank spin inside the draft step and its FULL graph, so every rank must launch it the same number of times.
  • Installation depends only on configuration, and CPU MIN all-reduces at load make the ranks agree on it.
  • The per-call choice depends only on the padded batch shape. It applies up to 8 request rows (4 at 8 ranks).
  • Steady state reads nothing back from the GPU.
  • The draws reproduce the fused path, except for the bias reduction order before its BF16 rounding, so a bias element can differ from cuBLAS's in its last bit.

Relation to #59511 (in this PR's base). #59511 captures the DFlash context combine and anchor in the draft FULL graph, staging the aux hidden states. With the switch on, this PR runs the combine, plus the DSpark context-KV projection, earlier: on a side stream inside the post-forward graph. prepare_draft_inputs then stores the hidden states and publishes the anchor before the side stream forks. Without the side stream, #59511's path applies unchanged.

[Perf][DSv4.1] DeepSeek-V4.1-Flash specialized decode on GB300
3c957a6 
Add an opt-in decode executor for small decode batches of
DeepSeek-V4.1-Flash on GB300 (TP4, DSpark), enabled with
--additional-config '{"decode_backend": "latency_specialized"}' (the
default, auto, keeps the stock decode), under
vllm/models/deepseek_v41/nvidia/specialized_decode/. As in vllm-project#61867, the
model owns the executor: the model state builds it once the weights are
loaded, and FULL-graph captures of pure decode steps run their decoder
layers on it. Its paths:

- a fused Lamport all-reduce + mHC at every sublayer boundary up to 384
  rows, writing the attention input as MXFP8, collecting wo_b's
  published output and taking the deferred MoE finalizes;
- GEMMs for 1-8 rows: a CuTe DSL routed-expert front, route kernel and
  tcgen05 GEMMs; FlashInfer's low-latency MXFP8 GEMM with pinned
  tactics for the attention projections; a low-batch BF16 GEMM for the
  indexer projections; a CuTe DSL LM head and the custom all-gather for
  logits;
- indexer and attention: shared sparse-index tables, a persistent KV
  counter for the sparse-MLA decode, cooperative top-k, side-stream
  indexer work and a row-sharded dense indexer;
- attention-metadata builds replayed from CUDA graphs, and the Engram KV
  projection chain on the prefetch stream.

The executor is validated on GB300, MRV2, TP4 and DSpark; any other
deployment raises at start-up on every TP rank with the requirements it
misses. With the default, the model runs as before.

[Perf][Spec Decode][DSv4.1] DSpark draft on the specialized decode
003c91e 
With decode_backend latency_specialized, the DSpark draft of
DeepSeek-V4.1-Flash gets a decode executor of its own, which the
target's model state builds on the target executor's kernels and
streams. The speculator's per-step work is fused, captured in a CUDA
graph or moved off the critical path:

- the draft layers on the fused all-reduce + mHC, the executor's
  attention and the routed-expert and MXFP8 GEMMs, with a CuTe DSL draft
  MoE finalize;
- the Markov loop as one sampling kernel per draft position, and the
  whole chain in one cooperative CuTe DSL kernel per rank with the Markov
  head sharded by vocabulary;
- sampling, postprocess_sampled and the draft input preparation in a
  post-forward CUDA graph, which a model state offers through
  post_forward_cudagraphs, with the draft context work on a side stream;
- all draft KV-cache groups prepared in one launch. This applies to
  every DFlash, DFlash2, LiLiCorr and DSpark user and writes the same
  outputs.
