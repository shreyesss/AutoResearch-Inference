📌 Description
Follow-up to
#6343
(SM90 FP4 MegaMoE):
Cleanup fix:
with
single_active_dispatch_warp
, the inactive dispatch warp cleaned the workspace with empty expert counts and left pool blocks ≥ 32 of hot experts stale, so the next launch failed (H20, 97–128 tokens per rank, e.g. CUDA-graph capture); it now fetches the counts first (outputs bitwise unchanged, timing within noise).
H200 push dispatch:
add measured H200 EP8 buckets that enable push for M ≤ 32 on DeepSeek-V4-Flash and MiMo-V2.5-Pro, and M ≤ 64 on DeepSeek-V4-Pro (rotated pool at M 33–64), saving about 10 µs per call (1.03–1.16x kernel time, bitwise-identical outputs; H20 and EP4 plans unchanged).
Other models:
accept any expert count that divides across ranks, keep the selected plans compilable for untuned geometries (H20 buckets match the full geometry, the
BLOCK_M=8
stage count follows the shared-memory budget, unsupported shapes raise
ValueError
), and allow push only on validated plans, so Kimi-K2, DeepSeek-V3, GLM-4.x and Qwen3 shapes now run correctly while plans of the three tuned geometries are unchanged.
Usage docs:
the weight-preparation docs now state what callers must convert before
transform_{nvfp4,mxfp4}_weights_for_mega_moe
: Marlin byte order (checkpoints are usually low-nibble-first), scales inside the decoder range (NVFP4
6 * scale <= 448
; MXFP4
2^-5
–
2^6
for groups with nonzero codes, otherwise outputs silently saturate or flush), and the excess moved into per-expert global scales passed at run time; the module example shows the full flow.
How to use:
FlashInfer only provides the kernels and the layout transforms; frameworks convert checkpoint tensors to the format above at load time (the SGLang integration does this for
nvidia/DeepSeek-V4-Flash-NVFP4
, where about 51% of blocks would saturate without rebalancing).

- Allow push / rotated pool only on the validated small-M plans (M <= 64,

- The H20 tile buckets assume the RS arm of the three tuned geometries; match

  H7168/E384 (Kimi-K2) and H >= 7680 no longer overflow at M <= 16.

⚡ Quick win
Give gate/up global-scale folding its own exactness check and error message.
When
l1_global_scales
has shape
[E, 2]
, the code multiplies the smaller half's E4M3 local scales by
ratio = g / max(g)
. If the gate/up ratio is not a power of two,
local * ratio
is usually not representable in E4M3.
_exact_e4m3_bytes
then raises an error that says "the per-expert scale range is too wide to fit 6 * scale <= 448 losslessly". That error names the wrong cause. The real cause is the gate/up global ratio, and the scale range can be narrow.
A realistic trigger exists. Some ModelOpt exports store separate w1/w3
weight_scale_2
values that are not a power of two apart. The MXFP4 path already rejects this case with a direct message (
"MXFP4 gate and up global scales must differ by 2^k"
). The NVFP4 docstring also does not say that
[E, 2]
globals must fold exactly.
Check the folded scales before the power-of-two shift, and raise a gate/up-specific error.
🛠️ Proposed fix
local = torch.cat(

                 local[:, :n] * ratio[:, 0, None, None],
                 local[:, n:] * ratio[:, 1, None, None],
             ),
             dim=1,
         )
+
if not torch.equal(local.to(torch.float8_e4m3fn).float(), local):
+
raise ValueError(
+
"NVFP4 gate and up global scales cannot be merged exactly: "
+
"folding their ratio into the E4M3 local scales is lossy"
+
)
global_scales = merged
