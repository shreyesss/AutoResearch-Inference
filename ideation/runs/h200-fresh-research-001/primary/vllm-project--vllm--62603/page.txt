Overview
vLLM has no MegaMoE that runs on Hopper today:
the DeepGEMM MegaMoE (
deep_gemm_mega_moe
) requires SM100;
the FlashInfer MoE-EP megakernels (
flashinfer_moe_ep_cutedsl
,
flashinfer_moe_ep_mega_deep_gemm
) require SM100
This PR runs block-FP8 MoE checkpoints on Hopper with FlashInfer's SM90 FP8 MegaMoE, which ships in FlashInfer 0.7.2. The kernel fuses dispatch, both expert GEMMs and combine. It goes through the existing
--moe-backend flashinfer_moe_ep_cutedsl
path with no model code, so any block-FP8 MoE can use it.

Claims
GLM-5.3-Flash on 8x H200 (DP8/EP8, 128K/512 decode, MTP3): +11% to +18% output throughput and -6% to -14% TPOT p50, at concurrency 8 to 192.
One MoE layer at EP8: -7% at 8 tokens/rank, up to -48% at 8192 tokens/rank.
GSM8K: 0.919 vs 0.917.
The backend is opt-in. Default backends do not change.

Details
Kernel.
FlashInfer
Sm90PullFp8MegaMoeConfig
, with FP32 128x128 weight scales and a SwiGLU clamp.
FlashInfer's push-style SM90 backend has no SwiGLU clamp, so it cannot serve
swiglu_limit
models.
Weights.
The kernel wants FC1 rows interleaved as
[pair, {gate, up}, 8]
under one 128x128 scale. Each scale block therefore covers rows from two checkpoint blocks, and both use
max(s_gate, s_up)
.
This is exact for power-of-two scales, which GLM-5.3-Flash has. Other checkpoints get one extra E4M3 rounding on half of the FC1 rows.
Workspaces.
The kernel always processes its whole token buffer, with a launch geometry picked for that size. With a single buffer sized at
max_num_batched_tokens
, decode is slower than the baseline.
The adapter therefore adds 64-, 256- and 1024-token workspaces. Each call uses the smallest one that fits the largest batch across DP ranks. Without DP-wide token counts it uses the default workspace, because every rank must pick the same buffer.
Loaders.
The fp8, compressed-tensors, online FP8 and Quark FP8 MoE methods now call the experts'
process_weights_after_loading
. It is a no-op for other experts.
The SM90 path is chosen from the quant config, not the weight dtype. FP8 weights keep their dtype, so a rebuild from preprocessed weights picks the same path.
Idle ranks.
With pass-through stages, the experts own the EP collective. A rank without tokens therefore still enters them. The change is identical to the one in
[Beam] Enable CuTeDSL NVFP4 MegaMoE
#62073
.
Limitations.
The backend needs expert parallelism and
nvshmem4py
.
It rejects DBO, runtime weight transfer and
apply_router_weight_on_input
.
Shared experts are not fused.
FlashInfer's SM90 input staging is torch-composed, about 1.2 ms per step at C128.

[Perf][MoE] Run block-FP8 MoE on FlashInfer's SM90 MegaMoE
…
a5225b2
--moe-backend flashinfer_moe_ep_cutedsl now also takes block-FP8 (128x128)
checkpoints on Hopper. They run on FlashInfer's SM90 FP8 pull-style CuTeDSL
megakernel, which fuses token dispatch, both expert GEMMs and the combine,
through the existing FlashInfer MoE-EP adapter.

- The FP8 oracle reorders w13 into the kernel's FC1 layout: gate and up rows
  interleaved by 8 under shared 128x128 scales. Power-of-two checkpoint scales
  survive this as exponent shifts.
- The kernel always runs its whole token buffer, with a launch geometry picked
  for that size. The adapter therefore adds 64/256/1024-token workspaces and
  picks the smallest one that fits every EP rank's batch.
- Fp8MoEMethod calls the experts' process_weights_after_loading hook, as the
  NVFP4 and MXFP4 methods do. It is a no-op for the other FP8 experts.

GLM-5.3-Flash on 8x H200, DP8/EP8, 128K/512 decode with MTP3, A/B/A: output
throughput +11% to +18% at concurrency 8-192, TPOT p50 -6% to -14%.
EP8 MoE layer microbenchmark: -7% at 8 tokens/rank to -48% at 8192.
GSM8K (1319, 5-shot): 0.919 vs 0.917.

[MoE] SM90 MegaMoE: idle ranks, input-side router weights, other loaders
…
c135b27
- Passthrough experts own the EP collective, so FusedMoEKernel no longer
  skips them on a rank without tokens (the same change is in
vllm-project#62073
).
- The SM90 FP8 kernel weights the activation before fc2, so layers that
  weight the expert input (apply_router_weight_on_input) are rejected.
- The compressed-tensors, online FP8 and Quark FP8 MoE methods call the
  experts' weight hook as well, so they also build the megakernel.
- The SM90 path is chosen from the quant config rather than the weight dtype,
  and block-FP8 kernel weights stay FP8 on the layer. Rebuilding the kernel
  from preprocessed weights selects the same path.

Tests: input-side router weights are rejected; a rebuild keeps the SM90
config; an empty rank and a CUDA graph replay through FusedMoEKernel stay
bit-exact (without the idle-rank change the empty-rank case hangs).
