📌 Description

Co-authors: @AichenF, @jychen21, @YijiaZhao.

Submitted by: xuechengw.

flashinfer.megamoe runs expert-parallel MoE on NVLink-connected Hopper GPUs,
using NVFP4/MXFP4 weights, FP8 E4M3 activations and BF16 outputs. The kernels
perform token dispatch, two expert GEMMs, clamped SwiGLU and top-k reduction.

Weights Family Launches
NVFP4 fused 1
NVFP4 split 2: L1, then L2
MXFP4 fused 1

Usage

Allocate MegaMoESymmBuffer collectively before graph capture. Prepare weights
with transform_nvfp4_weights_for_mega_moe or
transform_mxfp4_weights_for_mega_moe; all ranks stage inputs and call matching
kernels in matching order.

from flashinfer import megamoe

buf.stage(x_fp8, x_sf, topk_idx, topk_weights)
megamoe.nvfp4_mega_moe(y, nv_w1, nv_w2, buf, kernel_family="auto")
# Or, with MXFP4 weights:
megamoe.mxfp4_mega_moe(y, mx_w1, mx_w2, buf)

NVFP4 supports 256 or 384 total experts. The process group selects EP4 or EP8;
no separate execution API is needed. EP4 uses the generic fused schedule;
EP8 retains its measured tuning policies. Auto selection uses fused through
256 tokens per rank, then split.
Input scales are FP32 per 128 channels; routing uses INT64 expert indices
(-1 masks a route) and FP32 weights. Hidden width is a multiple of 256 and
intermediate width a multiple of 128. Raw weight scales use UINT8 E4M3 per
16 values for NVFP4 or E8M0 per 32 values for MXFP4.

Performance

Cold L2 before each call; one MoE call per graph; CUDA events; maximum time
across ranks per call, then the median of 50 samples. Split timing includes
both launches. Packing, compilation and cache clearing are outside timing.
M is tokens per rank; capacity is the allocated maximum tokens per rank.

megamoe: host layer and Python API for the fused NVFP4 MoE kernel
c372f6f 
Wires the SM90 NVFP4 MegaMoE fused kernel into FlashInfer's JIT pipeline.

The kernel resolves its shared-memory layout, task schedule and dispatch
protocol at compile time, so the plan is selected in Python and rendered into
the config header; one module is built per (shape, plan) pair.

  flashinfer/megamoe/heuristics.py   plan selection (tuning tables, all-M arm,
                                     counter-dispatch policy, pool sizing)
  flashinfer/megamoe/__init__.py     MegaMoESymmBuffer + nvfp4_mega_moe
  flashinfer/jit/megamoe.py          Jinja render + JitSpec
  csrc/megamoe/*.cu, *.jinja         launcher, TMA descriptors, TVM-FFI binding
  tests/moe/test_megamoe_nvfp4_sm90.py

The symmetric-buffer layout is computed in C++ and returned as byte offsets so
Python slices exactly what the kernel addresses. The scale-factor region is
sized for the largest BLOCK_M candidate, since it is allocated once while the
plan varies per call -- sizing it from the current plan silently corrupts every
BLOCK_M != 8 schedule.

Needs -std=c++20 (float non-type template parameter for the activation clamp)
and builds against the pinned CUTLASS 4.4.

Verified on 8x H20-3e (EP8) against the DeepGEMM reference in the same process:
  - correctness: 27/27 bit-identical over Flash / Pro / MiMo at
    M = 1, 2, 4, 8, 16, 32, 64, 128, 256
  - performance: same kineto kernel timer, max over 8 ranks -- 18 of 27 points
    within +-2%, all within +-8%; the spread is measurement noise on a shared
    host (at large M, where the signal dominates, every point is within 2%)

megamoe: host layer for the split NVFP4 MoE family
6daf7a5 
Adds the BN128 split path to the Python API. `nvfp4_mega_moe` now dispatches on
tokens-per-rank: the fused kernel at or below `family_threshold` (256), the
split pair above it, where a single persistent kernel no longer fits the
working set.

The split family runs two kernels per call -- L1 (dispatch-dequant + first GEMM,
2-CTA cluster) then L2 (second GEMM + scatter) -- each with its own pipeline
depth and shared-memory budget. Those are template parameters, so they have to
be known before the module is built. Rather than paraphrasing ~100 lines of
shared-memory arithmetic in Python, the reference sizing code is carried over as
`megamoe_sm90_nvfp4_split_plan.cuh` and compiled into a small template-free plan
module that Python queries first; the kernel module is then rendered from its
answer. Mis-sizing that pipeline would be silent, so it is worth not
re-deriving.

  csrc/megamoe/megamoe_sm90_nvfp4_split_plan.{cuh,cu}   plan query
  csrc/megamoe/megamoe_sm90_nvfp4_split.cu              two-phase launcher
  csrc/megamoe/megamoe_sm90_nvfp4_split_binding.cu      TVM-FFI binding
  csrc/megamoe/megamoe_sm90_nvfp4_split_config.jinja
  flashinfer/jit/megamoe.py, flashinfer/megamoe/__init__.py

the L1 output box is 64x64 (each of the two M warpgroups stores its own

scales are per-128 like L1's, not per-BLOCK_N/2.
