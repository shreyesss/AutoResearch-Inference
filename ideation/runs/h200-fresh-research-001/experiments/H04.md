# H04 — Use real request counts for draft sizing

## Source observation

Installed uniform-batch helper takes target DP-sync request counts. #58984 separates real requests from target graph capacity; its multi-commit patch conflicts with this image.

## Upstream fix

Carry DP-wide logical request count separately and use it for draft batches while retaining target padding and distributed liveness.

## Root transfer prediction (untested)

Ragged/idle-rank workloads may spend less time drafting dummy rows. Fixed adaptiveOFF makes the observed padding gap a necessary activation question.

## Baseline eligibility and cheapest first step

Follow DSpark inheritance into the installed helper and compare logical, target-padded and draft-padded counts. Adapt exact final patch behavior; do not blindly cherry-pick.

## Strongest comparator

Identical k5, seq64, graph buckets and sampler with current request accounting; compare balanced as a negative control.

## Activation denominator

Steps with logical count below target graph capacity / all draft steps; dummy rows avoided by every rank.

## Mechanism and competing explanation

Draft rows and time, acceptance and verify frequency, CPU synchronization and graph fallback. A better batch mix is a competing explanation.

## Reject, stop or defer

No active padding gap, draft resizing changes graph policy/acceptance, distributed mismatch, or only synthetic speedup.

## Correctness scope

G01/G02/G05: sampling distributions, KV offsets, idle ranks, pause/resume, dummy inputs and graph replay.

## Workload and held-out conditions

Ragged D1, mixed E1 and fixed burst E2; balanced and held-out arrival schedules.

## Model statement and experiment

Separate the DP-wide maximum real request count from target CUDA-graph capacity when constructing DSpark draft batches. First inspect the installed uniform-batch helper and complete patch revision: the supplied excerpts establish DFlash inheritance and the proposed unpadded-count mechanism, but not the complete deployed dispatch path. If target padding makes the drafter select larger graphs, port the execution-shape fix while retaining startup capture capacity and coherent dummy-rank metadata. The predicted benefit is less draft work during ragged or partially occupied traffic, with little benefit when both counts select the same graph. H20 results motivate testing but do not predict H200 gains: acceptance changed, adaptive verification was enabled, and TTFT regressed at one reported load.

**Control:** Attested baseline with all settings preserved. Include the strongest supported static graph-size refinement within cap512 as a separate comparator, without increasing seq64 or changing speculation.

**Correctness:** Test unequal and idle ranks, startup capture versus online dummy batches, graph boundaries, metadata agreement, buffer bounds, KV rollback, EOS and cancellation. Validate actual conditional DSpark proposals against declared probabilities and committed-token distributions with an independent reference and a negative control. Acceptance and GSM8K nonsignificance are insufficient. Map these tests to the supplied G01-G05 contract once its definitions are available.

**Cost:** Low-to-moderate port effort; distributed and sampler validation dominate. No execution performed. Parameterized node cost per qualified output token is C8*T/(3600*Nqualified), with C8 unknown.

**Held out condition:** Primary native agent-f75 8K/1K and fixed-schedule Mooncake anchors at seq64. Hold out different ragged arrival patterns, mixed long prompts and cold/warm phases. Keep cache-isolated 1K/1K results separate.

**Inconclusive if:** The complete patch is unavailable, graph telemetry is missing, eligible events are rare, acceptance differences remain unexplained, or full-run intervals cannot distinguish benefit from drift.

**Metrics:** Across both replicas and every rank: real requests, DP-wide maximum, target capacity, draft query width, selected graph and executed rows. Denominator: uniform draft dispatches following target FULL graphs with capacity above the DP-wide real maximum; numerator: those selecting fewer executed rows. Also collect exact output tokens, draft/verify/accepted deltas, TTFT tails, request TPOT=(last-first token time)/(server output tokens-1), throughput, qualified goodput, KV blocks, preemptions and replay lag.

**Rejects if:** Complete inspection finds equivalent behavior already active; adequate eligible coverage shows no graph/work reduction; or correctness fails or serving performance regresses against the strongest comparator.

**Supports if:** The port reduces actual draft execution on eligible events and improves unprofiled serving metrics beyond drift without quality or predeclared TTFT-tail regressions. Confirm small gains with at least five alternating paired full-run blocks, intervals and held-out replication.

**Treatment:** First inspect source/configuration and existing logs. After eligibility and correctness qualification, change logical-row propagation alone. Follow attestation, activation, correctness, unprofiled screening, separate mechanism diagnosis, paired confirmation and held-out evaluation.
