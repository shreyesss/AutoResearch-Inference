    Single-node H20-3e report: vision CP + DSpark, long-prefill improvements, and three upstream PRs

    Thanks for maintaining this roadmap and for the kernel/CP work behind it. We have been integrating and testing DeepSeek-V4.1-Flash on one 8× NVIDIA H20-3e server, with text, image+text, tool calling, streaming, and cache reporting as requirements.

    Our October 5–7 experiments started from unmodified SGLang v0.5.21 and ended with a production deployment of a pinned integration build. The strongest paired comparisons were:

    • 524,032-token cold TTFT: 323.261 → 25.531 s, a 92.1% reduction / 12.66× speedup.
    • C64 aggregate output: 877.01 → 2,534.61 token/s (+189.0%); per-request streaming decode: 15.69 → 49.10 token/s (+213.0%).

    These are whole-deployment improvements, not the isolated effect of any one PR. We have contributed #39306, #42922, and #42924; their narrower validation and attribution are described below.

    1. Setup and measurement scope

    • Hardware: 8× H20-3e, SM90, approximately 140 GiB visible memory per GPU, NVLink/NVSwitch (NV18 topology), 2 TiB host RAM, two NUMA nodes.
    • Baseline: v0.5.21 at e00930c5489053f26d86b179cee0d087f846acbb, TP8/EP8, DSpark block size 5 already enabled, no CP, no decoder bounded replay, GPU-resident Engram, no HiCache.
    • Final: TP8/EP4, CP8 interleave, CP decode-attention TP, DSpark5, decoder SWA bounded replay, FlashInfer MXFP4 MoE with FP8 precision; Engram host table in per_rank layout, NUMA binding, HiCache ratio 1.5 / write_through.
    • Both use a 524,288-token context limit, static memory fraction 0.8, chunk size 8192 and max-running-requests 64. Prefill CUDA graphs remain disabled; decode CUDA graphs are enabled.
    • Final local integration revision: 79b468a7435e1bd29ad0d377587ff10b3c214ba3 (not an upstream release/commit). Runtime: PyTorch 2.13.0+cu130, Triton 3.7.1, FlashInfer 0.6.18; the final DeepGEMM integration uses sgl-deep-gemm 0.2.2. This is a backported integration, not a claim that stock v0.5.21 supports this configuration.

    The baseline and final integration use the same V4.1 model weights on the same hardware. No P/D disaggregation is used. All performance below is from a single eight-GPU server. These results describe the pinned October 5–7 snapshots, not the latest heads of every roadmap PR.

    Comparison boundary: the near-512K and C64 baseline measurements were supplemented using exactly the final workload construction, warmup and three measured rounds. Input hashes, token counts, output lengths and zero-cache-hit conditions match. Other baseline cells are historical references: cold-prefill nonces differ, and the early natural-generation prompts/warmup procedure differ from the final protocol. The tables explicitly mark the paired supplements with †. Runs were sequential, on different dates, not randomized interleaved A/B trials.

    2. Optimization path and what we retained

    1. Use vision-compatible CP as the foundation. We chose model: DeepSeek V4.1 vision CP and single-owner image encoding #40219 for its merge-before-shard multimodal preparation and single-owner image encoding. We adapted the owner callback API and fixed physical request-pool row mapping in the Torch prefill indexer. We borrowed the replay-tail idea from [DSV4.1] DeepSeek-V4.1 support prefill CP #40161 later, rather than importing its entire P/D integration.
    2. Integrate the Hopper paths and H20 configurations. This included [Perf] Optimize DeepSeek V4.1 Flash Hopper paths and Blackwell prefill selection #41251, [DSV4.1] Add H20 block-FP8 tuned configs #41098 and the relevant [DSV4.1] Enable Hopper decode optimizations for TP8 #39114 path, plus scorer/Top-K, compression, RoPE, dispatch and preparation changes listed below. We checked actual dispatch and added tables for six further missing matrix shapes encountered in this integration; small tuning differences below 3% retained the default. These additional local tables are distinct from the original six tables in [DSV4.1] Add tuned H20-3e block-FP8 GEMM configs #39306.
    3. Enable Engram host storage and HiCache together, then tune EP. The per_rank layout shards the host Engram table across ranks rather than replicating the entire table eight times. The combined memory configuration increased the engine-reported KV token-pool capacity by about 31.25% relative to our preceding GPU-Engram/HiCache-ratio-2/memory-fraction-0.88 configuration, with essentially unchanged near-512K TTFT. This is a combined memory-layout result, not a standalone offload speedup.
    4. Add decoder bounded replay while preserving image requests and DSpark. After the last KV-source layer, replay shortens the late-layer token rows. We added tail-aware CP gather, global token indices for logits/DSpark, original CP-owner mapping, and preservation of canonical image IDs. This became [DSV4.1] Support decoder SWA bounded replay with vision CP and DSpark #42924, with [DSV4.1] Fix Torch prefill indexer request-pool rows under CP #42922 as a separate row-mapping fix.
    5. Add fused prefill scoring and native SM90 block32 FP8 GEMM. [DSV4.1] Fuse Hopper prefill indexer scoring into one Triton kernel #42365 fuses indexer score/ReLU/weighting/head reduction; [SM90] Use native block32 DeepGEMM for DeepSeek-V4.1 #42604 enables the supported native DeepGEMM linear paths. We retained the existing compact-candidate path and fallbacks. Routed MXFP4 experts still use FlashInfer.

    The later stages used the same workload protocol:

    Stage 128K cold TTFT (s) 524,032-token cold TTFT (s) C64 aggregate output (token/s)
    Integrated CP/DSpark + host Engram/HiCache, EP8 10.533 56.613 2,263.19
    Change to EP4 9.416 52.323 2,362.80
    Add decoder bounded replay 6.682 41.390 2,380.37
    Add #42365 + #42604 5.385 25.531 2,534.61

    These are sequential stage comparisons. EP4 improved long prefill and C64 throughput, but at that step C1 decode fell 5.2% (169.42 → 160.53 token/s); it was a workload tradeoff, not a universal EP4 win.

    Ablation of #42604: retaining #42365 but removing #42604 and reverting its DeepGEMM dependency upgrade changed 524,032-token TTFT from 25.531 to 26.824 s (+5.1%), C1 decode from 180.05 to 168.23 token/s (−6.6%), and C64 aggregate output from 2,534.61 to 2,356.33 token/s (−7.0%). We therefore retained both. This ablation compares the adjacent runs and includes the dependency change; it is not a kernel-only attribution.

At the snapshots we fetched, #40436 and #40421 contained the same KV-reuse changes, so we counted that work once. Some paths replace others; backported PR count is not a count of simultaneously active speedups.

    Experiments not retained:

    • TP8/EP1 with Marlin W4A16: C64 aggregate output 1,797.47 token/s, versus 2,362.80 for the then-current EP4 build. Both backend and parallelism changed, so this is not an isolated EP comparison.
    • TP8/EP1 with an adapted FlashInfer W4A8 path: preserve logical shard boundaries, then pad the 288-wide expert intermediate dimension to 384 for the required 128 alignment, including gate/up halves, down columns and scale handling. It passed our operator/model checks, but C64 reached 2,139.99 token/s, still below EP4.
    • TP8/EP2: slightly better TTFT, generally worse natural-generation aggregate throughput.
    • Chunk 8192 → 16384: about 1.5% better long TTFT, about 4.6% worse C64 aggregate output; retained 8192.
    • CP local-projection deduplication: approximately 21–33% faster in the projection+gather microbenchmark, only 0.4–1.1% TTFT improvement end to end with mixed throughput results; removed.
    • [DeepSeek V4.1] an FP8 Tensor Core path for the FP4 grouped indexer #40160 H32 adaptation: correctness checks passed, but none of the six tested shapes beat the existing scorer; not dispatched in production.
    • The medium-mHC path remained disabled pending further validation.

    5. Our three upstream PRs and their independent evidence

    #39306 — H20-3e block-FP8 GEMM configurations. The original Hopper kernel prerequisite has since landed as #39657, so our updated PR uses that upstream kernel and preserves the six H20-3e tuning tables, numerical tests and benchmarks in the current GEMM module layout. October 7 validation on pinned main covered 3,120 numerical subcases and 72 GEMM shape/batch points. Against generic configs: 69 faster / 3 within ±3% / 0 slower; against H200 tables run on H20: 49 / 12 / 11. Thus the H20 tables are not universally best. The previously reported 44.16 → 84.48 token/s (+91.3%) C1 serving improvement is explicitly historical, measured in the earlier pinned #39114 integration without CP/speculation, not a new current-main serving result or an additive gain on top of the tables above.

    #42922 — Torch prefill indexer request-pool rows under CP. Maps real local query rows to physical request-pool IDs, covering non-contiguous slots, unequal request lengths, tails and padding. It is a small correctness/enablement fix, directly targeting main; exercising the relevant end-to-end vision-CP path requires #40219. We do not attribute a standalone model speedup to this fix.

    #42924 — decoder SWA bounded replay with vision CP and DSpark. Stacked on #40219 + #42922. The new replay implementation is isolated in a seven-file incremental diff. It preserves #40219's multimodal input contract and supplies tail-aware hidden/auxiliary-state gather, global logits/DSpark indices, original CP ownership and canonical image IDs, following the tail-handling idea in #40161.

    For #42924 we ran a separate, smaller control/candidate comparison: pinned main@d7190b01 + #40219@cfbace49 + #42922 and a common owner-callback API adaptation, TP8/EP8, CP8, DSpark5. The candidate adds replay support and enables it. No other production optimization bundle, host Engram or HiCache is included. These isolated PR runs use a separate official dev runtime: PyTorch 2.14.1+cu130, Triton 3.8.0, FlashInfer 0.7.0.post1 and sglang-kernel 0.4.9; exact pins and commands are in the PR.

    As of October 13, all three PRs are open and non-draft. #42924 is ready for review but needs a rebase as main and its still-open #40219 dependency have advanced; the tested pins above remain the provenance of these results. We are reporting local validation, not claiming upstream GPU CI has passed.

    Our practical takeaway for this hardware/workload is that vision-compatible CP + DSpark + decoder replay, followed by the fused Hopper prefill indexer / native block32 FP8 paths, made the deployment substantially more usable. Decode and mixed-load scheduling still have room to improve: in two finite mixed-load checks (128K+C8 and 256K+C32), the longest streaming gaps were about 5.0 s and 11.1 s, respectively—not production P99s.

    Thanks to the authors of the underlying SGLang, FlashInfer and DeepGEMM work. Our contributions are H20-specific tuning, integration/compatibility fixes, and validation of this combined serving path. Hopefully the measurements and the three focused PRs provide useful feedback for this roadmap.
