Motivation

PR #41364 adds topk_page_transform, which combines DeepSelect Top-K selection with the page-table transform in its epilogue.

DeepSeek V4.1 on Hopper still uses:

torch.topk
  -> sort raw indices
  -> gather physical KV slots

This PR connects the new DeepSelect operator to that runtime path.

Modifications

  • Use topk_page_transform for the SM90 full-topk decode path.
  • Write transformed int32 KV slots directly into the existing output buffer.
  • Preserve raw-index ordering with sorted_index=True.
  • Keep the existing Torch path when raw indices are also required.
  • Keep SM100 and newer architectures on the existing DeepGEMM path.
  • Add CPU dispatch/fallback tests and an H20 runtime integration test.

Accuracy Tests

Validated on NVIDIA H20:

Test Result
DeepSelect kernel tests 10/10 passed
Related indexer unit tests 28/28 passed
New runtime integration tests 5/5 passed
_torch_decode statement coverage 90%

Coverage includes short contexts where width < topk, variable row lengths, page-table mapping, sorted output, and the raw-index fallback.

Speed Tests and Profiling

The replaced region was benchmarked on NVIDIA H20 with CUDA 13.0 and PyTorch 2.13. Each complete run used 20 warmup iterations followed by 5 groups of 100 measurements. The table reports the mean of the medians from two complete runs.

The measured regions were:

Before:
torch.topk -> raw-index sort -> slot gather -> output copy

After:
DeepSelect top-k -> sorted-index epilogue -> page-table transform
Rows Width Top-K Before After Speedup
1 32K 512 163.264 us 31.744 us 5.14x
8 32K 512 163.992 us 31.592 us 5.19x
32 32K 512 163.664 us 31.456 us 5.20x
1 128K 1024 162.864 us 31.760 us 5.13x
8 128K 1024 164.960 us 32.480 us 5.08x

This is a microbenchmark of the replaced Top-K and transform region, not an end-to-end serving throughput claim.
