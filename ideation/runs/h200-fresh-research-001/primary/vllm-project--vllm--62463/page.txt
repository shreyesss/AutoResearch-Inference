Overview
Add a Triton candidate-only decode scoring path for DeepSeek V4.1 on SM90,
reading FP8 K directly from the paged indexer cache instead of scoring the
full context and masking it afterwards.
Related to
#61830
. This is a separate implementation from the gather-based
prototype in draft
#62000
: it avoids the intermediate candidate-K buffer.
The flag is off by default (
VLLM_DSA_CANDIDATE_PAGED_DECODE=1
to enable).
Claims
On H20 TP8 with ~1M input tokens, the evalscope A/B below measured a
9.6–23.8% reduction in mean ITL
across concurrency 1/2/4/8.
Consumer logits use 16,384 candidate columns instead of the full compressed
context. The candidate-source layers, pre-candidate layers and prefill path
are unchanged.
Path selection uses configuration checks, not capture-time context lengths.
Live lengths and page tables remain device inputs during CUDA graph replay.
These results cover the measured long-context workload, not a general
no-regression claim. Accuracy and shorter-workload checks are still pending.

I use ITL as the main latency metric here, with TPOT and throughput as
supporting results. Under speculative decoding, streamed chunks can contain
multiple tokens: client ITL is not necessarily one GPU iteration, nor is it
independent of acceptance, scheduling or buffering. TPOT remains a valid
user-facing metric, but neither metric alone isolates the kernel change.
This is one A/B pair, not a confidence-interval result. Many intervals within
the same requests do not replace independent runs. At concurrency 4, overall
completion throughput was 827.33 -> 814.72 tok/s (-1.5%) despite lower ITL,
so this is not a throughput win at every concurrency.
I also ran an earlier TP4 test at 200K context. It showed a much smaller ITL
change; the TP8 evalscope run and trace below are the main evidence here.

Model-level accuracy results are pending. I'll compare the flag on and off

Details
The path prepares per-row candidate blocks and causal bounds, reads candidate
K directly through the page table, scores into a compact buffer, runs the
existing top-k, and remaps the selected columns to request-local positions.
It reuses candidate preparation and remapping from vLLM's SM100 sparse path.
FP8 dot products use FP32 accumulation; invalid columns are masked and valid
column counts are passed to top-k.
For the tested model,
index_head_dim=128
,
index_n_heads=32
,
candidate_topk_blocks=2048
,
candidate_block_size=8
, and
index_topk=512
.
The compact FP32 logits buffer is
[rows, 16384]
(1.5 MiB at 24 rows).
With five speculative tokens, six decode rows represent one fully populated
request in the kernel input; this is not necessarily the client's concurrent
request count because scheduling and graph padding can change the batch.
The path requires SM90, an FP8 indexer cache, no DCP/PCP, and supported
candidate geometry. When disabled or rejected by the availability check, the
existing dispatch remains in use; existing unsupported combinations may still
raise errors. The gate has no batch-size or context-length profitability
threshold. Avoiding a K copy does not remove preparation, sorting, top-k and
remapping costs, so short-context performance still needs checking.
What's next
Accuracy:
compare lm-eval results with the flag off and on.
Performance outside 1M:
benchmark shorter contexts, small batches and
smaller real datasets to check for latency or throughput regressions.
Kernel work:
try a CUDA/CUTLASS implementation and compare it with
Triton. I'll profile scoring, candidate preparation and top-k before
deciding which part to optimize; there is no measured speedup for this yet.
I'd appreciate feedback on the implementation while I finish the accuracy and
short-workload checks. Those results still need to be confirmed before merge.
Prefill optimization is outside this PR.

Score only the candidate blocks in the SM90 DSv4.1 decode indexer
…
57b53a5
The V4.1 candidate-consuming indexers have no paged sparse scoring kernel
on SM90, so they score the whole compressed context and then mask the
logits down to the candidate blocks. With a 16K-position candidate set
against a 1M-position context that discards ~98% of the scoring.

Score the candidate positions only, reading K in place from the paged FP8
indexer cache into a compact per-row logits buffer, then remap the
selected columns back to request-local positions. The candidate-source
and pre-candidate indexers stay dense, and prefill is untouched.

The path is gated by candidate_paged_decode_available(), a predicate over
model/platform/scheduler config only: SM90, FP8 indexer cache, no
DCP/PCP, power-of-two candidate geometry, and topk within the candidate
capacity. Every input is config-fixed, so the decision is a CUDA-graph
invariant: a captured graph cannot diverge from the path chosen at
capture. The profiling run reserves the candidate workspace sized by
max_num_seqs * (1 + num_speculative_tokens), so the hot path never
requests more than was profiled. The per-row candidate preparation is a
small extra step, paid only when the path is active.

Candidates are indexed per decode row, as the dense path mask does; only
the causal lengths are shared across a request's speculative rows.

Numerics follow the decode reference: dot, relu, head weights, sum over
heads, then one dequantization multiply per column. Scoring runs on fp8
tensor cores with fp32 accumulation.

Default off behind VLLM_DSA_CANDIDATE_PAGED_DECODE.

Share the per-step candidate plan across consumer layers
…
1abc6a2
The candidate expansion (prepare + sort) is a deterministic function of the
step-level candidate buffer and seq_lens, identical for every
candidate-consuming layer, but it ran once per layer. Compute it once per
step into builder-owned buffers and let the later layers reuse it, the same
pattern the SM100 path uses for its kernel metadata. Bit-identical
memoization: same input tensors, same kernels, same output.

Also early-exit scoring tiles fully past a row's valid candidate count, so
short contexts no longer pay MMA work for the padded tail of the fixed-width
candidate window. The grid stays static, so this is CUDA-graph safe.
