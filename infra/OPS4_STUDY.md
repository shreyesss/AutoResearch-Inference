# OPS4 serving study: fixed four tasks

The agent tunes **one vLLM serving configuration** for pinned Qwen/Qwen3.8-27B on the single RTX PRO 6000 Blackwell GPU. Every candidate is measured on all four tasks at each task's exact frozen request bodies and timestamps. The twelve primary coordinates are output tokens/s (higher), TTFT p99 (lower), and TPOT p99 (lower), separately for each task. `suite-front.json` reports complete-configuration point-estimate Pareto membership; per-task fronts and all dominated, failed, and incomplete attempts remain visible. No scalar score, SLA, or production-representativeness claim is implied.

| Task ID suffix | Source `ops_aiperf` input | Request shape | Arrival point |
| --- | --- | --- | --- |
| `chat-low-v1` | `synthetic-chat.yaml` | nominal 512 input / forced 256 output tokens | calibrated source Poisson 2.56 configured RPS; exact realized schedule frozen |
| `agent-low-v1` | `synthetic-agent.yaml` | nominal 8,192 input / forced 1,024 output tokens, Qwen thinking on | calibrated source Poisson 0.15 configured RPS; exact realized schedule frozen |
| `document-reference-v1` | `synthetic-document.yaml` | nominal 32,768 input / forced 512 output tokens | calibration selects a drainable ordinary point, then freezes its exact schedule |
| `mixed-reference-v1` | `synthetic-mixed.yaml` | engineered 45% chat / 20% agent / 15% document / 20% code lengths | calibration selects a drainable ordinary point, then freezes its exact schedule |

Nominal input length describes the source generator; the server's actual prompt token count, including template effects, is measured. All four are **independent, single-turn, synthetic diagnostic** inputs. Mixed weights are engineered, not a measured deployment distribution. Bursty, multi-turn, semantic, and production traces are outside this first campaign. All raw source and frozen manifests are tracked in `configs/workloads/`; the rsynced `Deepseek_serve/` source stays untouched.

The agent receives the current B0 report, all four workload cards, exact campaign/domain files, prior candidates and feedback, and path-indexed raw request/server/GPU artifacts. It may read these files and keep short `notes.md` between attempts. Its Docker container has a writable attempt folder and internet research (`web_search=live`, Docker bridge networking); the model and reasoning effort are campaign settings. It cannot change inputs, evaluator policy, score, server launcher, or run the GPU. The controller validates proposals, evaluates the full four-task suite, records all outcomes, and exports reports. External documentation is hypothesis evidence, never a substitute for measured cells.

The fixed four-task search gate requires: (1) each frozen input independently replayed and content-hash validated, (2) one complete, normal, matched fresh-server screen B0 cell per task, and (3) an intact pinned environment. A transient server queue is admissible only when at most three requests wait, post-send drain is at most 10% of dispatch time, dispatch lag p99 is at most 20 ms, and all requests complete cleanly. The admission reason and queue/drain evidence stay in the cell result. This is exploratory inference-metrics research. Repeats and longer windows are required before claims about stable tails or serving capacity. The first candidate can itself test parameter sensitivity; no historical manual result is injected as a prior.

Search variables are the active, versioned entries of `configs/search-domain.json`: sequence cap, batched-token cap, GPU memory fraction, prefix caching, and MTP draft tokens. Other controls may be activated only in a new versioned domain after runtime support and measurement relevance are established. Missing parameters resolve to B0. A change is judged against **matched B0 on every task**, including failure, queue, drain, latency distribution, output rate, and diagnostic counters; a fast but incomplete or backlog-growing cell cannot enter the frontier.
