Summary

Replace fmaxf(x, 0) with x + fabsf(x) in the SM90 FP8 MQA logits epilogue, recovering the 2× throughput gap between FMNMX (half-rate) and FADD (full-rate) on Hopper. The factor-of-2 introduced by the identity is resolved by folding 0.5f into the existing scale_kv multiply — zero extra instructions, bit-exact numerics.

Background

On SM90, fmaxf(x, 0) compiles to a single FMNMX, which issues at 64 ops/clk/SM — half the rate of FADD/FFMA (128 ops/clk/SM). Meanwhile x + |x| compiles to a single FADD with the absolute-value operand modifier, which is a free encoding bit in the instruction word:

FADD R3, R3, |R3|    ; one instruction, full rate (cuobjdump, sm_90a)

The relu executes once per (token, head, kv) score element in the MQA logits epilogue, so at 64 vs 128 ops/clk/SM the FMNMX form doubles the FP32 pipe time spent on relu alone.

Since x + |x| = 2 · relu(x) holds exactly for all finite IEEE-754 floats (+0 for x ≤ 0), the doubled sum is simply halved by folding * 0.5f into the already-existing scale_kv multiplication (an exponent decrement, also exact):

// Before:
return fmaxf(shifted_accum[j], 0) * weights[i][(j / 4) * 2 + (j & 1)];
...
float v_0 = (sum[0] + sum[1]) * scale_kv_0;

// After:
return (shifted_accum[j] + fabsf(shifted_accum[j])) * weights[i][(j / 4) * 2 + (j & 1)];
...
float v_0 = (sum[0] + sum[1]) * (scale_kv_0 * 0.5f);

The same technique is already used by the SM100 kernel (sm100_mqa_logits.cuh, packed FADD2 variant); this PR brings it to SM90. Verified via cuobjdump -sass: zero FMNMX across all JIT-instantiated sm90_fp8_mqa_logits cubins.

Performance (H200, 132 SMs, SM90A)

Production indexer shapes, best of 3 reps, before → after:

Shape Before After Gain
H=32, D=128, SQ=512, SKV=140k, FP32 logits 1018 TFLOPS 1093 TFLOPS +7.4%
SQ=512, SKV=130560, H=64, BF16, CP=1 1042 TFLOPS 1126 TFLOPS +8.1%
SQ=512, SKV=130560, H=32, BF16, CP=0 941 TFLOPS 989 TFLOPS +5.1%
SQ=2048, SKV=8192, H=64, BF16, CP=1 980 TFLOPS 1027 TFLOPS +4.8%

Full tests/test_attention.py sweep (192 contiguous MQA cases on SM90): avg +3.7% (SK=65536 subset +4.4%, H=64 subset +5.5%, best case +11.3%). Gains scale with the relu's share of kernel time: larger SKV, more heads, smaller head dim → bigger win. Paged MQA logits (separate kernel, untouched) is unaffected.

Correctness

  • x + |x| = 2 · relu(x) exactly for all finite IEEE-754 floats (x > 0: x + x = 2x; x ≤ 0: x + (−x) = +0); the ÷2 via * 0.5f is an exact exponent decrement.
  • All 192 SM90 cases in tests/test_attention.py pass (numeric diff vs simulated reference, 20× bitwise self-consistency, mask equality) — verified on H200.
  • NaN semantics differ (x + |x| propagates NaN; fmaxf(NaN, 0) returns 0), but WGMMA accumulator outputs are finite in practice; this matches the SM100 kernel's existing behavior.

The MR replaces fmaxf(x, 0) with x + fabsf(x) in the SM90 FP8 MQA logits epilogue (sm90_fp8_mqa_logits.cuh) and folds the compensating * 0.5f into the existing per-KV scale_kv multiply. The diff is exactly 3 lines and matches the description.

Verified points:

  • Numerics: x + |x| == 2*relu(x) is exact for all finite IEEE-754 floats (x>0: 2x; x<=0: exactly +0). scale_kv * 0.5f is an exact exponent decrement. Result is bit-identical to the previous path for finite accumulators.
  • Placement of the 0.5f fold is correct: applied once per output element after the intra-thread reduction (sum[0]+sum[1]) / (sum[2]+sum[3]) and before the __shfl_xor_sync inter-thread reduction, so each of the kNumHeads contributing terms is halved exactly once. scale_kv_0/1 are loop-invariant across the BLOCK_Q loop, so scale_kv * 0.5f is hoisted by nvcc — genuinely zero extra instructions per element.
  • NaN semantics: fmaxf(NaN, 0) returned 0, whereas NaN + |NaN| propagates NaN. This matches the SM100 kernel (sm100_mqa_logits.cuh L492-506 already uses the identical x + |x| trick via __fadd2_rn followed by / 2), and WGMMA FP8 accumulators are finite in practice, so this is acceptable and consistent rather than new risk.
  • Scope: the paged MQA logits kernel is untouched, as stated.

No blocking issues. Performance claims (+3.7% avg, +7.4% on production shape, zero FMNMX in SASS) are plausible given FMNMX is half-rate on SM90 and the abs operand modifier is a free encoding bit on FADD; they were not re-measured here (no Hopper GPU in this environment). Two non-blocking, purely maintainability-oriented suggestions are left inline.

v4

Correct, low-risk SM90 micro-optimization. The MR replaces the half-rate fmaxf(x, 0) ReLU in the SM90 FP8 MQA logits epilogue with a full-rate FADD using the free absolute-value operand modifier (x + |x|), and compensates the resulting exact factor of 2 by folding * 0.5f into the already-present scale_kv multiply. I verified the change end to end: (1) for every finite IEEE-754 float, x + |x| == 2*relu(x) exactly (+0 for x <= 0, and x + x == 2x exactly for x > 0); (2) the factor-of-2 is uniform across the per-term weight multiply and across both the intra-thread and inter-thread (shuffle-xor) reductions, so it factors out exactly; (3) scale_kv * 0.5f is an exact power-of-two scaling for normal scales, so fl((2*sum) * (scale/2)) == fl(sum * scale) is bit-exact versus the previous fmaxf path. The change is local (3 lines in one file: line 286 transform plus the two * 0.5f folds at lines 297-298), preserves the kernel's dataflow/synchronization, and is consistent with the existing SM100 sm100_mqa_logits.cuh implementation that already uses the same fabsf + /2 identity. The claimed SASS result (a single FADD with the abs operand modifier replacing FMNMX) is consistent with the documented SM90 issue rates. Verified caveats, none blocking: (a) only non-finite inputs differ, since fmaxf(NaN, 0) == 0 while x + |x| propagates NaN and x == -inf gives NaN; WGMMA accumulator outputs are finite in practice and this matches the SM100 kernel, so it is acceptable; (b) the exactness of the halving relies on scale_kv being normal (subnormal halving could lose a bit, and the doubled accumulator could overflow only near FLT_MAX), which realistic FP8 dequant scales and attention logits never approach. No correctness, safety, API, or concurrency issues found, and no changes requested.
