The optimization builder owns the three-file C03 port and launch isolation. The orchestrator reviews both and schedules execution. An optimization-builder change to evaluator expectations or verdicts is not permitted.

The existing setup is sufficient. Keep the local node 223, exact `latency-2xdep4-sla.yaml`, 0.5× timestamp replay, existing launcher `.venv`, existing `.venv-aiperf` 0.13 client, and pinned serving container. ## Small, separate evaluator implementation

The needed work is one bounded observation patch, one focused fixture module, and one offline paired-result/report reader. Keep them separate from the optimization diff. Reuse the existing JSON/CSV exports and `score.json`; the reader consumes the existing score rather than replacing it. Store implementation, tests, frozen assertions and receipts under the C03 worktree. No persistent service, new database or scheduling layer is necessary.

The observation patch belongs to the evaluator builder, including when it touches a file that the optimization builder also changes. The orchestrator composes independently reviewed changes and preserves separate hashes. Diagnostic A and B get the same observation semantics; ordinary service comparisons have these hooks disabled in both. With probes completely disabled, an instrumentation-overhead benchmark is unnecessary. If keeping probes enabled becomes necessary, pause and obtain a designer-approved matched overhead check before using those timings.

Record the following missing fields with a shared replica/DP-step/rank identity:

- Real local request count before target graph padding, plus the four-rank count vector from the **existing** synchronized row, so the offline oracle computes its own maximum. Do not add an extra all-reduce just for telemetry.
- Target graph mode, target descriptor request capacity and token count; actual DSpark query width; online versus startup/profile/capture/dummy state.
- Requested draft tokens/rows, selected draft descriptor mode/capacity, and the execution descriptor actually submitted for replay. Requested counts are not executed rows.
- Valid input/position/slot/KV metadata extents, local real count and effective dummy count. For controlled fixtures record marked row/request identity and proposal/RNG ownership; do not dump production prompts or every probability tensor.
- Counter epoch/reset, missing/duplicate rank-step records, dropped samples and the observed graph table hash. Raw sampled steps must align across all four ranks; independent random samples cannot establish an all-rank invariant.

Use exact aggregate counts/histograms for all diagnostic dispatches and a bounded deterministic sample for inspectable records. If recording drops any event needed for an invariant, report incomplete coverage rather than treating absent rows as zero. No per-token synchronous log printing or `.item()`/device synchronization added to the measured service path. The selected graph descriptor is an adequate first proof of executed graph capacity; a separate short trace is required only when descriptor accounting cannot establish actual dispatch.

For supported qualifying events, every observed B executed bucket must equal the independently predicted bucket and all-rank metadata must be coherent. There is no allowed fraction of incorrect requests. Report the number of stronger opportunities, fraction with lower executed rows, and same-bucket controls separately. Reject the mechanism on adequate stronger opportunities with no observed reduction, after validating the observation path. A rare-exposure workload remains a limited-scope result even if controlled fixtures prove the arithmetic.

Count each dispatch/opportunity once per `(replica, counter epoch, DP step)`. Its four rank records verify one event; they never multiply the denominators or the 1,000/100/100/20 coverage floors. If burst is needed for diagnosis it is no longer wholly unobserved, although its service endpoints remain held out. Median remains the primary endpoint. A median-inactive/burst-active finding is a burst mechanism lead requiring a separately preregistered burst-primary experiment, not permission to switch the current primary endpoint.

The full arithmetic grid is cheap. Do not expand it into hundreds of end-to-end model replays: use CPU/reference coverage for every boundary and bounded GPU cases for distinct execution/preparation branches. If a branch cannot be covered by the bounded set, add its named case before treatment measurements, with the reason recorded.

## Frozen quantitative decisions

The designer's finalized contract fixes the 2% useful-gain threshold, 3% tail guard, five paired blocks and existing replay/service gates. This review adopts these precise execution rules:

1. The stronger-opportunity floor is ≥100 total and ≥20 per replica with all ranks accounted for, counted as unique dispatch events as above. Absence and insufficient observations are distinct outcomes.
2. Controlled fixtures require exact metadata, input probability tensors, RNG ownership and expected committed tokens. No generic floating-point tolerance is authorized. If nondeterminism or full-model numerical differences prevent the scoped comparison, stop that correctness lane and obtain a written designer addendum specifying fixed A-only calibration repetitions, tolerance and error bounds before further B evaluation. Never derive tolerances from B discrepancies or acceptance. This does not require bitwise equivalence of every full-model intermediate across different batch shapes.
3. Screening promotes only a pair with valid fidelity, correct activated mechanism, positive primary point gain and no observed >3% median TTFT p99 or E2E p99 regression. Otherwise the performance screen is deferred/inconclusive, not final rejection of a 2% effect. Correctness failure blocks the port. Do not repeat a valid unfavorable screen until it wins.
4. Bootstrap the arithmetic mean of five paired percent gains using 10,000 resamples of five complete block indices. Initialize Python `random.Random(20261020)` and use `randrange(5)` for each index. Take sorted resampled means' 2.5/97.5 percentiles with linear interpolation at `q*(10000-1)`. Tail regressions use `100*(B_tail/A_tail-1)`, the same sampled block indices and the same percentile rule. These are per-endpoint intervals, not simultaneous familywise coverage. Decide once after five valid blocks; insufficient precision is inconclusive, with any further campaign requiring a new predeclared addendum.
5. An invalid fidelity/identity arm invalidates its whole pair; retain both original arms and reasons. Replace only after an identified, resolved and recorded external fidelity/identity cause, repeating the entire pair with the same seed and arm order under fresh IDs. Permit at most two whole-pair replacements; a third invalid pair stops confirmation as inconclusive. Candidate-induced errors or suspected correctness regressions require investigation and cannot be replaced as noise. Never replace a slow B or completed service-SLO-ineligible result whose fidelity passes. Correctness failure is a stop.

The reduced scope deliberately avoids a new stochastic sampler statistical-certification project: C03 changes execution counts, not the rejection algorithm. If the implementation intentionally changes valid probabilities, RNG ownership or rejection semantics, it exits this plan and requires a new evaluator contract.

## Handoff and evidence

Before optimization implementation, the evaluator designer freezes the contract, the evaluator builder supplies the observation/fixture schema and failing negative controls, and the orchestrator approves composition. Before timing, independent checks must show the fixtures catch wrong capacity and row ownership, the candidate meets them, and source/image/graph identity is matched. A passing test must include its assertions and coverage; a bare command success is insufficient.

Each stage keeps a small receipt: source and contract hashes; A/B identity; fixture coverage and intentional negative-control failures; aligned rank/step examples and complete histograms; original AIPerf artifacts and scorer verdict; separate paired benefit/guard/fidelity verdicts; unresolved gaps. Preserve failed and incomplete runs. The implementation builder must not edit these receipts or regenerate expectations using its changed helper.

Review conclusion: feasible with the existing tools and a small C03-specific diagnostic/fixture addition. Current baseline service failures are measurable baseline behavior, not a reason to discard the completed corrected run. Actual online mechanism exposure, treatment correctness and benefit remain untested.
