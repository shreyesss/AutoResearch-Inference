# Evaluator recommendations: critique and decisions

**Scope:** documentation and proposed evaluation only. No serving change, benchmark, profiler capture, or correctness run was performed. The two pasted recommendations substantially duplicate each other; the second additionally requests AIPerf's SPEED-Bench and MTP-specific capabilities.

## Accepted, with corrections

| Suggestion | Decision and reason |
|---|---|
| Preserve native synthetic and fixed-schedule Mooncake | **Accept.** Native `agent-f75` has a specific 8K/1K, Zipf-prefix, exact-output protocol; AIPerf synthetic `agent` is not equivalent. Mooncake measures a separate arrival/cache/length distribution. Preserve both historical cohorts and their existing scorers. See [source audit](EVALUATION_CAPABILITIES.md). |
| Collect vLLM, host and GPU telemetry for every comparison | **Accept as a required measurement contract.** First inventory metrics on the *deployed image*. Scrape every replica and rank, retain labels and timestamps, compute counter deltas over the measurement interval, and detect missing series/resets. A `/metrics` scrape alone cannot identify the final rank or prove that a particular kernel ran. |
| Add Nsight Systems | **Accept for short diagnosis.** Compare matched baseline/candidate captures, annotate request/iteration phases, preserve process/rank and CUDA graph mode, and export machine-readable traces. The existing wrapper sets `--sample none --cpuctxsw none`; CPU scheduler hypotheses require an explicit CPU capture mode. Profiles are diagnostic, never capacity points. [vLLM profiling](https://docs.vllm.ai/en/latest/contributing/profiling/), [Nsight Systems guide](https://docs.nvidia.com/nsight-systems/UserGuide/index.html). |
| Keep Nsight Compute targeted | **Accept.** Select a demonstrated active kernel and representative shape after timeline inspection. Replay/instrumentation disturbs runtime; report kernel resource/traffic evidence separately from unprofiled serving capacity. [NVIDIA profiling guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html). |
| Use upstream tests and lm-evaluation-harness | **Accept, scoped.** Run changed-path numerical/sampling/parser tests first. Use a pinned generation-task quality subset when model math/precision changes; record task, prompt template, parsing, seeds, per-example output and score. A small suite detects regressions but cannot certify semantic equivalence. Chat APIs do not support the harness's loglikelihood tasks; choose generation tasks or a compatible completion endpoint. [Harness API guide](https://github.com/EleutherAI/lm-evaluation-harness/blob/main/docs/API_guide.md). |
| Add cold/warm, pressure, context and load cases | **Accept as targeted fixtures, not an unbounded Cartesian product.** Verify that cold is actually cold and that pressure produces occupancy/evictions. Keep request identities, prefix distribution and offered load matched. A single warm-cache number can hide eviction or rank churn. |
| Save artifacts and produce four-part report | **Accept, strengthen.** Separate validity, performance, mechanism and correctness verdicts. Also report activation failure, missing telemetry, route/shape selection and changes in GPU memory that alter usable KV capacity. |

## Corrections to the proposed flow

1. **Activation precedes expensive evaluation.** A candidate needs an exact baseline membership and path/shape check. E09's FlashMLA kernel, E02's padded rows and E14's internal selector must actually execute; source-level applicability alone is insufficient.
2. **Correctness is mechanism-specific.** G01 needs distributional sampler checks, G02/G03 need changed-input replay and memory/synchronization probes, G04 needs real tool-role encoding, G05 needs idle/restart liveness. A generic model-quality score is not a substitute. The existing native session driver strips tools and synthesizes tool-like text as a user turn; it cannot certify G04.
3. **Profiling is conditional.** If an isolated candidate is inactive or fails a cheap correctness gate, stop. If counters already explain a repeatable result, a full Nsight capture is optional. CPU-only and cold-start experiments may need process spans/readiness timestamps more than GPU kernel analysis.
4. **Use real comparison units.** Pair complete runs, not individual requests or GPU ranks, for uncertainty. A single attractive Mooncake 1× throughput point is arrival-limited; capacity needs the common offered-load grid and passing SLO gates.
5. **Track tradeoffs explicitly.** Extra graph buckets, precision layouts, offload and host backing can change HBM/KV capacity, restart time or tail latency. A faster isolated kernel can worsen the service frontier.
6. **Treat AIPerf features as versioned capabilities.** The pinned [0.13.0 release](https://github.com/ai-dynamo/aiperf/releases/tag/v0.13.0) includes speculative metrics; its [SPEED-Bench guide](https://github.com/ai-dynamo/aiperf/blob/v0.13.0/docs/tutorials/speed-bench.md) describes category reports. The audited `ops_aiperf.runner` exposes its own finite CLI and has not been shown to support every direct `aiperf profile` option. Verify the actual installed binary, dataset loader, server wire format and per-request telemetry before using them. Do not relabel a direct AIPerf diagnostic as a historical E2 run.

## Evidence standard

Each [mechanism card](MECHANISM_CARDS.md) separates **source-observed inefficiency**, **source-proposed fix**, and **our additional hypothesis**. An upstream PR shows motivation and implementation intent, sometimes results on other hardware; it does not prove that the pinned B200 image has the bug or that the patch improves this service. A measurement marked `missing` means **unverified**, not zero. The [evaluation plan](EVALUATION_PLAN.md) specifies the activation gate, PR-specific internal measurements, integrations and final evalset.
