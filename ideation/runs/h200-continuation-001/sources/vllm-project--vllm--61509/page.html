Overview

With adaptive verification on, Model Runner V2 counts the allocator cache left by adaptive verification's cost-profiling dummy runs as CUDA graph memory, and takes it from the KV cache. This PR releases that cache before capture_model takes its closing memory reading.

Claims

  • Fixes the over-counted CUDA graph memory under adaptive verification, in both the memory-profiling estimate pass and the real capture (0.92 → 0.07 GiB in the run below). The KV cache gets that memory back.
  • When KV capacity is the bottleneck, decode throughput recovers: 40.5 → 113.2 tok/s in the run below, matching the same config without adaptive verification (110.2 tok/s).
  • Startup only. Nothing changes in steady-state execution, and runs without adaptive verification are unaffected.

Validation

Startup log. 1× L4, Qwen/Qwen2.5-1.5B-Instruct with Qwen/Qwen2.5-0.5B-Instruct as draft_model, num_speculative_tokens=4, enable_adaptive_verification=true, TRITON_ATTN, max_model_len=32768, max_num_seqs=3, prefix caching on:

vllm serve Qwen/Qwen2.5-1.5B-Instruct --attention-backend TRITON_ATTN \
  --max-model-len 32768 --max-num-seqs 3 --gpu-memory-utilization 0.36 \
  --speculative-config '{"method": "draft_model", "model": "Qwen/Qwen2.5-0.5B-Instruct",
    "num_speculative_tokens": 4, "enable_adaptive_verification": true}'
# compare the two "Graph capturing finished ... took X GiB" lines and "GPU KV cache size"

Throughput. Decode-bound long-context workload, greedy, max_tokens=256:

  • 12 prompts, each a 24K-token slice of vLLM's docs followed by a question.
  • Contexts are processed in groups of 3. Each group is first prefilled with one question, then timed with a different question, so the timed requests reuse the warmed prefix.
  • One run per config. The memory numbers are deterministic: both runs without the fix logged 0.92 / 0.88 GiB.
gpu_memory_utilization Config "Graph capturing ... took" (estimate / real) GPU KV cache Prefix hit rate Output tok/s
0.36 main, adaptive verification 0.92 / 0.88 GiB 64,688 tokens 37.8% 40.5
0.36 this PR, adaptive verification 0.07 / 0.04 GiB 86,960 tokens 50.0% 113.2
0.36 adaptive verification off (reference) 0.07 / 0.03 GiB 87,376 tokens 50.0% 110.2
0.9 main, adaptive verification 0.92 / 0.88 GiB 376,432 tokens 50.0% 110.6
0.9 this PR, adaptive verification 0.07 / 0.04 GiB 398,912 tokens 50.0% 110.1

At 0.36, 64,688 tokens can't hold three ~24.3K-token requests. Prefixes get evicted and re-prefilled (hit rate 37.8% vs 50%), and decode runs fewer requests at once. At 0.9 there's enough KV either way, so only the KV size changes.

The effect is larger with bigger models. With #60339's suffix speculator and adaptive verification on Qwen2.5-7B at 24K context (L4, utilization 0.9), the leftover cache was 1.88 GiB:

  • KV cache: 44,400 tokens before, 79,584 after.
  • Long-context decode: 0.28× of no speculation before, 1.39× after.

Tests.

pytest tests/v1/worker/test_gpu_model_runner_v2.py tests/v1/worker/test_gpu_model_runner_v2_cudagraph_profiling.py tests/v1/spec_decode/test_adaptive_verification.py
# 48 passed

The new test_capture_model_excludes_adaptive_verification_profiling_cache covers both profile_only=False and profile_only=True, and fails on main.

Details

Root cause. capture_model reads free memory, captures the graphs, then reads free memory again. The difference is reported as CUDA graph memory. When adaptive verification is on, the profiling for its cost curves also runs between those two readings: batches_to_profile, i.e. 5 replays of each capture size plus tail sizes up to max_num_batched_tokens, with the profiling context length. Those dummy runs free their tensors, but the caching allocator keeps the blocks. get_memory_info therefore sees them as used: about 0.85 GiB here, and 1.9 GiB with a 7B target (allocated delta ≈ 0, all of it reserved cache).

The same capture_model serves profile_cudagraph_memory's estimate pass, whose result is subtracted from the KV budget. So the KV cache is sized as if graphs needed that memory.

Fix. Call torch.accelerator.empty_cache() after set_initial_cost_curves, matching the empty_cache() that already runs before the first reading. The profiling timings are already collected by then, since StepTimingCollector.collect synchronizes on exit.

Scope.

  • Model Runner V1 has no adaptive verification.
  • [Spec Decode] Cache adaptive verification profiles #52233 (opt-in persistent profile cache) touches the same block. On a cache hit it would skip the dummy runs, but it's off by default and doesn't change the accounting.
  • [Bugfix][Spec Decode] Profile adaptive verification tail on a schedulable batch shape #54065 and [Bugfix][Spec Decode] Profile adaptive verification tails as mixed batches #54077 change the shapes of the profiled tail, not the memory accounting.

Not duplicating existing work. The only related results are the PRs listed under Scope.
