# E13: Coordinate prefill across DP ranks

**Status:** planned, untested; performance inspection rank 13.

## Hypothesis

Bounded prefill synchronization may protect decode steps from rank-asymmetric prefill stalls.

## Source-grounded change and eligibility

- [vllm-project/vllm#51199](https://github.com/vllm-project/vllm/pull/51199): DP4/EP4 ranks execute coordinated work; isolated long prefills can stall decoding ranks. Cheap asynchronous coordinator release is relevant even though source test usedDP8,2Kbudget,no prefix cache.
  - Gate: Inspect coordinator/scheduler integration on actual source, existing prefill_schedule_interval and adaptive equivalents, async scheduling/DSpark compatibility; measure cross-rank phase skew before port.
  - Limits/dependencies: Open DRAFT. Author provides unit tests, not a measured B200 performance A/B; prefix-disabled 2K setup differsours.
  - Evidence: “Decode continues while prefill
  is delayed, with bounded fail-open and recovery behavior to guarantee progress.” See [root-candidates/candidates.json](../root-candidates/candidates.json) for snapshot, state and provenance.
- [vllm-project/vllm#61834](https://github.com/vllm-project/vllm/pull/61834): Synchronous alignment plus protected decode steps may reduce mixed iterations, but adds a CPU collective every step and can raise TTFT. Evaluate as alternative to#51199 undercurrentDP4 groups.
  - Gate: Existing prefill_schedule_interval is mutually exclusive; inspect wave reset, dummy/pause step participation, shutdown/cancellation and KV-pressure fail-open. Profile addedcollective cost beforeGPUscale.
  - Limits/dependencies: Open DRAFT; upstream branch noGPUrun. Reported MI355X DeepSeek-V4-Pro numbers come fromanother developmentbranch, single runs/differentnodes; gainsnottransferable.
  - Evidence: “On: one 6-int CPU all-reduce per step.” See [root-candidates/candidates.json](../root-candidates/candidates.json) for snapshot, state and provenance.

## Decision contract

Follow [the common protocol](../PROTOCOL.md). First prove the relevant path is active and the delta is absent. A failed applicability check means **not applicable**, not an experiment failure. Keep raw requests and failures. Run the mechanism diagnostic separately from unprofiled capacity measurements.

**Support:** the predicted mechanism changes in the intended direction, correctness passes, and the preregistered objective improves with repeatable run-level evidence. A correctness gate supports only its scoped correctness claim.

**Reject for this scope:** triggered mechanism and adequate measurement precision, but no practical end-to-end benefit; or a reproducible correctness/SLO regression. Retain successful kernel-only results separately.

**Inconclusive:** inactive/unverified path, missing baseline identity, too few qualifying requests, noisy confidence interval, changing workload/cache state, replay degradation or insufficient coverage.

**Alternative explanation:** changed prompt tokens, graph memory/KV capacity, cache hit rates, output lengths, arrival pressure or dependency upgrades may cause the apparent gain. Hold them fixed or report the change as a separate arm.

**Held-out check:** confirm on the other existing workload and a held-out Mooncake window; do not tune and claim success on the same window alone.

**Execution:** use the verified command forms in [evaluation audit](../evaluation/EVALUATION_CAPABILITIES.md); substitute candidate digest and isolated arm/profile. No image, benchmark, fixture implementation or deployment has been run for this plan.
