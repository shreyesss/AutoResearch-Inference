# H05 — Remove repeated scheduler/cache bookkeeping

Lane: **main**. Live-layout priority: **5**. Status: conditional plan; no GPU test or measured gain.

## Problem and causal hypothesis

Python scans of long null SWA block-table prefixes and repeated unchanged partial-prefix registration may consume scheduler time before GPU work can begin.

## Applicability to our H200 deployment

Verify live stack samples and absent equivalent implementation. #61724 needs long null heads; #51333 needs repeated same block/hash registration. Current seq64/rank is smaller than the source high-concurrency profile.

## Isolated control and treatment

A versus #61724; separately A versus #51333. Combine only individually confirmed fixes in a later integration arm.

## Evaluation and predicted mechanism

E1: native agent-f75; E2: frozen Mooncake median/burst/cache-heavy. H200 capacity discovery and held-out confirmation in PROTOCOL.md.

Measure: Scheduler CPU samples and step time; scanned entries; repeated registration count; GPU idle gaps; long-context TTFT/ITL and qualified goodput.

## Why an additional evaluation is or is not needed

Reuse E1/E2; stratify existing long-context requests. Only add long synthetic lengths through the existing driver if the frozen trace lacks this cohort. Upstream release/promotion/preemption tests guard cache correctness.

## Decision and falsification

Apply [the preregistered protocol](../PROTOCOL.md). Confirm path and missing behavior before spending GPU time. Support requires correctness, predicted mechanism movement and a useful held-out SLO outcome. Reject an active, well-measured change with no useful endpoint gain or a correctness/tail regression. Mark absent-path, underpowered or failed-replay cases inapplicable/inconclusive; do not label them disproven. Correctness lanes establish only scoped correctness.

## Evidence limits

Low applicability at short contexts or GPU-bound high load; do not credit faster Python code as a frontier improvement.
