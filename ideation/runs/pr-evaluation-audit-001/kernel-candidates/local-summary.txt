61039 [Perf][DSv4.1] Length-aware candidate block selection in the decode indexer STATE merged 2026-10-14T20:15:59Z HEAD 5e952d607749297e28d96050e2023fc3a6295b5f 
 ## Purpose

DeepSeek-V4.1's decode indexer writes its logits into a `[rows, max_model_len]` buffer, a width that must stay static for CUDA graphs (1M with the default `max_model_len`). Each row only holds its own context, but `select_candidate_blocks` scored every block of the full width and then ran `torch.topk(2048)` over all of them. At 1M that costs about 850 us per decode step, whatever the actual context length. This PR makes candidate selection length-aware.

- **Score only valid blocks.** `_block_scores_kernel` now runs a fixed `(rows, 32)` grid that walks each row's tiles only up to the row's end, and it writes each row's valid block count.
- **DeepSelect instead of `torch.topk`.** On the DeepSelect path, the block count is passed as DeepSelect's per-row `end`. Short rows are padded with -1. Candidate order does not matter, because the sparse expansion sorts. The full-width `torch.topk` path stays as the fallback for no DeepSelect, non-contiguous output, `topk > 4096` and narrow logits, and its behaviour is unchanged.
- **NaN rows.** DeepSelect leaves NaN rows only partly written, which can happen during warmup or capture on an uninitialized KV cache. On the DeepSelect path, NaN blocks are pinned like the newest block, as `torch.topk` ranks NaN first. NaN rows therefore still get complete, in-range candidates.
- **bf16 decode logits.** The decode indexer now asks DeepGEMM for bf16 logits when the top-k backend is `deep_select` and DCP is off. This halves the bytes that the top-k and candidate passes read. The logits kernel still accumulates in fp32 and only rounds the output, which is byte-identical to `bf16(fp32 logits)`. The other top-k backends and the DCP merge still get fp32.
- **Footprint.** `candidate_blocks.py`, the decode call in `sparse_attn_indexer.py`, and a `logits_dtype` passthrough on `fp8_fp4_paged_mqa_logits` (default fp32). The DeepSelect availability check reuses `has_deep_select()`.

## Kernel microbenchmark

`select_candidate_blocks` alone, DeepSeek-V4.1-Flash decode shapes: 384 rows (64 requests x 6 tokens), logits width 1,048,576 (default `max_model_len`, ratio-1 candidate-source layer), 2048 candidate blocks of 8. 1 x GB300, FlashInfer CUPTI timing with CUDA graph replay and cold L2, median. ## Details

`combine_topk_swa_indices` writes `[0, combined_len)` of each row and relies on the rest being `-1`, which `topk_length` pairs with. The `out=None` branch gets that from `torch.full(-1)`; the `out=` branch does not seed it. Both NVIDIA callers pass a workspace slice (`flash_mla_mega_attn.py` prefill, `flashmla.py`), so the tail holds whatever an earlier user of the arena left there.

The FlashMLA prefill kernel processes the index list in whole `B_TOPK` tiles (the reason for the 128 alignment) and still loads the KV rows of a tile's entries past `topk_length`, masking them to p = 0. A stale in-range index that lands on a `kv_ws` row this call did not write brings in arbitrary bytes, and 0 * NaN = NaN, so the masked entry still poisons the output row. Rows with a short window are the ones with a tail: at layer 0 (width 128) a fresh prompt's positions 0-126; in compressed layers (width 640) every row with fewer than 512 top-k candidates or a window shorter than 128 (for example right after an SWA bounded-replay start).

62467 [Bugfix][Kernel] persistent_topk: don't select float4 tail lanes past the row length STATE merged 2026-10-19T16:13:56Z HEAD ee1aff3e875caadf5d5e32ef1be55e7e6409dfb5 
 


## Overview

FIX #62466

`histogram_2048_topk` in `csrc/persistent_topk.cuh` can return indices `>= seq_len`. This happens when the row length is not a multiple of 4 and the top-k threshold lands in the fp16 `-inf` bin. This PR skips lanes past `seq_len` in the collection loop and adds a regression test.

## Claims

- `persistent_topk` no longer returns indices past the row length on the `histogram_2048_topk` path (k < length <= 8192, at most 32 rows).
- The out-of-bounds reads of `logits` in the refinement pass are gone.
- Rows with length % 4 == 0 and rows whose threshold is above the `-inf` bin are unchanged. The guard only drops lanes that were never real elements.

## Validation

GPU: NVIDIA B300 SXM6 AC (sm_103), CUDA 13.0, torch 2.14.0+cu130. `_C_stable_libtorch` rebuilt from this branch; main measured with the precompiled wheel for 3e96f9cf6.

## Details

Root cause. The last float4 load of a row (`load_float4_predicated`) fills the lanes past `seq_len` with `-inf`. They are binned like real elements. The collection loop gates candidates only on `vec_valid = i < n_vec`. When fewer than k in-row scores are above the `-inf` bin, the threshold is that bin, so the tail lanes become "equal" candidates. Refinement then reads `logits[idx]` for them and can output them.

Fix. Add `in_range = vec_valid && elem_idx < seq_len` and use it for `is_above` and `is_equal`. Tail lanes still count in the histogram, but that does not move the threshold. They only add to the `-inf` bin, the lowest non-NaN bin, so the counts above it are unchanged. And since `seq_len > k`, the in-row elements alone already reach k at the `-inf` bin.

Reachability, and why there is no end-to-end repro. The kernel path needs a decode row with k < length <= 8192, at most 32 rows, and the persistent backend. The persistent backend is picked by `--sparse-indexer-topk-backend persistent`, by `auto` on SM12x and pre-SM90 GPUs, or by `auto` when the logits row stride is not divisible by 4. The bug also needs fewer than k in-row scores above the fp16 `-inf` bin. I checked every in-tree caller:

- DeepSeek V3.2 / GLM-5 style DSA decode (`sparse_attn_indexer`): in-row scores come from `fp8_fp4_paged_mqa_logits` and are finite. Prefill uses `top_k_per_row_prefill`, not this kernel.
- Qwen4-exp QSA: scores are sums of ReLU terms, so they are finite and >= 0.
- Step5 rejects the persistent backend.
- DeepSeek V4.1 `apply_candidate_mask` does write `-inf` inside decode rows. But the shipped DeepSeek-V4.1-Flash config keeps 2048 candidate blocks of 8 tokens (16384 positions) on full-length (`compress_ratio` 1) layers. Every row on this path (<= 8192) is therefore fully covered.

So no shipped model reaches the bug with default or near-default flags. Reaching it needs a config with `candidate_topk_blocks * candidate_block_size < index_topk`, or more than `length - k` scores at or below about -65504. The layer-level script in the issue shows the V4.1 composition (`apply_candidate_mask` then `SparseIndexerTopk("persistent")`) with such a candidate set. If the bug were hit, `triton_convert_req_index_to_global_index` only drops `tok < 0`, so the result would be wrong KV slots with no error.

`cooperative_topk`, `histogram_256_topk` and the radix path are not affected. I checked lengths 8193 to 70001 with all-`-inf` rows on main and saw no bad indices.

Performance: one extra compare per element in the collection loop. No measurable change expected; not benchmarked.

58818 [Perf][DSv4.1] Share the FlashMLA decode plan across KV cache groups STATE open None HEAD 0457e961490be6234aac531a76e40859874f9813 
 ## Purpose

`DeepseekSparseSWAMetadataBuilder.build()` creates one empty `FlashMLASchedMeta` per DeepSeek-V4 layer type. The first `flash_mla_with_kvcache` call of each type runs FlashMLA's tile-scheduler planner, and the later layers of that type reuse the plan (the comment calls it "shared across all ~60 layers of that type within a decode step").

However, the builder runs once per KV cache group. With the packed KV cache layout, DeepSeek-V4.1-Flash's sliding-window caches are spread over 8 groups, and each group builds its own holders. So the planner runs once per (group, layer type). A torch-profiler trace of one TP8 decode step shows 18 planner launches in the target model (before layers 0-9 and 20-27) and 3 in the DSpark drafter (one per draft layer), where 4 are enough.

`get_mla_metadata_kernel` is a single 32-thread block with a serial loop over the SM partitions, and every launch sits in front of its layer's attention. On H20 it takes 16.6 µs per launch at 1 request and about 41 µs at 64 requests.

A plan depends on the batch shape and on the values of the decode `topk_length` / `extra_topk_length`. FlashMLA's interface allows reuse only while those values stay the same, but it asserts only shapes and config. Across the KV cache groups of one metadata build pass the values do match:
- The SWA lengths come from the same query and sequence lengths, window, valid-token mask and `replay_start`. Each group builds the mask from its own slot mapping, but every sliding-window group writes each scheduled token, so the masks agree; `replay_start` is one tensor passed to every builder.
- The top-k lengths count the valid entries each index layer writes. Every decode top-k path fills the entries past a row end derived from `seq_lens` and `next_n` alone with -1 (for example `rowEnd` in `csrc/libtorch_stable/sampler.cu`), under the same valid-token mask. So each index layer of a compress ratio yields `min(rowEnd, topk)`.

That second point is also why a group's same-type layers can already share one plan today, though they take their top-k from different index layers.

This PR lets the groups share the holders:
- MRV2's `build_attn_metadata` passes one dict to every group's `CommonAttentionMetadata`, next to the existing `_token_to_req_indices_cache`.
- The sliding-window builder takes its plan holders from that dict, keyed by its block size, causality and index width.

What stays as before:
- Callers that do not pass the dict (the V1 runner, the draft metadata refresh of the autoregressive speculator) keep one plan per group.
- DBO micro-batches and the DSpark drafter build in separate passes, so they never share a plan.
- SM100 does not take this path: it defaults to FlashMLA mega attention, which does not use these plan holders.

Planner launches per decode step drop from 21 to 4.

**Duplicate check.** `gh pr list --repo vllm-project/vllm --state all --search` for `tile_sched`, `FlashMLASchedMeta`, `get_mla_metadata`, `tile scheduler` and `planner flashmla` shows no PR that shares the plan across KV cache groups.

Related: #58762 (RFC #58638) reuses Mamba/GDN metadata across KV cache groups in the same `build_attn_metadata` loop. This PR does the same for DeepSeek-V4's FlashMLA plans, which are built per group however many groups there are.

## Details

**Layout.** Upstream's V4.1 records used to put a page's data rows first and all its scale rows after. They are now interleaved, so token `i` sits at `i * 528` (512 fp8 values, then 16 UE8M0 scales) or `i * 288` (256 Bof e2m1 pairs, then 32 e4m3 scales). The writers (`fused_deepseek_v4_qnorm_rope_kv_insert`, `rope_quant_insert`, the MXFP8 quantize-and-insert in `cache_utils.py`) and readers (the Triton MXFP8 / NVFP4 gathers and the CuTeDSL dequant gather) only change their offsets. The V4.0 record (584 B, separate scale region) is untouched.

**Block stride.** The new decode kernels gather tokens with TMA as rows of a 2D view over the whole cache, so they require `k_cache.stride(0) % bytes_per_token == 0`. DSv4.1 packs every layer's page (SWA, compressed, indexer, compressor state) into one physical block, so each view's `stride(0)` is the whole block. `DeepseekV4SWACache` therefore takes `packed_block_stride_alignment`, and V4.1 sets it to `lcm(528, compressed record)`: 528 with `fp8_ds_mla`, 3168 with `nvfp4_ds_mla`. ### SM100 FP8 indexer

Every CUDA FP8 indexer writer already stores an exact power-of-two scale `2^ceil(log2(amax/448))` per 128-wide token. On SM100 (`mqa_logits_use_mx_scales()`) the writers store that scale's exponent as four equal UE8M0 bytes instead of the fp32, which is an exact MXFP8 encoding of the same values (same cache size, same FP8 bytes):

| Writer | Models |
|---|---|
| C++ `indexer_k_quant_and_cache` (`scale_fmt="mxfp8"`) | DeepSeek-V2-class `Indexer` (V3.2 via that class, DeepSeek MTP), HY-V4, DeepSeek-V3.2 under PCP |
| DeepSeek-V3.2 fused norm/RoPE (`_fused_norm_rope_kernel`) | DeepSeek-V3.2, GLM-5/5.2 (`GlmMoeDsa`), Dots3Note, V3.2 MTP |
| DeepSeek-V4 compressor (Triton; the CuTeDSL compressor is head-512 MLA only) | DeepSeek-V4 |
| DeepSeek-V4.1 `indexer_k_norm_rope_store` | DeepSeek-V4.1 |
| GLM-5.3 kpool prefill compress + decode update | GLM-5.3 |

Readers need no change: `cp_gather_indexer_k_quant_cache` (prefill, all of the above) and the DCP/PCP gathers copy the 4 scale bytes verbatim, and DeepGEMM reads the paged cache directly. The 512-wide MLA caches, MXFP4 caches, and the MiniMax-M3 / Qwen4 indexers are untouched.

FP8 Q keeps folding its per-(token, head) power-of-two scale into `weights`; `mqa_logits_mx_inputs` passes unit MX Q scales (exact, since `relu(s·x) = s·relu(x)` for `s > 0`) and casts weights to BF16. The BF16 logits are upcast to FP32 for the existing FP32-only top-k kernels (`as_fp32_logits`); routing BF16 logits straight to a BF16-capable top-k (DeepSelect / LiteTopK, #59921/#59922) is a follow-up.

SM90 and SM120 keep the FP8 format, FP32 weights and FP32 logits. Consequently the FP8 indexer cache's scale bytes now differ between SM100 and other architectures: moving that KV cache between SM100 and non-SM100 nodes (cross-generation PD disaggregation, shared KV offload) is not supported for these models. Same-architecture setups are unaffected.

## Details

The receive buffer was `torch.empty_like(rows)` in each forward, from the caching allocator. 62091 [Perf][DSv4.1] Read GPU Engram tables from peers' HBM instead of DP collectives STATE open None HEAD eb6ec5f6f88758c0838bb5352ff5967ba707345f 
 ## Purpose

With `cpu_offload: false`, DeepSeek-V4.1's Engram tables live in HBM, but every lookup still goes through DP collectives: a pynccl `all_gather` of the hash ids and an `all_to_all_single` of the rows on the node-local `edp` group. Decode runs in FULL CUDA graphs, which do not honor `eager_break_during_capture`, so these collectives are captured next to MegaMoE's cross-rank kernels. In DEP decode on GB200, every rank then blocks in `graph.replay()` of the same decode graph at the first real step (seen with `CUDA_LAUNCH_BLOCKING=1`); host-offloaded tables, with no NCCL in the graph, never hang. I did not pin down the exact NCCL/MegaMoE interaction. This PR removes the collectives instead: GPU tables are row-sharded over the Engram DP group in symmetric memory, and each rank looks up only its own tokens, reading every row from the owning peer's HBM. Lookups need no collective, barrier or graph break.

* **Kernel.** `_engram_lookup_kernel` gains `PEER_ROWS`. With it, `weight` is a per-rank pointer table: a row's owner is `id // PEER_ROWS`, and its scales follow the rows in the same symmetric buffer. Tables are read-only after loading, so reads need no synchronization.
* **When.** `cpu_offload: false`, TP=1 and an Engram DP group (co-located DP replicas). The table sets `dp_size = 1`, as `dp_shared_memory` does, and `DeepseekV4Model` reads that to skip the hash gather and dummy hashes. Host tables keep `dp_shared_memory` / `EngramPeerExchange`, since symmetric memory cannot map another process's host memory.
* **Across nodes.** By default the group stays node-local. With `embedding_across_dp: true` (off by default), GPU tables are split over every DP rank, e.g. 1/32 of the table per GPU at DEP32; all DP ranks must then share one NVLink domain, as on GB200 NVL72. A group with the DP group's ranks reuses `_DP` instead of building a second communicator: a separate 32-rank group cost ~1.1 GiB/GPU and failed `gpu_memory_utilization=0.95`.
* **Not covered.** GPU tables with TP > 1 keep head sharding and its collectives. Peer mode stages BF16 rows per layer rather than `EngramBatch`'s packed MXFP8 rows, so `wkv` quantizes its own input; feeding packed peer rows to `EngramBatch` is a possible follow-up.

## Overview

## Details

**Root cause.** For `fp8_ds_mla` with fewer than `MIN_HEADS_FOR_BF16_PREFILL` heads per rank (`fp8_use_mixed_batch`), every step makes a single `flash_mla_with_kvcache` call with `s_q = num_tokens`. The wrapper pads q to 64 heads with `new_zeros`, and the kernel allocates `out`, `lse` and `o_accum`, all O(T * 64). The profile run skips attention, so none of this is counted when the KV cache is sized. At large `max_num_batched_tokens`, a full step therefore OOMs after startup.

**Fix.** `__init__` already reserves `(max_tokens, padded_heads, 576)` and `(max_tokens, padded_heads, 512)` bf16 workspace slots for the BF16 prefill path, which is not used in mixed-batch mode. `_fp8_flash_mla_kernel(use_workspace=True)` takes flat views of those slots sized for the FP8 decode padding (the reserved head padding is at least as wide). It zeroes only the padding heads and passes `out=` to the kernel.
- Only the mixed-batch caller turns this on. Pure-decode, HiSparse and separate prefill/decode callers keep the allocating path, because their T is small.
- The returned output aliases the workspace. It is consumed by the `v_up` projection or the DCP merge before any other workspace user runs. The separate prefill/decode path already returns workspace-backed output the same way.
- The q input comes from workspace slot 0, the q-concat buffer, so it doesn't overlap the padded-q slot.
- No new CPU/GPU synchronization: the added checks are host-side shape asserts.
- `lse` is still allocated by the kernel (T x 64 x 4 B = 8 MiB at 32K).

**Limitations.** The kernel-internal `o_accum` (2 x T x 64 x 512 x 4 B = 8 GiB at T=32K on SM90) is still allocated per call and isn't counted by the profile run. That is fixed in vllm-project/FlashMLA#29. This PR removes the wrapper-side share.

59327 [Perf][DSv4.1] Faster Engram host lookups: sorted rows, inline big lookups STATE merged 2026-10-01T03:54:45Z HEAD 24a50efaaee9ba5d9aacff6df79b7afb52935983 
 ## Purpose

Speed up DeepSeek-V4.1 Engram lookups from CPU-offloaded tables. On GB200 they are bound by GPU address translation, not bandwidth: each row misses the TLB on the small pages that back the table.

- **Sorted host lookups.** Large lookups from small-page host tables (pinned or `/dev/shm`) sort their rows by table offset, so neighboring rows share page walks. THP tables skip it, and so do lookups below the sort threshold.
- **Inline big lookups.** From the inline threshold (tokens, max over DP ranks), the lookup runs on the main stream at full width instead of the prefetch stream. Persistent main-stream kernels (MegaMoE, mHC, block-scaled GEMMs) cannot co-reside with lookup CTAs, so a background lookup stalls them anyway, and EP collectives then wait on the slowest rank.

`_engram_lookup_thresholds` picks both thresholds per GPU family: 36864 rows and 4096 tokens on Blackwell (measured on GB200). Other GPUs, including ROCm, keep both paths off and behave as before.

All Engram logic now lives in `common/engram.py`, so NVIDIA and AMD share one implementation and `nvidia/engram.py` is removed.

Also fixed along the way:

- DP replicas share the tables only if `/dev/shm` has enough free space (it used to check the total size). The Engram DP leader decides and broadcasts, so replicas always agree, and peers do not hang if the space query raises.

59923 [Perf][DSv4.1] Exchange packed FP8 Engram rows across DP and feed wkv MXFP8 STATE merged 2026-10-09T07:30:18Z HEAD 4f6745cd95e710360392079c0e997a0cf7ba38b7 
 ## Purpose

DeepSeek-V4.1's Engram tables are already MXFP8 (FP8 rows with one ue8m0 scale per 32 values) and `wkv` is an MXFP8 GEMM, but the lookup dequantizes each row to BF16, DP replicas all-gather those 512-byte rows layer by layer, and `wkv` quantizes them right back. - **Packed rows, direct MXFP8.** The lookup copies each row's 256 FP8 bytes and 8 scale bytes as they are, and one unpack kernel writes them in FlashInfer's MXFP8 activation layout (F8_128x4 scales). `wkv` takes them as a `QuantizedActivation`, so both the dequant and the requant are gone, and the output is bit-identical.
