Purpose

Partial mitigation for #52463: the tie-break rotation added in #47420 degrades prefix-cache locality for multi-turn / shared-prefix traffic under the internal DP load balancer. Consecutive turns of one conversation are tied decisions at low load, so they rotate across DP ranks and every turn misses the prefix its previous turn cached.

This PR remembers which engine served a prompt's first-block prefix (LRU of 16k entries, keyed on cache_salt + LoRA id + first block_size prompt token ids) and prefers that engine only when scores tie:

  • Load-aware decisions unchanged — a lower-scored engine always wins.
  • Unrelated tied requests still rotate — [Core][DP] Rotate load-balancer tie-break to avoid systematic engine bias #47420's fairness fix is preserved (regression-tested).
  • Explicit data_parallel_rank and late-interaction routing bypass affinity, unchanged.
  • Stale entries from elastic-EP scale-in are discarded; sub-block prompts (which cannot hit the cache) are exempt.

Test Plan

  • tests/v1/engine/test_dp_lb_prefix_affinity.py — 8 CPU-only unit tests driving get_core_engine_for_request directly: session stickiness across turns, tied-unrelated rotation preserved, load-beats-affinity, sub-block exemption, cache_salt separation, explicit-rank bypass, scale-in staleness, LRU bound.
  • Hardware A/B on 8×H100 (DeepSeek-V4-Flash-0731, DP=4+EP, --api-server-count 4, fp8 KV, aiperf mooncake trace designed for 81.7% prefix reuse — full methodology in [Bug][DP] Tie-break rotation from #47420 degrades prefix-cache locality for multi-turn traffic under internal DP LB #52463): identical runs, only this patch differs.

Test Result

Unit: 8/8 pass (run inside vllm/vllm-openai:nightly image).

* hit rate unchanged while throughput moved — consistent with run-to-run variance at 160 requests/level, not a cache effect; happy to re-run if reviewers want more samples.

Known limitation (why this is a mitigation, not the full fix): with --api-server-count N each frontend process has its own client and affinity map, and SO_REUSEPORT spreads one session's connections across processes — client-side affinity only sees its own process's requests (this bounds the c=1 recovery at 61.5% vs 81.6% measured on v0.23.0, a pre-#47420 release — a version-level baseline, not a single-commit revert of #47420). The complete fix needs prefix-awareness at a shared layer (DP coordinator or a shared affinity table); #52463 is the home for that design discussion.
