# X03 — Evaluate KV offload as a separate cache-capacity configuration

Lane: **exploratory**. Live-layout priority: **not ranked**. Status: conditional plan; no GPU test or measured gain.

## Problem and causal hypothesis

A larger reusable KV working set could avoid recomputation under cache pressure if transfer cost is lower than repeated prefill.

## Applicability to our H200 deployment

No KV offload tier is enabled in observed command. Prove cache pressure, compatible DSpark group ownership, save/restore lifetime and transport availability first.

## Isolated control and treatment

A: current GPU-only cache. B: one qualified offload connector with explicit dependency set and fixed host budget. Compare alternative restore paths independently.

## Evaluation and predicted mechanism

E1: native agent-f75; E2: frozen Mooncake median/burst/cache-heavy. H200 capacity discovery and held-out confirmation in PROTOCOL.md.

Measure: GPU versus host hit tokens; transfer bytes/latency; eviction/recompute; host memory; acceptance and TTFT tails.

## Why an additional evaluation is or is not needed

Existing cache-heavy replay tests benefit. Add eviction/restore, cancellation and stale-KV fixtures because ordinary warm traces do not prove connector correctness.

## Decision and falsification

Apply [the preregistered protocol](../PROTOCOL.md). Confirm path and missing behavior before spending GPU time. Support requires correctness, predicted mechanism movement and a useful held-out SLO outcome. Reject an active, well-measured change with no useful endpoint gain or a correctness/tail regression. Mark absent-path, underpowered or failed-replay cases inapplicable/inconclusive; do not label them disproven. Correctness lanes establish only scoped correctness.

## Evidence limits

Engram CPU offload is unrelated to KV offload. Mooncake workload does not itself activate a connector.
