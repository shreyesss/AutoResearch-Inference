# Evaluation v2: design for approval

**Status: proposed, not implemented.** This is the next campaign protocol for the pinned Qwen3.8-27B / one RTX PRO 6000 / vLLM 0.28.0 study. It does not alter the qualified `fixed-four-v1` campaign or reinterpret its historical cells. The rsynced source folders remain untouched.

## Decision in one page

| Question | v2 decision |
| --- | --- |
| What does the agent optimize? | vLLM serving configuration. AIPerf traffic settings remain controlled evaluator variables. Until application SLOs are supplied, report a throughput–latency tradeoff and do not claim SLA capacity. |
| What is the ordinary iteration? | One frozen, mixed, open-loop **development** task with chat/agent/document/code labels. A short matched screen rejects obvious failures; promising configurations receive longer or independent development windows. Keep the four OPS4 tasks as mechanism diagnostics for survivors. |
| What is adaptive? | Separately sweep **offered rate** on B0 and finalists to map throughput–latency curves. AIPerf selects load points; it does not change the server. Before SLOs this is exploratory. Once SLOs exist, estimate and independently confirm an SLA boundary. |
| What is the final decision? | A predeclared finalist and matched B0 on a physically isolated test stream, with class-specific latency and error results, uncertainty, and complete request accounting. Test inputs/results are unavailable to the proposer until selection is frozen. |
| What does the human see? | Every proposed configuration and sampled load point, including failures and dominated points; p50/p90/p95/p99, throughput, error, queue, lag, drain, timing cost, raw requests and telemetry; compatible-load Pareto plots and rate curves. |

## Why we are changing the evaluator

The current four-task candidate took 2,744 seconds: 1,350 seconds starting four servers, 1,181 seconds of benchmarking and 202 seconds of warmup. It measures 307 short-chat, 27 agent, 18 document and 36 mixed requests per configuration on exact frozen schedules. Its frontier uses 12 point-estimate coordinates: output tokens/s, TTFT p99 and TPOT p99 on each task. It already exports p50/p90 and raw records, but has no active fast gate, capacity search, independent test stream or uncertainty-based promotion. A 36-request mixed repeat took 763–792 seconds including startup. The observed p99 change for the 4,096-token-budget candidate was driven largely by one document-shaped request, so a similar repeat on the **same** schedule is not new content evidence. See [recorded results](results/2026-10-18-research-reset/README.md) and [evaluation audit](infra/OPS4_EVALUATION_REDESIGN.md).

AIPerf can choose benchmark rate/concurrency points and repeat each point. The installed 0.13 `bayesian` preset currently falls back to Optuna TPE without optional BoTorch. It has one-dimensional SLA boundary planners and stores the complete trajectory in `search_history.json`. It **does not choose a statistically sufficient request count, fix invalid dispatch, fit vLLM settings, remove server startup, or certify a capacity boundary from its selected in-sample point**. The live two-point, 12-request smoke demonstrated client-throttled dispatch and enormous latency distortion. See [local audit](infra/AIPERF_ADAPTIVE_FINDINGS.md) and [AIPerf 0.13 reference](https://github.com/ai-dynamo/aiperf/blob/v0.13.0/docs/sweeping/bayesian-optimization.md).

## Workload, sampling and SLO contract

1. Version the development mixed stream's source YAML, class weights, generated bodies, tokenizer, output policy, seed, arrival recipe and hashes. Its present 45/20/15/20 weights are engineered, **not** production frequencies. Keep each request's class label; an aggregate mixed p99 cannot stand in for class-specific behavior. Freeze a distinct test stream using new content and arrival seeds. Existing visible OPS4 assets cannot be relabelled as an untouched test.
2. For a matched server-setting comparison, use the same frozen bodies, timestamps, output rules, cache state and protocol on B0 and the candidate. Alternate B0/candidate order across independent windows to limit time drift. Do not compare points at different load as causal evidence for a server knob.
3. For capacity characterization, use one fixed request corpus/distribution while varying **arrival rate** with a high enough AIPerf client concurrency cap that the client does not throttle it. Store both planned and actual dispatch. The rate sweep necessarily changes timestamps; independently frozen schedules at selected rates provide confirmation.
4. Make sample count (`--request-count` or a bounded duration), trial repeats (`--num-profile-runs`), search iterations and seed explicit in the versioned protocol. AIPerf controls these quantities; it does not infer their scientific adequacy. Use a 36-request screen only for accounting, boot, severe regression and mechanism visibility. Set the longer window and repeat count from measured B0 variability and the intended percentile precision. At current 0.1 request/s, 300 mixed requests require roughly 50 minutes of dispatch and give only about 45 document requests; we must not promise a fast, reliable document p99 from that mix.
5. The user will supply application TTFT/TPOT deadlines. Record for each class: deadline, percentile or attainment fraction, offered load, output-length policy, observation window and error allowance. B0 observations are feasibility evidence, not the SLA. Before deadlines arrive, label results `exploratory` and plot measured tradeoffs. For context, B0 short-chat TTFT p50/p90/p99 was 178/245/310 ms at its current load; document was 5.71/7.26/8.37 s, with only 18 requests. No target is invented by rounding these values.
6. Treat p50/p90/p95/p99 as measurements with denominators and uncertainty. TPOT is a per-request decode interval statistic, distinct from aggregate output tokens/s. For a 99% attainment claim with zero breaches and independent requests, about 299 requests **per class** are needed merely for a one-sided 95% binomial bound; temporal correlation raises the effective requirement. Use multiple windows and report intervals rather than letting a tiny sample p99 become a pass/fail SLA claim.

## Evaluator stages and promotion

| Gate | Work and expected wall time | Decision / evidence grade |
| --- | --- | --- |
| 0. Static | Validate typed domain, resolved effective flags, compatibility, duplicate configuration, input/model pins. No GPU. | Reject invalid proposals before deployment. |
| 1. Fast matched development screen | Fresh-start mixed task, current measured reference ~13 minutes per cell, 36 requests. | Full accounting, clean dispatch, no errors, bounded queue/drain; reject only clear regressions outside B0 repeat variation. **No tail or capacity claim.** |
| 2. Replicated development | Independent mixed seed/window(s), matched and interleaved B0, larger predeclared sample budget. | Compare per-class effects and run-to-run intervals; promote plausible tradeoffs. Stop early only for validity failure or a predeclared severe degradation, never for an apparent small p99 gain. |
| 3. Mechanism diagnostics | The existing chat, agent, document and mixed tasks for survivors; optionally a same-server bundle **after** cache/order qualification. Current fresh-server suite reference ~46 minutes. | Explain which request shape benefits or regresses. Preserve every task metric and request record. |
| 4. Load curve / capacity | On B0 and selected finalists, AIPerf probes rate with clean warmup and bounded requests per trial. Before SLOs, make an exploratory throughput–latency curve using a predeclared rate range and budget. After SLOs, replicate near the candidate boundary; prefer 1D monotonic/isotonic search for an approximately monotone boundary, and compare BO/TPE for broader tradeoffs. | Store **all** sampled points. A planner's best point is provisional; check backlog, realized rate and uncertainty. Only a confirmed SLO-boundary result is called capacity. |
| 5. Sealed test | Freeze finalist choice; run new content/arrival stream for B0 and finalist(s) at predeclared fixed load and, if relevant, independently selected capacity-confirmation rates. | Only this stage can support a held-out finding. Report class-specific attainment, intervals and full costs; fail closed on missing requests. |

Actual cost is a design acceptance measure, not a promise. A single 13-minute screen can save time only when it correctly rejects weak proposals. Longer windows and adaptive capacity search add GPU time for the proposals that survive. We will measure total cost per useful, confirmed finding and false-rejection risk, not only per-cell runtime.

## Measurement, profiling and visible output

For each trial persist: campaign/protocol/config/seed/content hashes; configured and realized RPS; planned/sent/completed/failed/censored counts; output tokens/s and requests/s; per-class TTFT, TPOT and end-to-end p50/p90/p95/p99 with eligible `n`; per-request SLO attainment once defined; scheduled-versus-actual dispatch lag; queue peak and time series, backlog/drain; GPU memory/utilization; KV/cache/MTP metrics **when present**; startup/warmup/traffic/shutdown times; AIPerf raw exports and `search_history.json`; vLLM logs and resolved launch settings. Missing counters say `unavailable`, never zero. Use targeted profiles only when they can test a stated mechanism; retain profile overhead and source.

Generate an inspection index, trial table, load curves for **every** sampled point, and per-class latency/throughput plots with repeat uncertainty. Show dominated, infeasible and invalid points. A small selected objective set may drive optimization, while p50/p90/p95/p99 and diagnostic metrics remain visible; adding every percentile as a Pareto axis would make the frontier hard to interpret. Define goodput explicitly as successful work meeting the chosen per-request deadlines per wall-clock second, and keep error/attainment constraints separate. No composite score without an approved contract.

Use B0 to test the *feasibility* of user-supplied targets, then refine the service contract. For example, B0 short-chat TPOT p90 of 54.3 ms/token corresponds to roughly 18.4 output tokens/s for that per-request statistic; an approximately 256-token response therefore spends many seconds decoding. Measure actual end-to-end latency rather than adding separate percentile values. The service owner decides whether that experience is acceptable. A target can be tighter than B0 if the research must improve it, but the initial state should be marked infeasible rather than quietly relaxing the target.

## Serving search and agent changes

The active five axes are `max_num_seqs`, `max_num_batched_tokens`, `gpu_memory_utilization`, prefix caching and MTP depth. Widen through a new versioned domain and matched B0, with conditional branches for scheduler/prefill controls, explicit KV budget or precision, hybrid Mamba cache behavior, and execution/graph controls. Do not treat memory fraction and explicit KV bytes as independent, or enable a control without workload evidence and a pinned-runtime boot check. Precision and source/kernel changes need separate answer-quality/correctness gates. [Search expansion analysis](infra/SEARCH_SPACE_EXPANSION.md).

The agent's single skill will be revised **after approval** to read B0 variation, all load points, class-specific diagnostics, validity and cost; state a mechanism, predicted metric/diagnostic change and falsifier; request targeted evidence where supported; and decide whether a candidate merits a deeper gate. It may inspect the filesystem and research the pinned runtime, but cannot edit evaluation policy, hidden test inputs, server commands or frozen loads. The controller records all proposals and outcomes. Add an outer mixed-variable BO/random/local-search comparator on the same server-setting domain and GPU budget; AIPerf's optimizer remains the **inner traffic** search. This tests whether agent research adds value beyond tuning a small numeric grid.

## Build acceptance checkpoints after approval

The build can use three parallel workstreams with separate files and one integration owner: **evaluator/AIPerf** (trial controls, validity, adaptive history), **serving domain/runtime** (typed conditional flags and resolved configuration), and **agent/reporting** (skill, evidence index, complete point tables and plots). Workload/versioning and the matched v2 B0 protocol are shared contracts, so integration starts by fixing those contracts before any stream launches a GPU experiment. Real GPU trials remain serial under one lease. The first reviewable implementation milestone is the static contract plus one matched mixed B0/candidate fast gate; adaptive capacity and sealed test follow only after that gate's actual speed and noise are inspected.

1. Version v2 protocol/domain/workloads and show the user the exact frozen dev/test manifests and B0 identity before GPU search.
2. Implement trial-level accounting and search-history ingestion; reproduce the known two-point smoke as **invalid for capacity** because of dispatch/client constraints.
3. Implement the one-task matched gate with a fresh B0; inspect wall time, phase breakdown, raw records and verdict. Verify a deliberately bad candidate stops, while a known near-flat candidate is not discarded on noisy p99 alone.
4. Run repeated B0 and one candidate on independent dev windows. Inspect variation, per-class metrics, costs and whether promotion decisions are stable.
5. Run a bounded exploratory AIPerf load curve on B0 with all points visible; after application SLOs arrive, test a declared boundary and confirm it on fresh traffic.
6. Test physical holdout isolation, complete ledger/report/Pareto output, agent evidence access and resume behavior. Only then open autonomous v2 search.
