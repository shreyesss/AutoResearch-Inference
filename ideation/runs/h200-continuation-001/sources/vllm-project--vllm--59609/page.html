Your current environment

Environment summary 
vLLM:    0.1.dev22318+gcb6458c5c (precompiled wheel, upstream main at cb6458c5ce)
PyTorch: 2.13.0+cu130
CUDA:    13.0

GPUs:    4x NVIDIA B300

🐛 Describe the bug

With --enable-eplb and num_redundant_experts=N > 0, DeepSeek V4 and V4.1 never load weights into the redundant slots of each MoE layer. Below, "redundant slots" means the N physical expert slots with ids n_routed_experts..n_routed_experts+N-1. They keep whatever the allocation held. EPLB routes about half of the tokens for logical experts 0..N-1 to these slots. Nothing errors or warns.

The cause is that DeepseekV4Model.get_expert_mapping calls fused_moe_make_expert_params_mapping(...) without num_redundant_experts, so the argument defaults to 0:

  • vllm/models/deepseek_v4/nvidia/model.py:1809
  • vllm/models/deepseek_v41/nvidia/model.py:1338

The returned mapping only contains physical expert ids 0..n_routed_experts-1. load_weights only passes the expert ids in this mapping to the weight loader (for mapping in expert_mapping: at vllm/models/deepseek_v4/nvidia/model.py:1723 and vllm/models/deepseek_v41/nvidia/model.py:1250), so the redundant slots are never loaded.

Scope: every --moe-backend outside MEGA_MOE_BACKENDS (vllm/config/kernel.py:160) is affected, including the default auto. The MegaMoE branch (deep_gemm_mega_moe and the FlashInfer MoE-EP backends) uses make_deepseek_v4_expert_params_mapping, which is a separate path and not part of this report.

Why the redundant slots receive tokens

EPLB's initial placement maps physical slot p to logical expert p % n_logical, so redundant slot n_logical + i should hold logical expert i. For each token, the router picks one of a logical expert's slots by hashing the token index modulo its replica count. With one redundant slot per expert, about half of the tokens for logical experts 0..N-1 go to the unloaded slot.

This happens in BaseRouter._select_experts, which calls _apply_eplb_mapping (vllm/model_executor/layers/fused_moe/router/base_router.py:300, defined at :203), which calls eplb_map_to_physical_and_record.

Inferred, not measured: later rearrangement steps copy weights between physical slots, so an unloaded redundant slot could also be copied into other slots.

Trigger without a GPU

from types import SimpleNamespace

from vllm.models.deepseek_v4.nvidia.model import DeepseekV4Model

n_routed, n_redundant = 4, 3
ffn = SimpleNamespace(use_mega_moe=False, n_redundant_experts=n_redundant)
fake = SimpleNamespace(
    config=SimpleNamespace(n_routed_experts=n_routed),
    layers=[SimpleNamespace(ffn=ffn)],
    start_layer=0,
    end_layer=1,
    named_parameters=lambda: iter(()),
)
ids = {expert_id for _, _, expert_id, _ in DeepseekV4Model.get_expert_mapping(fake)}
print(sorted(ids))
# main prints [0, 1, 2, 3]
# expected:   [0, 1, 2, 3, 4, 5, 6]

The same happens with vllm.models.deepseek_v41.nvidia.model.DeepseekV4Model. With n_redundant = 0 the result is correct.

Reproducer on GPUs

Save as minimal_repro.py and run with VLLM_ALLOW_INSECURE_SERIALIZATION=1 python minimal_repro.py (needs 4 GPUs). It uses the same config as the run described under "Observed on DeepSeek-V4.1-Flash".

import torch

from vllm import LLM


def replica_slots(worker):
    from vllm.distributed import get_ep_group
    from vllm.model_executor.models.interfaces import get_mixture_of_experts_model

    model = get_mixture_of_experts_model(worker.model_runner.get_model())
    # expert_weights: per MoE layer, tensors of shape [num_local_experts, ...]
    nonzero = torch.stack(
        [
            torch.stack(
                [(w.view(torch.uint8).reshape(w.shape[0], -1) != 0).any(-1) for w in layer]
            ).any(0)
            for layer in model.expert_weights
        ]
    )  # [num_moe_layers, num_local_experts]
    return get_ep_group().rank_in_group, model.num_logical_experts, nonzero.tolist()


def main():
    llm = LLM(
        "deepseek-ai/DeepSeek-V4.1-Flash",
        tensor_parallel_size=4,
        enable_expert_parallel=True,
        enable_eplb=True,
        eplb_config={"num_redundant_experts": 8},
        language_model_only=True,
        max_model_len=8192,
        kv_cache_dtype="fp8",
    )
    results = sorted(llm.collective_rpc(replica_slots), key=lambda r: r[0])
    nonzero = torch.cat([torch.tensor(r[2]) for r in results], dim=1)  # [layers, physical experts]
    n_logical = results[0][1]
    redundant = nonzero[:, n_logical:]
    print(f"redundant slots with all-zero weights: {(~redundant).sum()} / {redundant.numel()}")


if __name__ == "__main__":
    main()

Output on main:

redundant slots with all-zero weights: 320 / 320

The script counts all-zero slots because that is what an unloaded slot looked like here. The allocation is not initialized, so on memory that is not zeroed this count can be 0 even with the bug. In that case compare each redundant slot n_logical + i with slot i, as in the next section.

Observed on DeepSeek-V4.1-Flash

Setup: 384 routed experts, 40 MoE layers, 4x B300, TP=4 with --enable-expert-parallel, --enable-eplb, eplb_config={"num_redundant_experts": 8} (392 physical experts), default --moe-backend auto (selected the FLASHINFER_TRTLLM_MXFP4_MXFP8 Mxfp4 MoE backend), --kv-cache-dtype fp8, --max-model-len 8192, language model only.

I computed a per-slot checksum over all EPLB-managed expert weights (model.expert_weights):

  • All 320 redundant slots (8 per layer x 40 layers) differ from the slot holding the same logical expert.
  • Every redundant slot was 100% zero bytes. Source slots have about 0.35% zero bytes.

Zero-filled memory is what I observed. It is not guaranteed, since the allocation is not initialized.

Quality impact

The impact is small and easy to miss. Only 8 of 384 experts per layer have a replica, and only the share of their tokens sent to the replica loses that expert's output. GSM8K does not detect it. Setup as above, 250 test questions, 5-shot, greedy; rows differ only in num_redundant_experts and the fix:

Config GSM8K Replica slots that differ from their source
N=0, main 88.8% (222/250) none (no replicas)
N=8, main 88.8% (222/250) 320 / 320
N=8, with fix 88.0% (220/250) 0 / 320

Free-form greedy prompts showed it more clearly, though on a small sample. On main with N=8, two of four short prompts ("Write a Python function that returns the n-th Fibonacci number." and "Explain in two sentences why the sky is blue.") returned an empty completion. With N=0 and with the fix, all four returned normal answers.

Related

  • [Bug]: get_expert_mapping is inconsistent with load_weights for EPLB in DeepseekV2 and AXK1 #41920 / [Bugfix] Fix EPLB expert mapping for DeepSeekV2 and AXK1 #41930: the same missing num_redundant_experts in DeepseekV2's get_expert_mapping. There load_weights builds its own mapping with the redundant slots, so only BitsAndBytes and LoRA are affected. In DeepSeek V4/V4.1, load_weights uses get_expert_mapping itself, so the weights are never loaded.
  • [Model][EPLB] Add static expert maps for DeepSeek V4 #53022 changes the same function, but only for its static expert map path. It does not cover default runtime EPLB or V4.1.

Proposed fix

Pass the redundant expert count in both files. first_layer is already computed at the top of get_expert_mapping.

     num_experts=self.config.n_routed_experts,
+    num_redundant_experts=first_layer.ffn.n_redundant_experts,
 )

I will open a PR with this change and a unit test.
