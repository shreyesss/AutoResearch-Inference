[Perf][DeepSeek V4.1] Humming indexed MoE GEMM with EP on Hopper, and…
…
47e6dff
… a named MoE activation format

Humming indexed GEMM with EP on Hopper: for DeepSeek V4.1 (model_type
deepseek_v41 / deepseek_v41_text) MXFP4 experts on SM90, Humming now
picks the indexed GEMM also under expert parallelism, when there is no
all2all or the all2all is allgather_reducescatter. Other EP setups still
use grouped_contiguous. Humming is already the default MXFP4 MoE
backend on SM90 (
vllm-project#56997
), so this also changes the default path. On
TP8+EP, indexed is 47% faster at prefill and 63% faster at decode with
BF16 activations, and 24% and 36% faster with per-token FP8.
VLLM_HUMMING_MOE_GEMM_TYPE still overrides the choice.

Named MoE activation format: the DeepSeek V4 MXFP4 MoE selector now
honors --quantization-config.moe.activation, so per-token FP8 on Humming
is an explicit choice:

  --moe-backend humming --quantization-config.moe.activation fp8_per_token

- With --moe-backend humming, the format is checked before the weights
  load and then passed to the Humming conversion with schema fallback
  off. On SM90, mxfp8 is refused because WGMMA has no e8m0 input scales.
  Setting VLLM_HUMMING_INPUT_QUANT_CONFIG as well is an error. The env
  JSON alone works as on main.
- Another explicit backend that does not run the format fails, and auto
  keeps only the backends that run it. For example, fp8_per_token with
  flashinfer_trtllm no longer runs MXFP8 without saying so.
- The Kimi-K3 SiTU AITER path skips the selector and runs BF16 only, so
  it refuses a named format.
- The Humming MoE conversion logs the activation format it runs.
- user_moe_activation_override() is public and returns None when no
  vLLM config is set.

Without moe.activation, backend and activation selection are unchanged.
