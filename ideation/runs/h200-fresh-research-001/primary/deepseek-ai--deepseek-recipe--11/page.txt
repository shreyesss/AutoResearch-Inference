fix(v41): encode user content as plain BPE instead of matching control-token literals
When user content contains a literal such as
<｜User｜>
, the renderer
concatenates it with the template control tokens and encodes the whole string
in one pass, so the literal matches the corresponding AddedToken and is
smuggled into the prompt as a single control token. Token counts then diverge
from the official API:
<｜User｜>
counts as 5 in the recipe while the API
reports a 5-token increase, because the API BPE-encodes the literal as 5
ordinary tokens (
[30, 28217, 6756, 28217, 32]
).
This PR renders the prompt as template/content segments:
template segments (control tokens such as
<｜User｜>
,
<think>
,
<tool_result>
wrappers, tool-call markup) keep added-token recognition;
message content (system / user / assistant / tool / reasoning) is encoded
with an empty added vocabulary, i.e. as plain BPE.
render_conversation()
output is unchanged; only the
encode()
id path
changes. This also closes the control-token injection angle: user content can
no longer produce template control tokens.
