📌 Description

Adds the native BF16 twin of the SM90 (Hopper) pull-style CuTeDSL MegaMoE
backend: sm90_bf16_bf16_bf16_pull_cutedsl (BF16 activations, BF16 expert
weights, BF16 output; fused NVSHMEM dispatch + FC1 + SwiGLU + FC2 + combine
in one persistent kernel, WGMMA with fp32 accumulation). It is the kernel
team's moe_hopper_bf16 drop vendored next to the existing FP8
moe_hopper_fp8 drop, with the same shim / backend / test / bench layering as
sm90_fp8_fp8_bf16_pull_cutedsl.

What is in the PR:

  • Shim shim/hopper_bf16.py (MegaMoEHopperBf16Config / frontend / symm
    buffer / hopper_bf16_mega_moe), shim/tuner_bf16.py and
    shim/autotune_bf16.py (knob space, heuristic defaults, candidate sweep);
    the knob cache is shared with FP8 under dtype="bf16".
  • Backend backends/mega/kernel/sm90/bf16_bf16_bf16_pull_cutedsl/
    (Sm90_Bf16_Bf16_Bf16_PullCutedsl_MegaMoeConfig, staging = plain bf16
    copy, weights = gate/up 8-row interleave + K-major relayout, no
    quantization), registered in flashinfer.moe_ep, runtime requirements,
    python -m flashinfer.moe_ep.tune --dtype sm90_bf16.
  • Tests mirroring the FP8 set one-to-one minus the FP8-only axes
    (test_sm90_pull_bf16_{config,tuner,kernel_vs_reference}.py,
    test_moe_ep_sm90_pull_bf16_mega_multirank.py); run_tests.sh
    oracle_sm90 / mega_sm90 now cover FP8 and BF16.
  • Bench benchmarks/moe_ep/backends/mega/kernel/sm90/bench_moe_ep_sm90_bf16_pull_mega.py
    (BF16 twin of the FP8 token sweep), and docs (SKILL.md, TUNING.md BF16
    section with measured numbers, moe_ep_architecture.md, moe_ep_runbook.md).

Contract / differences from the FP8 backend: hidden % 256 == 0,
intermediate % 64 == 0, tile K = 64 (two-byte operands: the 128-byte swizzle
atom spans 64 elements), heuristic table keyed on tokens only, no
kind / fp8_scale_mode / fp8_accum_mode / dequant scales /
dedup_dispatch / grouped_token_back / combine_format knobs.

Performance

Three heuristic token sweeps with the benchmarks' default configuration
(DSV4-Pro P03 geometry: 384 experts, top-6, hidden 7168, intermediate 3072,
gate_up_clamp 10, load_balance_mode=atomic_counter, warmup 3 / 20 timed
iterations, 5 s cooldown per series, tokens/rank 8..32768), EP=4 on the same
4x H200 node with the SM clock locked at 1830 MHz:

torchrun --nproc_per_node=4 benchmarks/moe_ep/backends/mega/kernel/sm90/bench_moe_ep_sm90_mega.py --scale-mode both
torchrun --nproc_per_node=4 benchmarks/moe_ep/backends/mega/kernel/sm90/bench_moe_ep_sm90_bf16_pull_mega.py

Numbers are the compute series (bare MegaKernelBackend.compute(output=None):
fused mega kernel + standalone top-k reduce, zero-copy output), slowest-rank
mean per iteration; TFLOPS = FC1+FC2 FLOPs of one rank over that time
(2 * tokens * topk * hidden * (2I + I)). Each point runs the backend's
per-bucket heuristic launch config (FP8: swap-AB / non-swap M64N256 rows at
K=128; BF16: swap-AB rows at K=64).

  • Peak compute throughput per rank: FP8 per_tensor 994 TFLOPS, FP8 blockwise
    845 TFLOPS, BF16 553 TFLOPS.
  • BF16 delivers 0.53x the FP8 per_tensor TFLOPS (geomean over the 13
    buckets, range 0.49-0.57x) and 0.60x the FP8 blockwise TFLOPS (range
    0.52-0.80x). The ~0.5x against per_tensor is the expected ceiling: Hopper
    BF16 WGMMA peaks at half the dense FP8 rate and the bf16 dispatch wire
    carries twice the bytes per token, so both the GEMM-bound tail and the
    latency/bandwidth-bound head halve. Blockwise FP8 pays its per-block
    scale handling on 1024+ tokens (non-swap M64N256 rows at 600-850 TFLOPS),
    which is why BF16 closes to 0.63-0.80x there.
  • The FI compute path matches the kernel team's own BF16 harness
    (moe_hopper_bf16/run_token_sweep_benchmark.py, mega_us + topk_us) on
    the same node within +-2% at 512 / 2048 / 8192 / 32768 tokens (see the
    BF16 section of kernel_src/sm90/pull_style_cutedsl_megakernel/TUNING.md).
  • e2e (MoEEpLayer.forward) adds only 16-240 µs over compute for BF16
    (staging is a plain bf16 copy) versus 115-1100 µs for FP8 per_tensor and
    170-2900 µs for FP8 blockwise (torch-composed quantization staging).
