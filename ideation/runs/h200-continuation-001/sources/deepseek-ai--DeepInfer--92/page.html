Summary

DeepInfer currently runs on SM100 and Ascend 950. This PR adds an SM90 (Hopper) path so that DeepSeek-V4.1-Flash runs end to end on Hopper GPUs, validated on 8x and 4x NVIDIA H20-3e (141 GB):

  • same checkpoint, no conversion
  • attention DP / CP, MoE EP, DSpark
  • CUDA graphs on

Key design points:

  • The MXFP4 routed experts stay resident in FP4, so 4 GPUs are enough.
  • FlashMLA's last Hopper kernels (ba89a34) are extended to the V4.1 KV cache formats.

SM100 and Ascend behaviour is unchanged. Every SM90 path is selected by PLATFORM.is_sm90, and all new kernels live in deepinfer/model_executor/layers/sm90_ops/.

Results on H20-3e (details, settings and methodology below):

8x H20-3e 4x H20-3e
TTFT, 128K input (context parallel) 2.15 s 3.64 s
TTFT, 512K input 9.66 s 16.72 s
TTFT, ~1M input 22.2 s 38.5 s
Decode, 64 concurrent, 1024 in / 512 out, total tok/s 3793 2463
GSM8K (1319, 8-shot) 0.943 0.941

TTFT: one cold request at a time, median of 3, context parallel over all GPUs, NCCL all-gather overlapped with compute. Decode: random token ids, total output tok/s. The 8-GPU run uses the default prefill intervals; the only 4-GPU run used intervals 1 / 1. GSM8K: 8-shot completion, with the first 8 test questions as shots and all 1319 scored, as in SGLang's GSM8K harness.

A comparison with SGLang on the same hardware will follow in a comment.

Performance on H20-3e

All numbers come from examples/latency_benchmark.py, added in this PR, with these settings:

  • DSpark on: DEEPINFER_USE_NEXTN_DECODE=5, DEEPINFER_ENABLE_MTP_VARLEN=1
  • DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE=compact, DEEPINFER_YOCO_PREFILL_KEEP_TOKENS=140
  • CUDA graphs on

The TTFT prompts were code text from an earlier version of the prompt builder. The committed builder uses Python standard-library source instead, so it produces different token inputs.

TTFT, in seconds. One cold request at a time, median of 3 runs after 1 warm-up, prefill intervals set to 1.

The CP all-gathers use NCCL, the SM90 default. They were measured with DEEPINFER_CP_NCCL_OVERLAP=1, which overlaps them with compute. The default now waits for each all-gather at launch instead. 64 3793 (7.43 ms) 2930 (14.13 ms)

Why the two columns differ:

  • With intervals 1 / 1, every new request starts its prefill at once. DP ranks advance in lockstep, so the other ranks run slower decode steps meanwhile.
  • The default intervals batch those prefills. Under load, this cuts the median TPOT by 35–47%.
  • Profiling with 4K-in / 1K-out coding prompts puts the steady-state decode step at about 33–34 ms. The gap between the columns is prefill interference, not kernel time.

Notes for reviewers

  • Dependencies.
    • humming-kernels (PyPI, Apache-2.0) is imported lazily, only on SM90 and only by the humming / hybrid MoE backends. Without it, auto uses the pure-Triton triton_fp8 backend. That backend needs about twice the expert memory, so it fits at EP8 but not at EP4.
    • flash_mla_sm90 is built from a patch on FlashMLA ba89a34. I am happy to send the patch to FlashMLA instead.
    • The DeepSelect and DeepEP patches (SM90 builds only) are candidates for those projects.
  • Indexer numerics. The SM90 indexer follows the reference implementation's arithmetic, including an fp32 head sum. Its top-k picks can therefore differ from SM100 on near-ties.
  • Not ported. The SM100-only fused kernels (Mega MoE, mega_gate, mega_mhc, candidate-sparse MQA) are not ported; SM90 uses the existing non-mega paths.
  • Known gaps.
    • Single-request TTFT has a floor of about 0.19 s for prompts up to 8K tokens, because short prefills run eagerly and are bound by launch overhead.
    • On hosts where NVLink multicast works, setting NCCL_NVLS_ENABLE=1 lets CP use DeepEP's BucketBuffer. That was 3–5% faster than the default NCCL path at long context.
  • Open PRs touching the same code.
    • deep_cluster: add vendor registry and Biren discovery #60 (vendor registry) and Support SM90 (Hopper) GPUs in get_bf16_tflops_limit #88 change get_bf16_tflops_limit, as this PR does. If either lands first, I will rebase.
    • PLATFORM.is_sm90 is a capability flag on the existing GPU platform, not a new PlatformEnum member, in line with the direction in doc: RFC to finish the backend seam in deepinfer.platform and the build #63.
  • Not verified.
    • SM100 and Ascend were not run; I have no such hardware. Those paths are unchanged by construction, apart from the items listed above.
    • Hopper parts other than H20-3e, and multi-node runs, were not tested.
  • Follow-ups.
    • A DeepEP change that lets BucketBuffer all-gather without multicast. It is prototyped and bitwise-checked, but not included here.
    • A faster candidate-row indexer kernel.

Checklist

  • ruff check / ruff format --check (ruff 0.15.0) and scripts/format_csrc.sh --check pass
  • New tests under tests/; SM90-only tests skip elsewhere
  • Unit, numerics and end-to-end results on SM90 hardware

sm90_ops: add a block-[32, 32] FP8 GEMM for Hopper
12da8e7 
DeepGEMM's SM90 kernels take only 128-wide fp32 scales, so the V4.1 FP8
linears (32x32 UE8M0 weight blocks, 1x32 packed-UE8M0 activations,
recipe (1, 1, 32)) and the FP8-output wo_a einsum have no Hopper path.

Add a warp-specialized Gluon GEMM, originally written by the author of
this change as a swap-AB block-[32, 32] kernel for SM90 support of
DeepSeek V4.1 in SGLang (not yet upstream). It reads the packed int32
activation scales of
tile_kernels.quant.per_token_cast as they are and the checkpoint's fp32
32x32 weight scales, promotes each 32-wide K group in fp32 like
DeepGEMM's block32 recipe, and supports split-K, out += C, a grouped
mode for einsum("bhr,hdr->bhd") and an FP8 + packed-UE8M0 output
epilogue that matches the reference's bf16 einsum followed by
act_quant. Launch configs are tuned on H20-3e for every non-expert
V4.1 linear shape; other shapes and GPUs use a heuristic.
deterministic=True (split 1) makes each row independent of the batch
size. Split-K tile counters are passed in by the caller (one buffer per
weight, allocated outside CUDA-graph capture); a call without them
zeroes counters of its own, so concurrent calls never share them.

DeepInfer runs MXFP4 routed experts through deep_gemm's

host-side row-count hint (local tokens x top-k) that is only used to
pick tiles and kernels. EPLB shuffles the per-expert tensors that

FP8 activations raise at init on SM90.

deepinfer/environ.py):

- humming: humming-kernels (PyPI, Apache-2.0, validated with 0.1.12)

  kernel turns psum into humming's tile list on device, without a host
  sync, so the forward can be captured in a CUDA graph. humming
  re-rounds 32-groups whose exponent is more than 11 below their
  matrix's maximum; this is counted and logged once at init, and on

  GEMM; mainly a cross-check.

cp: fall back to NCCL all-gather without NVLS multicast
f68df48 
DeepEP's BucketBuffer creates its device communicator with
lsaMultimem whenever the group spans more than one NVLink rank, so
context parallelism aborts with "NCCL multimem is unavailable" on
systems without NVLink SHARP multicast or with NVLS disabled
(NCCL_NVLS_ENABLE=0, the SM90 default).

Add NcclCPBuffer, a stand-in for the subset of BucketBuffer that
CPManager uses: a session-scoped bump allocator over pre-allocated
storage (same alignment as BucketSession) and an all-gather on the CP
group's NCCL stream. A source that is this rank's shard of a
get_inplace_tensor region is gathered in place, any other source is
gathered into a fresh region without staging, and the wait callable
returns the token-concatenated view of the storage, so CPManager's
interface, aliasing and reuse contract are unchanged. The handle keeps
the NCCL work, so waiting orders whichever stream waits after the
collective.

Unlike BucketBuffer's copy-engine all-gather, NCCL's runs on SMs.
Overlapped with a GEMM that fills the GPU it slowed the GEMM by several
times the all-gather's own cost (rank kernels starved behind the GEMM
while peers spin), so by default the current stream waits for the
all-gather at launch; DEEPINFER_CP_NCCL_OVERLAP=1 defers the wait to
the callable instead.

DEEPINFER_CP_COMM_BACKEND=auto|bucket|nccl selects the backend. Off
SM90, auto is BucketBuffer exactly as before and its construction
errors propagate. On SM90 the CP group first all-reduces (MIN) a
per-rank multimem capability (NCCL_NVLS_ENABLE not 0 and CUDA
multicast supported) and takes the NCCL all-gather only when some rank
lacks it, so every rank picks the same backend before any buffer is
built. nccl is an explicit opt-in on any NVIDIA GPU.

tests/distributed/test_cp_manager.py checks bitwise results against a
reference for in-place, external, non-contiguous and FP8 sources with
several gathers in flight under rank skew and the CUDA sync guard, a
wait on a second stream, session reuse, error propagation on and off
SM90, the collective backend choice with one rank lacking NVLS or
multicast, both NCCL modes, and bitwise equality between the backends
where BucketBuffer can be built (skipped otherwise).

examples: add an offline latency benchmark
d9a9bae 
Add examples/latency_benchmark.py, which measures what a serving client
sees per request without an HTTP layer: it drives
LLMEngine.add_request / step on every DP rank in lockstep and times
each request from the host side. benchmark.py keeps measuring
steady-state step throughput.

Suites:
- ttft: one cold request at a time per input length (1K to 512K in
  powers of two plus ~1M by default; warmup + repeats), median TTFT
- single: sequential decode requests, per-request decode tok/s and TPOT
- concurrency: closed loop with C requests in flight (split evenly over
  DP ranks) after a discarded warm-up wave; total output tok/s, TPOT,
  TTFT
- gsm8k: few-shot completion (or one chat turn), greedy, accuracy, on
  a GSM8K JSONL file given with --gsm8k_data; questions used as shots
  are not scored unless --gsm8k_overlap_shots asks for the layout of
  SGLang's benchmark/gsm8k for comparisons

Throughput, TPOT and acceptance are computed from the tokens each
request actually emitted (golden-token draft_tok / accept_tok per
step), not from the full-acceptance step accounting of benchmark.py.
Prompts are token ids built before timing: exact-length coding prompts
in the checkpoint's chat format (realistic speculative acceptance) or
random ids. max_model_len defaults to the longest planned request, at
least 32768 and the model's candidate top-k minimum. Results go to one
JSON per suite (layout, DEEPINFER_* env, per-request records) plus a
Markdown summary; --commit records the source revision when the tree
has no .git.

The timing loop (_request_timing.py) is engine-agnostic;
tests/benchmarks/test_latency_benchmark.py tests it on CPU against a
simulated engine, including zero-overhead scheduling (outputs returned
one step late or by flush) and multi-rank lockstep, together with the
prompt builders, the GSM8K split and the max_model_len sizing.
