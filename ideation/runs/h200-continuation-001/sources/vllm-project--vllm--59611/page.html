Overview

Fixes #59609. With --enable-eplb and num_redundant_experts > 0, DeepSeek V4 and V4.1 never loaded the redundant expert slots. get_expert_mapping now passes num_redundant_experts, so load_weights fills those slots.

Scope: NVIDIA only. Only the NVIDIA V4 and V4.1 models allocate redundant expert slots; on ROCm, V4 builds its MoE layers without EPLB and V4.1 sets n_redundant_experts = 0.

Claims

  • On the FusedMoE path (every --moe-backend except deep_gemm_mega_moe, which already loads the replicas), redundant EPLB slots hold the weights of the logical expert they replicate. Before this change they kept uninitialized memory.
  • No change when num_redundant_experts=0.

Validation

DeepSeek-V4.1-Flash on 4x B300, TP=4, --enable-expert-parallel --enable-eplb, default --moe-backend auto (FLASHINFER_TRTLLM_MXFP4_MXFP8), --kv-cache-dtype fp8, --max-model-len 8192. "Replica slots that differ" compares a checksum of every redundant slot's EPLB-managed weights against the slot holding the same logical expert (8 slots x 40 MoE layers). GSM8K: 250 test questions, 5-shot, greedy.

Config Replica slots that differ GSM8K
N=0, main no replicas 88.8% (222/250)
N=8, main 320 / 320 (all zero bytes) 88.8% (222/250)
N=8, this PR 0 / 320 88.0% (220/250)

GSM8K is not sensitive to this bug: only 8 of 384 experts have a replica, and only the tokens routed to the replica lose that expert's output. Short greedy prompts show it more directly. On main with N=8, "Explain in two sentences why the sky is blue." ends at end-of-sequence as its first token (logprob -1.13 vs -1.63 for the runner-up). With this PR, " The" wins (-1.77) and end-of-sequence is second (-2.27).

The reproducer in #59609 prints redundant slots with all-zero weights: 320 / 320 on main and redundant slots with all-zero weights: 0 / 320 with this PR.

The new e2e test (below) fails on main and passes with this PR, run locally on 4x B300 with DeepSeek-V4-Flash:

Startup weight check GSM8K (1319 q)
main 344 redundant expert slots differ from their source (8 x 43 layers) not reached
this PR passes on all 4 ranks 94.8% 
cd tests && PYTHONPATH=.. pytest -s -v evals/gsm8k/test_gsm8k_correctness.py --config-list-file=configs/models-spec-decode.txt -k EPLB

Details

DeepseekV4Model.load_weights loads routed experts only through the ids returned by get_expert_mapping. That mapping was built with the default num_redundant_experts=0, so physical ids n_routed_experts..n_routed_experts+N-1 were never passed to the weight loader. EPLB's initial placement maps those slots to logical experts 0..N-1 and sends part of those experts' tokens to them.

DeepseekV2 has the same missing argument in get_expert_mapping (#41920, #41930). There, load_weights builds its own mapping with redundant slots, so only BitsAndBytes and LoRA are affected. In V4 and V4.1, load_weights uses get_expert_mapping directly, so the slots are never loaded.

Not changed:

  • deep_gemm_mega_moe uses make_deepseek_v4_expert_params_mapping, which is a separate path.
  • The ROCm V4.1 model sets n_redundant_experts = 0.
  • The MTP loader (deepseek_v4/nvidia/mtp.py) builds its mapping without redundant slots too. The drafter is not registered with EPLB, so its router never selects those slots. This is inferred from the code, not tested.

Test: the GSM8K harness gets an optional startup_rpc_checks config key. It calls each listed worker-extension method through /collective_rpc after the server starts and before any request. The check runs before traffic because EPLB rearrangement can move expert weights. tests/evals/gsm8k/eplb_checks.py checksums every expert slot, gathers the checksums across the EP group, and compares each redundant slot with the first slot of the same logical expert. GSM8K alone does not catch this bug: on V4.1-Flash it scored 88.8% on main and 88.0% with the fix. The new DeepSeek-V4-Flash-EPLB-TEP4.yaml (TP4, EP, 8 redundant experts) runs in the nightly ":nvidia: (B200) LM Eval Spec Decode" job. The check takes a few seconds; the config adds one V4-Flash cold start plus about a minute of GSM8K to that job.

The native MegaMoE path does not need the redundant ids in the mapping. make_deepseek_v4_expert_params_mapping returns logical ids only. DeepseekV4MegaMoEExperts.weight_loader then copies each logical expert to every local slot p with p % num_logical_experts == expert_id (_map_global_expert_id, deepseek_v4/nvidia/model.py). That is the same layout as EPLB's initial placement (build_initial_global_physical_to_logical_map), so the replica slots get their source weights.

I ran the new startup check with --moe-backend deep_gemm_mega_moe on 4x B300 (DeepSeek-V4-Flash, TP4, EP, 8 redundant experts), rebased onto main (7115b70c01), using the config from this PR plus that one flag.
