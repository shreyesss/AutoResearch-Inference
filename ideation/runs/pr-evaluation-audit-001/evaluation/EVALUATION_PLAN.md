# Evaluation plan: activation, internal evidence and final frontier

**Design only.** This document extends the [existing evaluation audit](EVALUATION_CAPABILITIES.md) and [common protocol](../PROTOCOL.md); it does not claim installed tools, successful GPU execution or a changed benchmark implementation. E1 is native `agent-f75`; E2 is AIPerf fixed-schedule Mooncake. Keep their historical dataset hashes and scorers. Use [mechanism cards](MECHANISM_CARDS.md) for PR-vs-agent provenance.

## 1. Per-candidate gated workflow

1. **Inventory:** attest actual image digest/source/flags, model and draft revisions, GPU/dependency versions, backend dispatch, topology, resolved profile including seq128, router overrides and all eight GPU IDs. Check whether the proposed behavior is already present; PR ancestry alone is insufficient.
2. **Activation probe:** write one preregistered trigger and one observable for the specific PR (table below). Run the smallest existing workload shape that reaches it. Record hit count and denominator. Zero with adequate coverage means inactive; missing telemetry means unverified. Stop before a full sweep if inactive.
3. **Scoped correctness:** run the changed path's upstream/reference tests and G01–G05 or quality suite where relevant. A correctness failure blocks performance promotion. Upstream tests must be checked against the actual ported source, not assumed to pass.
4. **Unprofiled screen:** matched control/treatment E1 point and relevant E2 window, same image environment apart from one isolated change, equal cache treatment, fixed schedule/seeds and admission/load. Record latency distribution, qualified goodput, error, replay lag and resource capacity.
5. **Mechanism diagnosis:** first counter deltas and structured spans; Nsight Systems only if timeline attribution remains useful. Nsight Compute only for an identified kernel question. Profiled samples cannot enter the capacity frontier.
6. **Confirmation and final:** follow [protocol replication](../PROTOCOL.md): paired A/B run blocks, held-out seeds/windows, frozen config and full E1/E2 frontier grid for finalists. Publish passing and failed load points, uncertainty and alternative explanations.

Every candidate report has independent verdicts: **applicability**, **correctness**, **activation**, **mechanism**, **service value** and **integration cost**. An active mechanism with no service gain is a valid negative result. An inactive path is not a failed optimization.

## 2. Internal measurement contract

**Request join key:** generate a non-sensitive request/run ID and carry it through loadgen record, external router, API frontend, engine/core and relevant profiler span. Attach session/prefix key hash, replica, API PID, DP rank, start/end, input/output tokens and cache-state ID. If production code cannot expose the full join, record the gap and use an isolated diagnostic instrumented image; do not infer rank from endpoint alone. Do not export prompt text by default.

**Per-run manifest:** source/image digest, patch set, configuration and router hashes, topology, workload dataset/seed/window hash, rate/concurrency, run phase, warmup/measurement timestamps, cache reset/prewarm policy, tokenizer/chat template, sampling parameters, profiler mode, node price scenario, actual GPU count and evaluator/scorer revisions. Verify clocks and UTC timestamps across client/host/containers.

**Continuous samples:** scrape `/metrics` from every reachable frontend/engine/replica/rank, plus DCGM/NVML and host/process metrics at documented cadence. Retain raw labeled series. Validate scrape coverage, timestamp alignment, counter reset, units and missing values. Use measured-interval deltas for counters, not cumulative process-lifetime values. The [vLLM metrics reference](https://docs.vllm.ai/en/latest/design/metrics/) documents cache-query/hit counters, queue and KV gauges and speculative counters, but names/labels must be verified on the pinned image. Record sampler overhead if new high-cardinality traces are enabled.

**Per-step diagnostic schema, only where needed:** phase (`prefill`, `decode`, `draft`, `verify`), logical requests/tokens, padded graph capacity, graph mode/bucket, scheduler budget, queue age, rank wait, selected backend/kernel, proposed/accepted drafts, cache queried/hit/prefilled blocks, tier/transfer bytes and CPU/GPU span start/end. Counters should be low-cardinality aggregates in steady runs; high-cardinality per-request/step logging belongs in short diagnostics.

**Profiler integration:** existing `testing/profiling/nsys_capture.sh` requires `clean_complete.json` plus `manifest.json`, defaults to profile `balanced`, and captures without CPU sampling/context switches. The native and AIPerf manifests are different; define a documented *adapter/marker validation plan* before calling it on E1/E2, preserving exact image/profile/overrides/router/load and matching baseline/candidate captures. Confirm all serving containers and worker PIDs are traced, annotate NVTX phases where available, set appropriate CUDA graph tracing, export SQLite/CSV, and retain raw `.nsys-rep`. For CPU hypotheses enable sampling/context-switch capture separately. Existing `ncu_capture.sh` is an isolated-container kernel microbenchmark path, not a whole-server comparator. [vLLM profiling guide](https://docs.vllm.ai/en/latest/contributing/profiling/), [Nsight Systems guide](https://docs.nvidia.com/nsight-systems/UserGuide/index.html), [Nsight Compute guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html).

**MTP-specific minimum:** before attributing any speedup to speculation, report proposed tokens, accepted draft tokens, verification steps, distribution of accepted length, drafter and verifier time, logical/padded draft rows, delivered output tokens/s and TPOT at the same offered load. Acceptance length can increase while service value falls if drafting costs more. For G01 add the independent statistical sampler fixture. [AIPerf metrics definitions](https://docs.nvidia.com/aiperf/dev/reference/ai-perf-metrics-reference), [vLLM metrics](https://docs.vllm.ai/en/latest/design/metrics/).

## 5. Fixed enhanced evalset and Pareto decision

**Freeze once before candidate selection** as `evalset-v1`: dataset hashes, seeds, exact offered-load grid, tokenizer/template, model/draft revision, cache-state recipe, profile/router and cost assumption. Do not retrofit the historical E1/E2 cohorts or tune on held-out windows.

| Layer | Fixed cohort/points | Why it is in the final set |
|---|---|---|
| E1 historical anchor | Native `agent-f75`, 8K/1K exact output, 75% constructed shared-prefix, Zipf64, `lat-seqs-128`; c256/384/512, 120s warmup/150s measure | Keeps comparability to existing frontier and stresses target decode/caching. Actual hits must be measured. |
| E2 historical anchors | Mooncake median, burst, cache-heavy 600s fixed windows at 1×, 1.25×, 1.5×, 2× timestamp speedup, extending the **same** grid only if saturation not bracketed | Exposes arrival, length and reuse variation; capacity is highest tested passing point. |
| Agent-75 enhancement | A *separately named* cold/warm prefix pair and short/long mixed-length pair generated with the existing native workload parameters, matched offered load | Disambiguates prefill/indexer/graph effects from the historical 8K point; not a replacement for it. |
| Mooncake enhancement | A separately prepared held-out window with recorded trace SHA, plus cache-pressure and idle-gap diagnostic cohorts only when relevant | Checks generalization, eviction and liveness without silently relabelling original windows. |
| Finalist correctness/quality | Relevant G01–G05 fixtures; pinned generation quality subset only for changed math/precision; MTP SPEED-Bench diagnostic for speculation changes | Prevents a fast but incorrect result from entering the frontier. These are gates/diagnostics, not equivalent to E1/E2 cost. |

At each **qualifying, unprofiled** load point compute request cost from the full eight-GPU node price scenario and *custom qualified goodput*; retain request count, output tokens, offered/completed rate, pass/fail reason and client replay lag. Use `cost_per_million_qualified_requests = 1e6 × node_price_per_hour / (3600 × qualified_rps)`; with the existing assumed $36/hour this is `10000 / qualified_rps`. Price is a scenario, not an observed quote. Report a separate token-cost view because request lengths vary. Zero qualified throughput has undefined/infinite cost. Do not mix AIPerf goodput with the custom scorer or compare cost across unmatched hardware counts.

Build the **three-axis cost–TTFT–TPOT nondominated set** only from runs passing the existing p99 latency, completion, error, output-speed and replay gates. For each workload/cohort, a point is dominated if another qualifying point has no worse cost, TTFT and TPOT and is strictly better in at least one. Show median and p95/p99 distributions alongside the selected TTFT/TPOT statistic, and show failed points separately. Compare configurations at matched offered load for latency claims and at highest tested passing load for capacity claims; report paired run-level uncertainty. A tradeoff across cohorts remains visible rather than being collapsed into one score. A single “winner” requires preregistered workload weights or a chosen operating point; otherwise return the frontier.

**Integration acceptance before execution:** validate actual binary help; reconcile the profiler clean-marker contract with native/AIPerf manifests; verify each endpoint/rank and all eight GPUs are scraped; attest runtime image rather than trusting `VLLM_IMAGE`; preserve external router and seq128 overrides; verify request joins and timestamps; ensure the same scorer/hash and cache treatment in A/B; prove a short trace export and profiler overhead isolation; freeze the evalset manifest. These are proposed work items, not completed changes.
