## Adaptive k5 compatibility and limitations

The existing controller is a plausible next lead, not yet qualified. `gpu/spec_decode/adaptive_verification.py:457–519` checks target backends for CPU/device query-length mismatch support and FULL graph support for variable per-request query lengths1–6; hard-wired DeepSeek attention is explicitly checked. `gpu/attn_utils.py:311–362` defines those checks. Additional attention groups outside the ordinary inventory must report ALWAYS. Ordinary `UNIFORM_BATCH` alone is insufficient.

The pinned v4.1 FlashMLA classes report the needed variable-query graph support: compressed-cache builder in `models/deepseek_v41/sparse_mla.py:221–227` and SWA builder in `models/deepseek_v41/nvidia/flashmla.py:38–47` report ALWAYS. The inherited backend API defaults to accepting device/CPU query-length mismatch unless overridden. The actual decode flattens query tokens (`nvidia/flashmla.py:200–204`), uses per-token sparse indices/lengths and passes `q.unsqueeze(1)` to FlashMLA (`:230–245`); it does not demand a uniform six-token sequence dimension there. `v1/attention/ops/flashmla.py:61–75` explicitly permits sparse FlashMLA on SM90 and SM100. This supports an SM90 eligibility case; it does not replace all-current-backend inventory or functional validation. Do not confuse the separate SM100-only Mega attention class with the H200 FlashMLA path.

Turning AV on changes target capture to variable-query decode and triggers startup cost calibration (`gpu/model_runner.py:717–739,1080–1086`). It retains full k5 proposal work. It uses stale confidence double buffering plus expected accepted-token benefit and startup cost tables (`adaptive_verification.py:256–355`), then redistributes the budget on GPU (`:397` onward). The controller chooses a budget per rank; subsequent existing DP max padding and graph-bucket rounding can consume the nominal saving. The baseline timing qualification must therefore expose target verification time, existing padding and the possible saving after synchronization; request-count opportunity alone repeats the C03 selection error. Thresholds, specific measurement windows, correctness checks and decisions belong to the evaluator designer.

There is also a specific interaction with the unmodified baseline: varlen target graph descriptors reserve `num_reqs=min(num_tokens,max_num_reqs)` (`gpu/cudagraph_utils.py:299–306`); the baseline FULL synchronization stores that padded request capacity (`gpu/dp_utils.py:201–210`); draft sizing multiplies it by5 (`gpu/spec_decode/speculator.py:519`). For illustration, five real requests with an AV target budget15 can select target bucket16/request-capacity16 and consequently draft80, whereas the fixed q6 target30 selects36/request-capacity6 and draft35. This follows the captured-bucket rules; it is not an observed AV run. It makes actual draft dispatch and end-to-end savings a necessary future qualification point. No C03 code is being reintroduced or combined with the current timing baseline.

The DeepInfer controller is related but not identical: its pinned `csrc/engine/mtp_varlen.hpp` also uses confidence and graph cost, with additional runtime forward-cost correction and sampler timing. No custom controller port is justified before testing the installed option. A shorter fixed k3 is source-permitted in the inspected DeepSeek config branch, which uses dspark_block_size only as an omitted-k default; it remains practically unqualified for this checkpoint, non-causal attention and graph/correctness behavior.
