Purpose
Stacked on
#56227
(base branch
feat/dsv41-swa-bounded-replay
; the diff shows only this PR's three commits). DeepSeek-V4.1's layers past the last KV-source layer (21-39 on V4.1-Flash) own nothing but sliding-window KV: every later layer attends the compressed KV of the source layers, and only the last 128 tokens' window KV is read after prefill. This is DeepSeek's decoder-side SWA bounded replay: in prefill those layers run on each request's last 128 tokens only, cold prefills included, while layers 0-20 still run on every token. It is a deliberate approximation, not an equivalent reduction of work: the kept rows' window attention in layers 21-39 is bounded at the trailing window (the SWA kernels read no window KV below it), so the last token's hidden state is not bit-identical to a full prefill; the long-range context reaches it through the compressed KV. The accuracy runs below (gsm8k on TP4 and DP4, two passes each) and DSpark's unchanged acceptance length are what this rests on.
DeepseekV4Model
(
nvidia/model.py
): when the layers after the last KV source are all sliding-window and the configuration allows it, the forward is split into
_run_layers
up to the cut,
DecoderReplayLayers
for the rest, and the final mHC collapse. Otherwise the forward is unchanged and a warning names the reason.
DeepseekV41ModelState.prepare_attn
(
nvidia/model_state.py
): after the step's own metadata it builds the replay layers' batch from the same inputs: the replay rows (one Triton kernel fills the rows, the row-subset
InputBuffers
, its slot mappings and its replay start), attention metadata through metadata builders of its own (the runner's hold the batch's metadata past the forward) and, under piecewise graphs, the size of the replay layers' graph. Everything lives in persistent buffers because that graph reads them by address. The result is set on
DecoderReplayLayers.replay_batch
; it is None when nothing trims in an eager forward and under FULL graphs (uniform decode).
DecoderReplayLayers
(
decoder_replay_layers.py
): gathers the seven layer inputs by the rows, runs the layers under a copy of the forward context with the replay batch's attention metadata, slot mappings, padding mask, batch descriptor and DP metadata, and scatters the outputs back to full-batch rows. Under breakable piecewise graphs the replay is an eager break of the model graph: the layers run in a graph of their own (
ReplayCudaGraphs
, keyed by the replay batch's padded size) captured inside the model graph's capture of the same size. Only prefills trim, so a capture's dummy batch keeps all its rows and every capture size gets a replay graph of that size; at runtime the replay batch pads to the smallest capture size that fits, which therefore always exists.
Data parallelism: the replay layers' MoE collectives need every rank's token count, so the model state has the ranks agree in
prepare_attn
with one CPU all-reduce carrying whether each rank trims and its replay token count. Any rank trimming makes every rank replay on those counts; under graphs all ranks run the one replay graph size that fits the largest count.
DSpark (
dspark/speculator.py
): the drafter derives its context KV from the target's aux hidden states, which under decoder replay exist only for the last window of each request;
_context_rows
bounds the context KV writes to the drafter's own window.
Shared changes, none behavioral for other models:
AttentionGroup.make_metadata_builder
(a builder outside the group's own list),
prepare_inputs_to_capture
hands the model state the capture's real cudagraph mode (the default state treats PIECEWISE like NONE), and an eager break of a breakable capture may capture graphs of its own.
The decoder side stays off, with a warning, when the pipeline stage does not hold every layer after the last KV source, under sequence-parallel MoE, prefill context parallelism or microbatching, with an Engram layer after the cut, or with a drafter whose window is wider than the target's. DeepSeek-V4.1 turns sequence-parallel MoE on for EP with TP > 1 under DP, so under DP the decoder side runs with TP = 1 today.
No other open PR implements the decoder side of SWA replay;
#56227
is the encoder side this builds on.
Usage
Nothing to configure: with
#56227
and this PR, DeepSeek-V4.1 on model runner V2 replays on both sides by default, including under
--data-parallel-size > 1
with TP = 1.
--no-swa-bounded-replay
turns both sides off.

[Model] Decoder-side SWA bounded replay for DeepSeek-V4.1
…
e8a0735
DeepSeek-V4.1's layers past the last KV-source layer (21-39 on V4.1-Flash) own nothing but sliding-window KV, so in prefill they only need each request's last window of tokens. DeepseekV41ModelState builds that batch in prepare_attn, right after the step's own metadata and from the same inputs: the replay rows, a row-subset InputBatch, attention metadata from metadata builders of its own and, under piecewise graphs, the size of the replay layers' graph, all in fixed buffers. DecoderReplayLayers gathers the layer inputs by the rows, runs the layers under a forward context of their own (attention metadata, slot mappings, padding mask, batch descriptor), eagerly or in a breakable graph captured inside the model graph's capture of the same size, and scatters the outputs back to full-batch rows. Only prefills trim, so a capture's dummy batch keeps all its rows and every capture size gets a replay graph of that size.

Shared changes: AttentionGroup.make_metadata_builder for a builder outside the group's own list; prepare_inputs_to_capture hands the model state the capture's real cudagraph mode (the default state treats PIECEWISE like NONE); an eager break of a breakable capture may capture graphs of its own.

The decoder side stays off, with a warning, when the pipeline stage does not hold every layer after the last KV source, when the replay batch cannot shrink per rank (sequence, data or prefill-context parallelism, microbatching), with an Engram layer after the cut, or with a drafter whose window is wider than the target's.

[SpecDecode] Bound the DSpark drafter's context KV to its window
…
618e894
A DSpark drafter whose layers are all sliding-window attention can only
ever read the last `window` context positions of a request, so projecting
and inserting context KV for the rest of a long prefill chunk is wasted
work. Under the target's decoder-side SWA bounded replay those rows also
carry no real hidden state (the target never computed them), so
restricting the precompute to the window removes the garbage KV they
produced. It rides --swa-bounded-replay. Adaptive verification sizes the
leading verification requests on the GPU, but those are never trimmed,
so the row selection from the CPU query boundaries still holds.

The DFlash context-KV precompute gains a row-selection hook that keeps
every row by default; DSpark implements it.

Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>
Signed-off-by: Yifan Qiao <yifanqiao@inferact.ai>
[Model] Run DeepSeek-V4.1 decoder-side SWA bounded replay under data …
…
d87ddc6
…parallelism

The replay layers' MoE collectives need every DP rank's token count, and the
replay batch shrinks per rank, so the decoder-side replay stayed off under
DP. DeepseekV41ModelState now has the ranks agree on their replay batches
where it builds them, in prepare_attn, which every rank calls every step:
one CPU all-reduce carries whether each rank trims and how many tokens its
replay layers would run on. Any rank trimming makes every rank replay on
those counts, which are the replay layers' DP metadata in eager mode; under
graphs all ranks run the one replay graph size that fits the largest count,
or the padded batch's when none trims. An idle rank's dummy batch trims like
a real one, so its rows fit whatever size was agreed.

Microbatching (DBO) joins sequence and prefill-context parallelism in the
unsupported list; it runs the model per microbatch, outside this agreement.
