# Independent meta-critic: advance the strongest live mechanism

The user explicitly requested a meta-critic to course-correct overly hard gates
and unexpected failures while pursuing real inference improvements. This review
was written after C25 component allocation 002, before any C25 full-model
integration or service result. It is an allocation recommendation, not evaluator
approval or a change to a historical verdict.

**Prioritize C25 native integration now.** C25 has the strongest local causal
evidence of the three candidates. Parking it solely because its small absolute
component saving appears unlikely to pass C03's 2% service threshold would make
a useful research system unnecessarily unable to learn from incremental gains.
Calling its current component result a service improvement would be equally
wrong. A bounded integration pilot is the missing next evidence level.

## Evidence and the claim it supports

The independently implemented component has 108 passing fixtures, six rejected
negative controls, repeated graph replay coverage, actual BF16 checkpoint
weights, and preserved installed RNG/cache semantics. Its eight timed shapes
all improve under the predeclared component analysis. Historical dominant FULL
draft capacities 1, 2, 4 and 7 save about 45, 67, 70 and 83 microseconds per
**complete five-step call**, respectively. These are 25–35% component gains.
The frozen component source and raw paired results live in
`../executions/sampler-component-002/component/result.json`.

This establishes a correct, faster isolated component under controlled inputs.
It does not yet establish native full-model activation, full-graph improvement,
accepted-token progress, service ITL, quality or production eligibility.
Historical shape frequencies include dummy cooperation and are not latency
weights. As a scale illustration only, 45–83 microseconds divided by a 35.9 ms
ITL is approximately 0.13–0.23%, assuming one exposed invocation per output
token. Do not multiply by five again or by eight GPUs. Queueing can amplify or
hide the effect; this arithmetic is not a service upper bound. The evaluator
already corrected that overly literal bound prospectively in
`../evaluator/C25_PRELAUNCH_REVIEW.md`, before component outputs.

The original C03 brief explicitly describes 2% as a practical threshold chosen
for that experiment. It remains binding for the declared C03/inherited service
confirmation claim. It is not a universal definition of a scientifically real
inference gain. Distinguish a detectable improvement, an economically useful
improvement, and passing the previously chosen 2% service target.

## Concrete next intervention

1. The optimizer should prepare the narrow installed DSpark integration with
   exact eligibility guards, scratch ownership/lifetime and baseline fallback.
   The independent builder should prepare native activation and controlled
   request/rejection/EOS/cancel/recovery checks. Reuse already adequate component
   evidence; another large synthetic fixture expansion is not the next priority.
2. Before seeing integration timings, the evaluator should declare a new named
   **C25 native integration pilot**. Freeze what is timed: an actual full native
   draft graph, or a complete decode cycle at fixed valid progress, rather than
   silently rebranding the existing isolated component. Keep an explicit
   native-call activation witness, actual input/output/state ownership and a
   paired baseline path. If a lighter wrapper test is feasible first, label it
   wrapper integration and retain the full-model gate.
3. Prefer a short controlled pilot that can reuse one cold model load and
   compare native graphs under the same runtime when isolation is demonstrably
   sound. If safely capturing both paths in one model process is impractical,
   use separately attested launches; do not introduce an unsafe shortcut to
   save startup. Root must budget cold load, fixed traffic, drain and cleanup,
   not merely measured kernel time. A suggested first ceiling is two node-hours
   (16 H200-hours) including at most the necessary baseline/candidate startups;
   the evaluator/root should tighten this to the concrete executable plan.
4. A useful pilot answers whether the installed path activates, preserves
   independent correctness, and retains positive native execution savings.
   Set the timing unit, repetitions, order, uncertainty and minimum worthwhile
   native saving before results. A positive bound above zero can establish a
   scoped technical gain; label its practical value separately. Do not import
   the service 2% threshold into every lower-level measurement.
5. Decide whether to allocate one full-service hypothesis attempt after that
   evidence. The current inherited service contract can still be run unchanged:
   its screen needs a positive point estimate and the 3% tail guards; its
   confirmation needs the frozen 2% lower bound. Alternatively, a genuinely
   different, prospectively justified C25 service objective can be registered
   before service data. Preserve the original contract and report that design
   change explicitly. Never lower a threshold after observing a disappointing
   service result, and never count requests or ranks as independent runs.

Reserve the second full-service attempt pending better evidence. A pilot is
not exempt from honest cost accounting merely because it is not called a full
attempt; record actual launches, traffic duration and GPU-hours in the ledger.
Conversely, an integration smoke run should not automatically consume an entire
hypothesis allocation unless the attempt policy actually defines it that way.

## Course correction for the other work and failures

**C26:** the installed loader/dispatch chain establishes BF16 weights, excluding
the proposed FP32-weight mechanism. Close this scope cheaply. Do not cast the
weights or force a third GPU experiment to satisfy a quota.

**C24:** the original timing failure remains unresolved and the exact global
policy needs state/coordination the installed local decision does not possess.
The proposed short-operation check on implicated GPU 6 is a reasonable bounded
discriminator. After that check, either identify a concrete correction or park
the full-model timing work. A string of increasingly elaborate diagnostics with
no decision-changing prediction would spend the night without testing an
optimization. A feasible post-synchronization policy is a new revision requiring
its own value/metadata argument, not validation by the synthetic counterexample.

**Unexpected failures:** component 001's diagnosed read-only mount failure was
appropriately preserved and repaired through a reviewed allocation 002. This
is an operational repair, not a scientific rejection or reason to abandon C25.
Apply the same distinction elsewhere. Preserve correctness failures and stop
the affected implementation; preserve infrastructure failures and permit a
bounded diagnosed repair. Avoid both blind retries and paperwork that prevents
a concrete safe repair already authorized by the user.

No waiver is recommended for RNG ownership, exact finite cache/token behavior,
wrong request slots, corrupt KV, lifecycle recovery, runtime identity or valid
measurement. Numeric occupancy percentages, universal practical-gain targets,
or a fixed diagnostic schedule are design choices: require a stated purpose,
then amend them prospectively if evidence shows they obstruct that purpose.
The meta-critic does not write the candidate, oracle or performance verdict.
