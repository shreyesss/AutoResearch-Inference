Motivation

#42465: DeepSeek-V4.1-Flash with --speculative-algorithm DSPARK and HiCache write_through deadlocks across TP ranks. With SGLANG_ENABLE_RANK_CONSENSUS_CHECKER=1 the ranks diverge on cache_finished_req ... owned_kv_len by 1-2 tokens, so each rank inserts a different prefix and the write-through backups no longer line up.

The mechanism, as @divyvasal found: the folded accept runs inside the target-verify CUDA graph and writes fixed epilogue buffers (commit_lens_buf, out_tokens_buf, ...) that the next replay rewrites. accept_and_finalize(folded_accept=True) returned read_accept(bs), i.e. views of those buffers, and the DSPARK worker put them into GenerationBatchResult.accept_lens / next_token_ids. Under the overlap scheduler _copy_result_to_cpu issues that readback on copy_stream after copy_stream.wait_stream(forward_stream) and then launches forward N+1 without waiting for the copy. When the copy engine is busy, for example behind the write-through device-to-host copy of a ~540K-token prefix, the readback runs after replay N+1 and reads step N+1's accept lengths. Each rank races on its own, so ranks commit different token counts. The in-graph accept is broadcast from rank 0, so the ranks agree on the device; only the host readback diverges.

Modifications

  • dspark_verify.py: DsparkVerifyEpilogue.snapshot_accept(bs) returns clones of the six accept buffers. The clones are made on the forward stream right after the replay, so stream order pins them to step N, and async_d2h's record_stream keeps them alive until the readback has run. TargetVerifyExecutor.accept_and_finalize returns the snapshot on the folded path. read_accept keeps returning views, because the in-graph _accept writes through them (build_accept_outs(..., out=self.read_accept(bs))).
  • scheduler.py: comment in _copy_result_to_cpu updated; no behavior change (the DSpark inline copy under Confidential Computing is kept as validated).
  • Cost: six small device-to-device copies per verify step on the forward stream, no extra stream sync.

Relation to #42812

#42812 clones inside read_accept. That was right at its base (264d1c2, 2026-10-06), where _accept wrote the buffers directly. Since #43790 (2026-10-12) _accept passes read_accept(bs) as its in-graph destination, so cloning there makes the graph write into throwaway clones and the static buffers never update. On today's main the existing test_dspark_accept_tail.py::test_graph_accept_matches_eager_greedy fails with #42812's hunk applied (4 subtests). This PR keeps the alias where the graph needs it and snapshots where the views escape. @shanemort1982 reported the same breakage on #42812 on 2026-10-19 and proposed the same split (views accessor as the write target, clones for the reader); this PR keeps read_accept as the views so the in-graph call site is unchanged and adds snapshot_accept for the reader.

Accuracy / tests

  • test/registered/unit/spec/test_dspark_accept_tail.py::TestFoldedAcceptSnapshot (CPU): the folded accept_and_finalize output must not alias the epilogue buffers and must keep its values after the buffers are rewritten. Fails on main (AssertionError: True is not false : correct_len), passes with the fix. The existing parity case still passes.
  • test/registered/unit/spec/test_dspark_overlap_readback_streams.py (1-GPU): deterministic replay of the interleaving with real streams and async_d2h: a spin kernel on copy_stream stands in for the busy copy engine, forward_stream rewrites the buffers for step N+1; views read step N+1 (the hazard), the snapshot reads step N. On an H200 (main 5cbe237 + this change): both cases pass; against the pre-fix dspark_verify.py the view case still reproduces the hazard and the snapshot case fails. The full test/registered/unit/spec/ sweep passes (308 tests, 176 subtests). Re-run on 2026-10-19 against main 8e7601a: same outcomes, sweep 311 passed, 182 subtests.
  • Not reproduced end to end: the hang needs DeepSeek-V4.1-Flash on 4 GPUs (TP4); @divyvasal validated the equivalent clone at 43.1M tokens per replica with 0 rank divergence in [Spec] DSPARK read_accept: return copies, not views of buffers the next verify replay rewrites (fixes #42465) #42812.
