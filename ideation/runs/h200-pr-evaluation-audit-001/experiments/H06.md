# H06 — Tune the Hopper mHC kernel at small token counts

Lane: **main**. Live-layout priority: **6**. Status: conditional plan; no GPU test or measured gain.

## Problem and causal hypothesis

The fused mHC post/pre-norm split configuration was tuned on Blackwell. A Hopper-specific split can reduce repeated per-layer cost for 1–8 query tokens.

## Applicability to our H200 deployment

Confirm the delayed mHC variant for hidden size5120 and actual per-rank query rows1–8. DSpark k5 at one active request can produce six rows, but DP padding must be observed.

## Isolated control and treatment

A: existing tile configuration. B: #61461 SM90 specialization; all larger-token paths unchanged.

## Evaluation and predicted mechanism

E1: native agent-f75; E2: frozen Mooncake median/burst/cache-heavy. H200 capacity discovery and held-out confirmation in PROTOCOL.md.

Measure: mHC kernel microseconds at rows1,2,6,8 and negative control16; per-rank shape histogram; low-load ITL and full-node qualified goodput.

## Why an additional evaluation is or is not needed

Use existing clients at total concurrency1/2/8, then normal E1/E2. Add upstream numerical tests because FP32 reduction order changes; no new benchmark service.

## Decision and falsification

Apply [the preregistered protocol](../PROTOCOL.md). Confirm path and missing behavior before spending GPU time. Support requires correctness, predicted mechanism movement and a useful held-out SLO outcome. Reject an active, well-measured change with no useful endpoint gain or a correctness/tail regression. Mark absent-path, underpowered or failed-replay cases inapplicable/inconclusive; do not label them disproven. Correctness lanes establish only scoped correctness.

## Evidence limits

Author reports H20 microbench gains and roughly1% low-load end-to-end gain; H200 unmeasured. Not a promise of capacity improvement.
