# E03 walkthrough: captured graph shapes that serving can actually use

**Scope:** explanation and source review. This does not modify the frozen [E03 plan](../experiments/E03.md), attest a running server, or claim a B200 result.

## What the server does

A CUDA graph records a GPU execution for a supported batch descriptor. At runtime, a batch can replay a FULL graph only if a captured descriptor covers its request count, token count, query length and other constraints. Otherwise the manager may choose another mode or eager execution. Graphs reduce repeated launch overhead, but capturing more of them uses GPU memory that could otherwise hold KV cache.

With fixed DSpark k5, a uniform target verification step can require six rows per request (five proposed tokens plus one), while an anchor-sampling draft pass can require five. The `lat-seqs-128` override permits a 128-request rank: 128×6=768 target rows and 128×5=640 draft rows. Those are upper-bound shapes, **not proof** that production ranks reach them. The audited profile defaults to 64 maximum sequences and sets a 512-token graph capture ceiling; check the resolved override and actual scheduler occupancy before applying the 128-row argument.

The pinned [`cudagraph_utils.py`](https://raw.githubusercontent.com/vllm-project/vllm/ac9126e58aa7bbab1856ba6593ba4d5003fea516/vllm/v1/worker/gpu/cudagraph_utils.py) rounds candidate capture sizes to the manager's query length and skips a candidate that crosses token or request limits. A larger ceiling therefore need not create the needed FULL descriptor. [vLLM #62040](https://github.com/vllm-project/vllm/pull/62040) reports a concrete `max_num_seqs=72`, q5 draft hole: one rounded candidate holds 71 requests, while the next holds 74 and is skipped. Its patch retains the full-batch candidate for a single query length. Its GB200/72-request result does not prove the same hole at B200/128 requests.

The separate [InferenceX #3095](https://github.com/SemiAnalysisAI/InferenceX/pull/3095) addresses small-batch capture coverage via a **minimum** capture size. A 512-token **maximum** does not establish that the required small graphs exist. Inspect the actual capture list before adopting a low-load explanation.

## Three arms, one question at a time

1. **A:** actual baseline with the resolved 512-token ceiling and capture list.
2. **B:** configuration-only capture coverage up to the required range, with target and draft descriptor lists checked. Keep k5, topology, workload and model fixed.
3. **C:** #62040 or a reviewed adaptation with the same settings as B, only if B still lacks a needed full-batch draft graph.

Before a serving A/B, record requested tokens, selected descriptor and graph mode **per rank and per target/draft step**, along with eager/PW/FULL fractions and graph-pool/KV memory. If actual occupied shapes already choose suitable graphs, the proposed optimization is inapplicable. If B restores coverage, credit the configuration change rather than the code patch. If C adds coverage, validate numerical outputs and changed-input graph replay before scoring serving behavior.

Run the existing synthetic occupancy sweep around observed boundaries and Mooncake burst windows. Compare TPOT, tails, qualified capacity and admission after accounting for graph memory. Extra FULL graphs can be a net loss if they crowd out useful KV cache. The upstream +4.4% report belongs to its GB200 and long-output conditions; it is not a B200 forecast.

**Current disposition:** enumerate descriptors and runtime dispatch first; then test the configuration arm, and the code arm only if it fills a measured gap. No live graph inventory or GPU comparison was run for this walkthrough.
