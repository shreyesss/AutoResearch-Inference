Purpose
With
--moe-backend humming
and expert parallelism, Humming runs DeepSeek-V4.1's MXFP4 experts on its grouped GEMM. On Hopper the indexed GEMM is much faster for this model. This PR makes
get_humming_moe_gemm_type()
return
indexed
when all of these hold:
the experts are MXFP4 with DeepSeek V4 routing;
model_type
is
deepseek_v41
or
deepseek_v41_text
;
the device is CUDA SM90;
there are no all2all kernels, or the backend is
allgather_reducescatter
.
Without EP, Humming already picks indexed, so nothing changes there.
VLLM_HUMMING_MOE_GEMM_TYPE
still overrides the choice. Since
#56997
, Humming is the default MXFP4 MoE backend on SM90, so V4.1 with EP on Hopper otherwise runs the grouped GEMM by default; this PR moves that default path to indexed too. The rule applies with BF16 activations and with per-token FP8 activations (
--quantization-config.moe.activation fp8_per_token
).
The MXFP4 MoE method (DeepSeek V4/V4.1, Kimi-K3, plain mxfp4) now runs
quantization_config.moe.activation
:
vllm serve deepseek-ai/DeepSeek-V4.1-Flash -tp 8 --enable-expert-parallel \
    --moe-backend humming --quantization-config.moe.activation fp8_per_token
Humming takes the named format as a fixed input schema, with its input-schema fallback off.
Other explicit backends must run the named format, and
auto
keeps only the backends that do. Before, these models ignored the name on every backend. Now a backend that does not run it stops vLLM, on every platform (CUDA, ROCm, XPU, CPU). The DeepSeek V4 MegaMoE backends (
deep_gemm_mega_moe
,
aiter_mega_moe
) build their own experts and do not read the name. On ROCm, the Kimi-K3 AITER path, which skips the backend selector, now refuses a named activation instead of ignoring it. For example,
fp8_per_token
with
flashinfer_trtllm
now stops vLLM instead of running MXFP8. A draft model with its own
speculative_config.moe_backend
inherits the target's
quantization_config
, so the same rule applies to it.
The startup log prints the format Humming runs:
Humming MoE activations: fp8_per_token (group size 0, scale dtype float32)
. The line appears for every Humming MoE model, gpt-oss included.
On SM90 Humming,
mxfp8
and
fp8_per_block_dynamic
stop vLLM at startup, before the weights load. Humming has no e8m0 input scales on WGMMA, and humming 0.1.16 rejects fp32 group scales with MXFP4 weights (
[Bug][Humming] MXFP4 weight + block-FP8 activation is listed as supported on Hopper, but humming-kernels 0.1.16 rejects it
#60600
). Group-wise scales are also 1.2x to 24x slower than per-token in the SM90 Humming GEMM at M >= 256 (numbers in the review reply).
VLLM_HUMMING_INPUT_QUANT_CONFIG
still works as on main, with no early check: a format Humming cannot run fails while the weights convert, as before. With
--moe-backend humming
, setting it together with
moe.activation
is an error.
gpt-oss is unchanged. With no name, nothing changes.

I think it is interesting to support this, but I am a bit skeptical about how safe it is to make it the default, i.e., assume per-token FP8 quantization has no accuracy impact over BF16/grouped-FP8.
Notably, on Blackwell where FP8 activations are already the default, we use MXFP8 (group-32 e8m0 scales), or block-FP8 (group-128); both much finer-grained than one scale per token row. I suspect per-token FP8 is too coarse, and GSM8K is simply not a rigorous enough eval to study real accuracy impact.
I would either make the per-token FP8 path opt-in for now, or evaluate this more exhaustively before making it default, e.g. on agentic evals.

Thanks, agreed. The latest push makes the activation format an explicit, named choice. It uses the existing typed field instead of a new env string, because those names are documented, validated at parse time, and shared with gpt-oss:
--moe-backend humming --quantization-config.moe.activation fp8_per_token
The names come from
QUANT_KEY_NAMES
(
fp8_per_token
,
fp8_per_block_dynamic
,
mxfp8
). Each name is one scale layout on every arch. A named format turns Humming's input-schema fallback off, so it runs as named or vLLM stops.
It applies to the MXFP4 MoE method: DeepSeek V4/V4.1, Kimi-K3 and plain mxfp4 checkpoints. A backend that cannot run the name stops vLLM at startup, also on SM100f. For example,
fp8_per_token
with
flashinfer_trtllm
or
auto
no longer runs MXFP8 silently.
On SM90 Humming,
mxfp8
and
fp8_per_block_dynamic
stop vLLM at startup, before the weights load.
mxfp8
needs e8m0 input scales, which Humming's WGMMA path does not have. humming 0.1.16 rejects
fp8_per_block_dynamic
(fp32 group-128 scales) with MXFP4 weights, although vLLM's supported-pairs table lists it for Hopper. I opened
[Bug][Humming] MXFP4 weight + block-FP8 activation is listed as supported on Hopper, but humming-kernels 0.1.16 rejects it
#60600

The startup log prints the resolved format, for example

[Perf][DeepSeek V4.1] Humming indexed MoE GEMM with EP on Hopper, and…
…
47e6dff
… a named MoE activation format

Humming indexed GEMM with EP on Hopper: for DeepSeek V4.1 (model_type
deepseek_v41 / deepseek_v41_text) MXFP4 experts on SM90, Humming now
picks the indexed GEMM also under expert parallelism, when there is no
all2all or the all2all is allgather_reducescatter. Other EP setups still
use grouped_contiguous. Humming is already the default MXFP4 MoE
backend on SM90 (
vllm-project#56997
), so this also changes the default path. On
TP8+EP, indexed is 47% faster at prefill and 63% faster at decode with
BF16 activations, and 24% and 36% faster with per-token FP8.
VLLM_HUMMING_MOE_GEMM_TYPE still overrides the choice.

Named MoE activation format: the DeepSeek V4 MXFP4 MoE selector now
honors --quantization-config.moe.activation, so per-token FP8 on Humming
is an explicit choice:

  --moe-backend humming --quantization-config.moe.activation fp8_per_token

- With --moe-backend humming, the format is checked before the weights
  load and then passed to the Humming conversion with schema fallback
  off. On SM90, mxfp8 is refused because WGMMA has no e8m0 input scales.
  Setting VLLM_HUMMING_INPUT_QUANT_CONFIG as well is an error. The env
  JSON alone works as on main.
- Another explicit backend that does not run the format fails, and auto
  keeps only the backends that run it. For example, fp8_per_token with
  flashinfer_trtllm no longer runs MXFP8 without saying so.
- The Kimi-K3 SiTU AITER path skips the selector and runs BF16 only, so
  it refuses a named format.
- The Humming MoE conversion logs the activation format it runs.
- user_moe_activation_override() is public and returns None when no
  vLLM config is set.

Without moe.activation, backend and activation selection are unchanged.
