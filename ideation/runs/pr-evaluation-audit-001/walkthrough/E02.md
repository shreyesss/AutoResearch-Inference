# E02 walkthrough: target graph padding leaking into DSpark draft work

**Scope:** explanation and source review. This does not modify the frozen [E02 plan](../experiments/E02.md), attest a running server, or claim a B200 result.

## What the server does

DSpark proposes five tokens per request; the target model verifies them. With data parallelism, ranks agree on an execution shape. A FULL CUDA graph may require more request slots than the busiest rank has real requests. Those extra slots let the target replay a captured graph.

Two counts matter: (1) the maximum **real** request count across ranks and (2) the larger **target graph capacity** after padding. They serve different purposes. The pinned `DPSyncState.num_reqs` may contain the second count for FULL graphs. The drafter's `_build_uniform_batch_dp_sync` then computes its batch tokens from that same count. Thus a target-only padding decision can select unnecessarily large draft work. See pinned [`dp_utils.py`](https://raw.githubusercontent.com/vllm-project/vllm/ac9126e58aa7bbab1856ba6593ba4d5003fea516/vllm/v1/worker/gpu/dp_utils.py) and [`speculator.py`](https://raw.githubusercontent.com/vllm-project/vllm/ac9126e58aa7bbab1856ba6593ba4d5003fea516/vllm/v1/worker/gpu/spec_decode/speculator.py).

For intuition, four real requests and target capacity sixteen would give 4×5=20 logical draft rows versus 16×5=80 capacity-derived rows before the drafter's own graph selection. This is an illustration, not a measured runtime shape or a promise of fourfold savings.

## What the proposed fix probes

[vLLM #58984](https://github.com/vllm-project/vllm/pull/58984) keeps the DP-wide maximum real request count separate from padded target graph capacity. Online DFlash/DSpark draft dispatch uses the real count; target execution and capture-time dummy runs keep the capacity they require. The patch also adjusts online dummy-rank preparation, graph dispatch, attention metadata and draft generation. Review those parts together for DP agreement and padding safety.

The upstream serving comparison used H20, DP8 and adaptive verification **on**. The audited B200 profile uses two DP4 replicas, k5 and adaptive verification **off**. The source mechanism is plausible here, but the upstream improvement cannot be transferred directly. Upstream acceptance varied across benchmark arms; identical request token totals do not establish identical stochastic behavior or task quality.

## First decision check

On the **actual running image**, capture per rank and step: logical requests, DP-wide real maximum, target graph capacity, draft input rows, draft graph bucket, draft GPU duration, and whether the step is online or a startup dummy run. Include skewed and shrinking batches with adaptive verification off. If draft rows never grow from target-only padding, classify this optimization as inapplicable to this configuration and stop before a serving A/B.

If the leak exists, compare A: unchanged and B: #58984 or a reviewed equivalent, with k5 and adaptive verification off in both. Check generated-token correctness, graph replay and DP progress; then measure draft time, acceptance, TPOT, TTFT, tail failures and SLO-qualified goodput with the existing synthetic and Mooncake workloads. Keep diagnostic profiling separate from scored serving runs. A draft-only time reduction is evidence for the mechanism, not yet an end-to-end win.

**Current disposition:** inspect first; test only if an active pad leak and meaningful draft cost are observed. No live runtime trace or GPU comparison was run for this walkthrough.
