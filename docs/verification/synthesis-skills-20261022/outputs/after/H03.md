# H03 — bounded callback-activation investigation

**Selection.** FAST-C remains a feasible dependency/configuration integration hypothesis: its code is already deployed, batching is disabled, and its missing optional package is now available only in staging [H03-E2, H03-E4]. FAST-G is infeasible as supplied for the H200 target because its launch path requires SM100 and has no SM90 fallback. The eight-SM100 throughput result cannot justify this deployment's TTFT experiment; an SM90 implementation would be a separate, unsupported port [H03-E3].

**Hypothesis and alternative.** Installing the required CPU dependency and enabling completion batching might reduce shared CPU contention enough to improve subsequent requests' p99 TTFT under load. This requires completion work to contend with admission/prefill/first-token delivery on the relevant resource. The callback occurs after completion, so its own request's first token cannot directly benefit [H03-E1]. The strongest alternative is that the callback is too small or off the critical shared CPU path, and batching adds delay or overhead without affecting TTFT. No CPU utilization, callback timings or contention evidence is provided [H03-E2].

**What the numbers mean.** The author's CPU microbenchmark reports 100 μs to 40 μs, a 60 μs reduction, at batch size 64 [H03-E1]. It does not establish 60% faster inference, p99 TTFT improvement or local callback savings. If, purely conditionally, that reduction applied once per completed request, dividing by 1024 output tokens yields about 0.0586 μs per output token of amortized callback work. If the timing instead covers an entire batch, attribution differs; its denominator must be clarified. Neither division yields client-visible ITL or TTFT, and CPU work saved is not necessarily exposed elapsed time [H03-E1–E2]. No local service timing or ROI is known. Arrival/completion timestamps alone cannot recover TTFT [H03-E2].

**Prior failure.** The startup failure is an execution error caused by a missing dependency, not a negative serving result: there was no traffic or performance measurement. Staging package availability changes feasibility, but does not prove serving-image compatibility, successful activation or benefit [H03-E4]. Reopen integration readiness without rewriting the prior outcome as “slow” or “refuted.”

**Cheapest next investigation, not performed.** Inspect the pinned callback/configuration path and dependency contract to answer three decision gaps: what timing unit/batch semantics FAST-C actually uses; whether batching can run with the serving image; and whether completion work shares a thread/queue/resource with first-token processing. Record source locations and distinguish observed call relationships from inferred contention. This is cheaper and more decisive than another microbenchmark or GPU run. Do not install packages, change the service or launch traffic now.

**Branches.** Stop pursuing FAST-C for this objective if inspection establishes isolation from TTFT-relevant resources with no plausible contention pathway. If a shared-resource pathway exists, retain the hypothesis but mark service value unknown. Missing dependency compatibility, ambiguous callback units, or absent runtime contention evidence are inconclusive; static source inspection alone cannot demonstrate contention. Reject FAST-G's current binary/path for this hardware and reopen only with an actual compatible implementation [H03-E3].

**Later matched comparison.** If separately authorized, compare batching off/on with the same compatible dependency installed in both arms, pinned serving image/configuration, H200 DP4/EP4 resources, agent-75 request distribution and arrival schedule. Collect actual first-token timestamps for p99 TTFT, callback time, CPU contention/utilization and effective batch sizes; include startup/traffic failures and completion behavior. Profile separately from scored measurements. Preserve output and service semantics and report uncertainty instead of inventing a sample floor or worthwhile-gain threshold. No supported p99 improvement means no demonstrated benefit; insufficient traffic/measurement is inconclusive.

**Self-review.** Advance source inspection only. Feasibility evidence supports a configuration candidate, while evidence for the requested service metric is weak. Sources are supplied synthetic records; no additional source inspection or experiment has occurred.
