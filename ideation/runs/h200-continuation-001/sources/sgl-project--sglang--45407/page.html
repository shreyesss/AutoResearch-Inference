Motivation

On H200 (SM90), DeepSeek-V4.1-Flash with decoder SWA bounded replay (on by default; the cookbook lists breakable prefill as supported with it) cannot serve with --cuda-graph-backend-prefill breakable. The late-layer tail fails in two places, both on paths that SM100 does not take: SM90 has no in-graph low-ratio path (low_ratio_prefill_graph is false), so the ratio-1/2 sources run as eager breaks or, in one place, get captured.

  1. Warmup before capture. The first faulting kernel is the device-side assert in torch.repeat_interleave (Repeat.cu:20: result_size == cumsum_ptr[size - 1]); the CUDA 719 and DeepGEMM errors that follow are knock-on errors. Call chain: bcg_deepseek_v4_low_ratio_sources → forward_low_ratio_sources → token_req_indices → repeat_interleave(req, extend_seq_lens, output_size=positions.shape[0]). Inside the tail, the eager break sees only the tail's live rows, while forward_batch.extend_seq_lens still spans the whole extend. The hoisted low_ratio_req_indices / low_ratio_pos_i64 already hold the tail's rows (live rows first, bucket-sized), but they are only used when their length equals the break's row count, which it does not inside an eager break.
  2. Replay of the first real request. With (1) fixed, capture and startup succeed, and the first real prefill asserts in a replayed graph: the output_size argument (8) must be the same as the sum of the elements in the repeats tensor (6). The source-layer KV write at the start of the tail (write_tail_source_kv) is called directly from the model, not through an eager break, so on SM90 its token_req_indices and the host-side compressor are captured with the capture-time row count.

#45381 fixes a different capture failure of the same low-ratio prefill-graph path on SM12x.

Modifications

  • deepseek_v4_backend.py (forward_low_ratio_sources): when the hoisted rows are longer than the break's rows in an extend, take their live prefix instead of rebuilding the rows from extend_seq_lens. Bucket-sized calls (the in-graph path) and calls without hoisted rows are unchanged.

    • The hoisted rows are longer only under the prefill graph, where both the prefill-graph metadata and the tail metadata store the live rows first and the padding after them. Outside the tail the live prefix therefore equals what token_req_indices computes; inside the tail it is the only correct value. The prefill-graph full top-k break (_prefill_graph_full_topk_break) already takes low_ratio_req_indices[:real] the same way. If a narrower condition is preferred, it can check the tail metadata explicitly; I will test that variant as well.

  • deepseek_v4.py: a new eager break, bcg_deepseek_v4_write_tail_source_kv, slices the source-layer input to the live rows like deepseek_v4_low_ratio_sources, with the same capture-stub contract as _low_ratio_sources_capture_stub. The tail's source-KV write uses it inside a breakable prefill graph when the backend has no in-graph low-ratio path; every other configuration keeps the direct call. The condition reads low_ratio_prefill_graph the same way as the existing low-ratio call site in _forward_prepare. With no live rows it skips the write but still sets tail_source_kv_layer_id, as write_tail_source_kv does, so the source layer's own pass inside the tail keeps skipping its compressor.

  • Tests:

    • TestDSV4LateLayerTailLowRatioRows checks that a tail-sized eager break gets the live prefix of the hoisted rows for both the compressor and the indexer.
    • TestDSV4WriteTailSourceKvBreak checks that the source-KV break passes only the first global_num_token_non_padded_cpu rows of x and positions to write_tail_source_kv, and that with zero live rows it does not call it but still marks the source layer.

    Their run is pending (the test module imports the CUDA backend and the model): I will run them on a GPU host and add the result here. TestDSV4LateLayerTailLowRatioRows should fail before this change (the rows rebuilt from extend_seq_lens do not match the break's row count) and pass after; TestDSV4WriteTailSourceKvBreak covers a function this PR adds, so it has no before/after comparison and only needs to pass.

Accuracy Tests

Setup: DeepSeek-V4.1-Flash on 8×H200, image lmsysorg/sglang:nightly-dev-cu13-20261018-b234b5c3. On that image the four touched functions (forward_low_ratio_sources, write_tail_source_kv, enter_late_layer_tail, prefill_graph_enter_late_layer_tail) match main @ 76560713 except for the in-graph two-level branch added by #43733, which SM90 does not take. The capture stub on the new break was added while rebasing onto main, which gave the low-ratio break the same stub in the meantime; the measurements below predate it. I will re-run startup, smoke and accuracy on a nightly built from current main and update this PR, which stays a draft until then.

Launch flags: --tp 8 --attention-backend dsv4 --moe-runner-backend marlin --mem-fraction-static 0.70 --chunked-prefill-size 16384 --prefill-decode-interval 16 --enable-decoder-swa-bounded-replay --swa-prefix-tails 1024 --speculative-algorithm DSPARK --speculative-dspark-block-size 5 --speculative-num-steps 1 --speculative-eagle-topk 1 --speculative-num-draft-tokens 6 --enable-hierarchical-cache --hicache-ratio 2 --language-model-only, plus --cuda-graph-backend-prefill breakable --cuda-graph-max-bs-prefill 4096 for the graph runs. "Eager" is the same launch without the two prefill-graph flags.

  • A second pair, measured in the same session with --max-running-requests 64: GSM8K 0.9742 with this change and 0.9742 eager.
  • Which requests exercise the changed path: under decoder SWA bounded replay every prefill extend runs the late layers over each request's last min(extend length, 128) rows, 128 being the model's sliding window (SWA_WINDOW), unless it asks for prompt logprobs or every hidden state; speculative verify extends do not run the tail. (--swa-prefix-tails 1024 is unrelated: it sizes how many radix-cached prefix tails the SWA KV pool keeps room for.) So every GSM8K and long-context prefill enters the tail, and the ones whose batch fits the captured buckets (here up to 4,096 tokens and a 16K context) run the two eager breaks changed here. Counts from the server logs are pending.
  • Smoke: 15 real prefills from 1 to 30,000 words (9 single, 6 concurrent, covering the padded bucket sizes) all returned HTTP 200; server logs had no assert and no CUDA error.
  • Prompt logprobs (21 fixed prompts, 40 to 12,000 words, 76,144 prompt tokens, /generate with return_logprob and logprob_start_len 0, T=0): the graph-vs-eager difference (mean |Δlogprob| 0.158 / 0.160) is the same as the run-to-run difference of each configuration (0.159 eager, 0.157 graph). Requests for prompt logprobs run the late layers over the whole prompt rather than the bounded tail, so this check covers the graph's numerics but not the tail path changed here; the tail path is covered by the accuracy rows and the smoke above.

--cuda-graph-max-bs-prefill 4096: with the default capture sizes the graph pool takes about 29.6 GB at --mem-fraction-static 0.70, and the first eager chunk of a 128K cold prefill (chunks past the 16K replay limit run eager) ran out of memory in the eager torch indexer scoring. Capping the capture at 4,096 tokens keeps the pool at 8.75 GB with the same KV pool size. That is a memory-headroom setting for this configuration, not part of the fix: with the default capture sizes the fix also captures, starts and serves the same smoke prefills without errors, with the same KV pool size, long-context retrieval 6/6 and GSM8K 0.9697 (within the ±0.0047 standard error); only the 128K cold prefill ran out of memory.
