Purpose
DeepseekSparseSWAMetadataBuilder.build()
creates one empty
FlashMLASchedMeta
per DeepSeek-V4 layer type. The first
flash_mla_with_kvcache
call of each type runs FlashMLA's tile-scheduler planner, and the later layers of that type reuse the plan (the comment calls it "shared across all ~60 layers of that type within a decode step").
However, the builder runs once per KV cache group. With the packed KV cache layout, DeepSeek-V4.1-Flash's sliding-window caches are spread over 8 groups, and each group builds its own holders. So the planner runs once per (group, layer type). A torch-profiler trace of one TP8 decode step shows 18 planner launches in the target model (before layers 0-9 and 20-27) and 3 in the DSpark drafter (one per draft layer), where 4 are enough.
get_mla_metadata_kernel
is a single 32-thread block with a serial loop over the SM partitions, and every launch sits in front of its layer's attention. On H20 it takes 16.6 µs per launch at 1 request and about 41 µs at 64 requests.
A plan depends on the batch shape and on the values of the decode
topk_length
/
extra_topk_length
. FlashMLA's interface allows reuse only while those values stay the same, but it asserts only shapes and config. Across the KV cache groups of one metadata build pass the values do match:
The SWA lengths come from the same query and sequence lengths, window, valid-token mask and
replay_start
. Each group builds the mask from its own slot mapping, but every sliding-window group writes each scheduled token, so the masks agree;
replay_start
is one tensor passed to every builder.
The top-k lengths count the valid entries each index layer writes. Every decode top-k path fills the entries past a row end derived from
seq_lens
and
next_n
alone with -1 (for example
rowEnd
in
csrc/libtorch_stable/sampler.cu
), under the same valid-token mask. So each index layer of a compress ratio yields
min(rowEnd, topk)
.
That second point is also why a group's same-type layers can already share one plan today, though they take their top-k from different index layers.
This PR lets the groups share the holders:
MRV2's
build_attn_metadata
passes one dict to every group's
CommonAttentionMetadata
, next to the existing
_token_to_req_indices_cache
.
The sliding-window builder takes its plan holders from that dict, keyed by its block size, causality and index width.
What stays as before:
Callers that do not pass the dict (the V1 runner, the draft metadata refresh of the autoregressive speculator) keep one plan per group.
DBO micro-batches and the DSpark drafter build in separate passes, so they never share a plan.
SM100 does not take this path: it defaults to FlashMLA mega attention, which does not use these plan holders.
Planner launches per decode step drop from 21 to 4.
