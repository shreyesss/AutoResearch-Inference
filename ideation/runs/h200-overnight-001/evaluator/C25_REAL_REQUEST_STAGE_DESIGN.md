## Minimal actual-path observation

The installed `StepTimingCollector` is not already complete for real traffic: `execute_model` starts its forward events, but forward-end and drafter start/end markers occur only inside `_dummy_run`; live `sample_tokens` does not close those events. Simply enabling `collect()` would not measure the intended actual-request path.

A new, separately reviewed observer should record preallocated same-stream CUDA event pairs immediately around the existing real `sample_tokens -> speculator.propose` call. Exclude the following draft-token assignment/broadcast. No new synchronization, tensor readback, numerical operation, graph selection, sampler policy, collective or scheduling decision belongs inside a timed call. Retain exact source/device/stream identity and both requested and executed target/draft descriptors. Count every observed call, including declared exceptions; dummy work, startup/capture, prefill/mixed batches and pure decode must remain distinguishable. Recording overflow or missing endpoint events is explicit incompleteness, never silent sampling.

CPU `gather_batch_req_state` already supplies request IDs, state-row mapping, scheduled-token/draft counts, prefill flags and context arrays. Snapshot that existing metadata without GPU reads. The ordinary `AsyncOutput.get_output` already waits on its copy event and exposes copied counts/tokens; an observer after the original method returns can retain evidence without another D2H transfer or synchronization. Resolve timing events only at a bounded window end after the required service drain, or through a reviewed deferred mechanism, never once per request/step. Whether existing phase controls can provide this cleanly is still under builder review.

**Proposal/verification ownership matters:** current `num_sampled`/rejected counts describe verification of the previous proposal; the timed call creates the next proposal. Join by request identity and monotonic sequence when associating a proposal with later verification. Preserve terminal proposals that never get verified. Keep worker-returned accepted-plus-bonus token counts separate from API committed output counts, because EOS/length truncation can differ. Record warmup and measurement requests separately, and retain raw request completion/error/usage evidence.

## Prospective interpretation

The timing endpoint is the CUDA span of a real proposal call. Report all rank, graph-capacity, context and phase distributions, with common fixed descriptor/context strata for A/B interpretation; report unmatched exposure rather than dropping it. Fixed dominant executed draft capacities1/2/4/7 remain visible, with every other observed capacity retained. Do not assume live scheduling produces the padded-native workload or reuse its round-pairing scheme. One A/B startup pair is exploratory; many events/ranks are not independent startup replicates. Any resampling must preserve a declared temporal block unit and be labeled within-start precision.

Report aggregate counted proposal calls, proposed request rows, verified proposals, terminal orphan proposals, worker output and client committed output. Summed per-GPU stage duration divided by committed output is a resource-time exposure ratio; it is not service wall time, ITL or a hard service speedup bound. Thermal/clock/power context, batch/context shifts and any target-stage control are attribution evidence, not an automatic subtraction or new arbitrary all-rank threshold.

No outcomes have selected the prefix, endpoint or budget proposal. Final traffic phase boundaries, warmup/drain semantics, observer flush, statistical summary, resource cap and exact input hashes must be frozen before the new code is executed. If those pieces cannot stay narrow and reviewable within the preparation budget, retain the completed component/native result and the explicit live-stage uncertainty.
