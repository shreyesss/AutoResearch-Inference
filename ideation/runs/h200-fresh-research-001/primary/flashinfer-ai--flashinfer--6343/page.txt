NVFP4 supports 256 or 384 total experts. The process group selects EP4 or EP8;
no separate execution API is needed. EP4 uses the generic fused schedule;
EP8 retains its measured tuning policies. Auto selection uses fused through
256 tokens per rank, then split.

intermediate width a multiple of 128. Raw weight scales use UINT8 E4M3 per
16 values for NVFP4 or E8M0 per 32 values for MXFP4.

across ranks per call, then the median of 50 samples. Split timing includes
both launches. Packing, compilation and cache clearing are outside timing.

megamoe: SM90 NVFP4 W4A8 fused MoE kernel (1/2)
…
5cbbedb
Framework-agnostic kernel headers for the SM90 (Hopper) NVFP4 MegaMoE fused
family -- a single persistent kernel that fuses the cross-rank token dispatch,
both FFN GEMMs (W4A8: NVFP4 weights, FP8 activations), SwiGLU and the combine
reduction over an 8-rank NVLink symmetric buffer.

This is part 1 of 2. It covers the BN256 fused family, which the host policy
selects for per-rank M <= family_threshold; the BN128 split family for larger M
follows in part 2 and reuses every support header added here.

Contents (include/flashinfer/megamoe/, no torch dependency per the framework
separation rule):
  sm90_nvfp4_mega_moe_fused.cuh / _body.inl   the fused kernel
  scheduler.cuh                               dev-m dynamic task scheduler
  layout.cuh                                  workspace / token-pool layout
  nvfp4_dequant.cuh                           NVFP4 -> FP8 dequant
  barrier.cuh, sym_buffer.cuh                 NVLink barriers, symmetric buffer
  detail/                                     ptx, sm90 mma, tma, shared helpers

Dispatch synchronisation uses counter-based push dispatch (the source rank
writes rows straight into the destination pool and release-adds a DONE count)
with a parity-rotated pool, gated by an M-range policy; outside those ranges it
falls back to the NVLink barrier protocol.

Requires -std=c++20 (the kernels take a float non-type template parameter for
the activation clamp).

Verified: 8 template instantiations build clean on sm_90a -- push+rotated,
barrier-only, push-only, static scheduler, BLOCK_M=24, and the Flash / Pro /
MiMo geometries, plus the phase-stamp diagnostic arm.

megamoe: host layer and Python API for the fused NVFP4 MoE kernel
…
c372f6f
Wires the SM90 NVFP4 MegaMoE fused kernel into FlashInfer's JIT pipeline.

The kernel resolves its shared-memory layout, task schedule and dispatch
protocol at compile time, so the plan is selected in Python and rendered into
the config header; one module is built per (shape, plan) pair.

  flashinfer/megamoe/heuristics.py   plan selection (tuning tables, all-M arm,
                                     counter-dispatch policy, pool sizing)
  flashinfer/megamoe/__init__.py     MegaMoESymmBuffer + nvfp4_mega_moe
  flashinfer/jit/megamoe.py          Jinja render + JitSpec
  csrc/megamoe/*.cu, *.jinja         launcher, TMA descriptors, TVM-FFI binding
  tests/moe/test_megamoe_nvfp4_sm90.py

The symmetric-buffer layout is computed in C++ and returned as byte offsets so
Python slices exactly what the kernel addresses. The scale-factor region is
sized for the largest BLOCK_M candidate, since it is allocated once while the
plan varies per call -- sizing it from the current plan silently corrupts every
BLOCK_M != 8 schedule.

Needs -std=c++20 (float non-type template parameter for the activation clamp)
and builds against the pinned CUTLASS 4.4.

Verified on 8x H20-3e (EP8) against the DeepGEMM reference in the same process:
  - correctness: 27/27 bit-identical over Flash / Pro / MiMo at
    M = 1, 2, 4, 8, 16, 32, 64, 128, 256
  - performance: same kineto kernel timer, max over 8 ranks -- 18 of 27 points
    within +-2%, all within +-8%; the spread is measurement noise on a shared
    host (at large M, where the signal dominates, every point is within 2%)

megamoe: make the assertion trap legal in a host pass
…
59eda09
The workspace sizing helpers are CUTLASS_HOST_DEVICE -- shared between the
launcher and the kernel -- so their assertion failure path is also compiled for
the host, where `asm("trap;")` is not a valid instruction. It only stayed hidden
because the fused launcher happens to reach those helpers through constant
evaluation.

Route both paths through FI_MEGAMOE_TRAP(): `trap;` under __CUDA_ARCH__,
__builtin_trap() otherwise. Device code is unchanged -- the coverage build's
cubin is byte-identical.

megamoe: build the fused NVFP4 module with -use_fast_math only when f…
…
3351387
…ast_math is set

gen_jit_spec() adds -use_fast_math to every module unless told otherwise.
For this kernel that overrides the fast_math argument: kFastMath=false picks
expf() and a true division for SwiGLU in the source, but -use_fast_math makes
nvcc lower expf() to the __expf() intrinsic and turns on --ftz anyway, so
fast_math=False still compiled to the fast-math kernel. The DeepGEMM reference
passes --use_fast_math to this family only when fast_math is set, and
fast_math=False disagreed with it on 1-2 bf16 ULPs (M=64, 256 on Flash).

Pass use_fast_math=fast_math so the compiler flag follows the template
parameter. fast_math=True, the default, builds exactly as before.

megamoe: host layer for the split NVFP4 MoE family
…
6daf7a5
Adds the BN128 split path to the Python API. `nvfp4_mega_moe` now dispatches on
tokens-per-rank: the fused kernel at or below `family_threshold` (256), the
split pair above it, where a single persistent kernel no longer fits the
working set.

The split family runs two kernels per call -- L1 (dispatch-dequant + first GEMM,
2-CTA cluster) then L2 (second GEMM + scatter) -- each with its own pipeline
depth and shared-memory budget. Those are template parameters, so they have to
be known before the module is built. Rather than paraphrasing ~100 lines of
shared-memory arithmetic in Python, the reference sizing code is carried over as
`megamoe_sm90_nvfp4_split_plan.cuh` and compiled into a small template-free plan
module that Python queries first; the kernel module is then rendered from its
answer. Mis-sizing that pipeline would be silent, so it is worth not
re-deriving.

  csrc/megamoe/megamoe_sm90_nvfp4_split_plan.{cuh,cu}   plan query
  csrc/megamoe/megamoe_sm90_nvfp4_split.cu              two-phase launcher
  csrc/megamoe/megamoe_sm90_nvfp4_split_binding.cu      TVM-FFI binding
  csrc/megamoe/megamoe_sm90_nvfp4_split_config.jinja
  flashinfer/jit/megamoe.py, flashinfer/megamoe/__init__.py

Two descriptor details differ from the fused path and are easy to get wrong:
the L1 output box is 64x64 (each of the two M warpgroups stores its own
post-SwiGLU tile, so it is not (BLOCK_N/2, BLOCK_M)), and the L2 activation
scales are per-128 like L1's, not per-BLOCK_N/2.

Verified on 8x H20-3e (EP8) against the DeepGEMM reference in the same process:
  - correctness: 6/6 bit-identical over Flash / Pro / MiMo at M = 512, 1024
  - performance: same kineto timer summed over both phases, max over 8 ranks --
    all six points within +-0.5%

megamoe: build the split NVFP4 modules without -use_fast_math
…
1d03b46
gen_jit_spec() adds -use_fast_math to every module by default, which implies
--ftz=true and lowers expf()/division to approximate intrinsics. The DeepGEMM
reference builds the split L1/L2 kernels with no fast-math flag at all, for
either value of fast_math: kFastMath alone picks __expf/fast_rcp or
expf/division in the SwiGLU epilogue. With the default flag, our split kernels
flushed denormal intermediates where the reference keeps them, and
fast_math=False still ran the intrinsic path (1-2 bf16 ULP mismatches at
M = 512, 1024, 2048 on Flash). A SASS diff showed the extra .FTZ suffixes.

Pass use_fast_math=False. Appending --ftz=false --prec-div=true
--prec-sqrt=true is not enough, because it does not undo the expf() lowering.

the FlashInfer and the DeepGEMM call instead of relying on the two "auto"
