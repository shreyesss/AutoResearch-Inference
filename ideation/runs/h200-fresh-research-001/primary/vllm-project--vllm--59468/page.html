Overview

DFlash and DSpark reserve max_num_new_slots_for_drafting draft slots per request in the scheduler token budget (K for DFlash, K − 1 for DSpark), but neither drafts in the target batch. This PR sets those slots to 0 and instead caps running requests (max_num_active_seqs) at max_num_batched_tokens // num_lookahead_tokens, so the separate draft pass still fits its buffers. Fixes #52922.

Claims

  • DFlash/DSpark requests no longer pay for draft slots. A DSpark decode with K = 5 is charged 6 tokens instead of 10. With --max-num-batched-tokens 512 that raises running requests from 52 to 64 and output throughput from 1373 to 3390 tok/s (DeepSeek-V4.1-Flash + DSpark on GB300, table below).
  • The draft pass stays within its max_num_batched_tokens-row buffers. A request cap does this instead of the slots, and it only binds when max_num_seqs × num_lookahead_tokens > max_num_batched_tokens.
  • This applies to DFlash on both model runners and to DSpark (MRV2-only), through the shared scheduler config. Slot accounting for P-EAGLE, PARD and draft models is unchanged.

Details

  • Root cause. Both drafters run a separate fixed-width query pass. Context KV is precomputed from the target's hidden states into its own buffers, and each request's query rows go into buffers of max_num_batched_tokens rows: DFlashSpeculator/DSparkSpeculator on MRV2, DFlashProposer.input_ids on MRV1. The slots only enforced num_reqs × query rows ≤ max_num_batched_tokens. A request cap gives the same bound without spending target budget.
  • Why throughput gains more than 64/52. On main, the 2–32 tokens left over split each new prefill into small chunks. Most steps then mix prefill into the decode batch and miss the FULL decode CUDA graph: ITL p50 is 169 ms on main vs 30 ms here.
  • Divisor. num_lookahead_tokens equals the draft pass's query rows per request: K for anchor-sampling DSpark, K + 1 for DFlash and fill-in DSpark. Each query row writes KV at a position that allocate_slots(num_lookahead_tokens=...) must cover. So it cannot fall below the query width without breaking draft KV allocation, and if it grows the cap only tightens. This also covers fill-in DSpark, whose old K − 1 charge did not bound its K + 1 query rows.
  • Where the cap lives. Right after the startup check, VllmConfig lowers scheduler_config.max_num_active_seqs to the cap only when the cap is below the current limit, and logs why, e.g. The dspark draft pass needs 5 query tokens per request within max_num_batched_tokens=512. Overriding max_num_active_seqs from 128 to 102. The scheduler is unchanged. Only its admission check reads max_num_active_seqs; unlike max_num_seqs, it doesn't size runner buffers or CUDA graphs and isn't part of the config hash.
  • Startup check. The existing max_num_batched_tokens check in VllmConfig now compares against num_lookahead_tokens instead of the draft slots. num_lookahead_tokens is at least every method's slots and covers the DFlash/DSpark draft pass, so the check still rejects a budget too small for one request's draft pass. It is slightly stricter than before: EAGLE, MTP and draft models now need a budget above K, and DFlash above K + 1, far below any practical budget.
  • MRV1. DSpark is MRV2-only. MRV1 DFlash shares the scheduler and its drafter has the same structure, so it gets the same change. It is covered by unit tests only, not end to end.
  • Review changes. Following @TheEpicDolphin's review:
    • the fix moved into max_num_new_slots_for_drafting, and the cap now applies on both runners instead of only MRV2;
    • the cap divides by num_lookahead_tokens, so anchor-sampling DSpark uses K rather than K + 1.
  • Not a duplicate.
    • [Bugfix] Separate target and draft scheduling budgets #53080 (open, conflicting) replaces max_num_new_slots_for_drafting with a per-step draft budget for every method (+237/−77).
    • [Core] Separate DSpark scheduler input budgets #52996 (open, conflicting) adds a DSpark-only budget charged K per request, which leaves DFlash over-charged.
    • [BUGFIX] Fix dflash batched token budget #53970 resizes the drafter buffers; it is complementary.

Good point! Changed to use num_lookahead_tokens which takes the sample from anchor option into consideration:

@property
def num_lookahead_tokens(self) -> int:
"""KV slots to reserve past the tokens the target model is scheduled for.
The drafter writes KV for positions beyond the target model's query
range, so every component that reserves blocks must add this margin:
the scheduler through `allocate_slots`, and the worker warmup, which
builds its own `SchedulerOutput`s. Consumers must read this property
rather than re-deriving their own per-method lookahead, so the
scheduler and warmup cannot drift apart.
"""
speculative_config = self.speculative_config
if speculative_config is None:
return 0
dspark_fill_in = speculative_config.use_dspark() and not getattr(
speculative_config.draft_model_config.hf_config, "sample_from_anchor", True
)
if speculative_config.use_dflash() or dspark_fill_in:
# Fill-in drafting uses a bonus query plus one query per draft token.
# DSpark's anchor-sampling layout does not need the extra slot.
return self.num_speculative_tokens + 1
if speculative_config.use_eagle() or speculative_config.uses_draft_model():
# Anchor-sampling DSpark drafts a block of num_speculative_tokens
# query tokens in which the anchor itself is the first prediction
# position (no separate bonus query), so it needs exactly
# num_speculative_tokens lookahead slots.
return self.num_speculative_tokens
return 0
